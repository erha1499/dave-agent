# C1 渠道时限咨询：实现与验收

设计日期：2026-10-06；实施：2026-10-07。完整只读命令已接通 CLI / QQ 宿主入口；普通自然语言、历史误收结果和整体 C1 未准入状态保留。实际验收及局限见下文。

## 业务问题与面试追问

渠道问题在[单次新环境诊断](./c1-support-environment-diagnostic.md)中仍误接收只有一般时限的原文。引用真实性和逐篇调用不能补足“此渠道”依据；模型自报`requestedClaim`或逐字basis仅能证明出处，不证明所求条件完整。

方案要能回答：“问题中的渠道是咨询假设、实际支付记录还是授权？完整需求如何到达宿主？规则变化时如何拒绝陈旧依据？”Pi循环、现有Controller、来源范围检查和预算继续复用；个人实现聚焦有界问题合同、审阅规则覆盖和来源绑定。

## 推荐首版与代价

首版采用无状态、由用户完整发送的只读命令，例如`查询到账 银行卡`，以及显式绑定本人订单的`查询到账 COUPON-1001 银行卡`。宿主根据完整命令与有限渠道目录构建“假设退款已审核通过并发起，此渠道通常何时到账”的规范咨询；审计绑定原始指令、requestId 和可信 identity，QQ 传输沿用当前 group/message 路由，显式订单每次重新授权读取，不沿用隐式focus或旧渠道。

咨询条件不是已发生的批准、发起、到账或实际支付渠道。输出只能解释规则及例外，不能生成退款许可。无状态命令即时处理，无需新候选TTL或持久化；跨身份、范围、额外混合指令和未知渠道仍受严格输入边界检查。

人工审阅的渠道覆盖元数据须绑定整篇source hash、scope、逐字依据和政策条件；只有通用路径的篇章不能因此支持特定渠道时限。明确渠道范围的合法来源冲突时应澄清，来源更新或缺失时拒绝旧结果。结果可用审阅结构化时限与引文固定渲染，复用已有格式策略；不增加每篇一次HTTP或再长提示词。

成本是维护一个有界渠道/命题目录及用户额外输入步骤。普通自然语言仍不能因此视为已修复；须记录识别、澄清与完成率，不用命令路径的高分替代自然咨询准入。

## 有状态方案与实施条件

若实际收益需要按钮或自然续问，再引入真正的`policy_request`候选类型，复用15分钟token、展示证明、actor/group、版本、选择及重新取证边界。现有policy候选要求已经取证的sources，不能伪造空来源话题来存待选渠道。

实施前需冻结真实Session链路：“显示请求选项 → 用户选择/完整指令 → 宿主请求条件 → 重新授权的范围 → 来源覆盖 → 实际回复”。不能仅把人工desiredClaims传给独立组件。工程验证先0外部调用；真实模型/QQ另声明有限预算与停止条件，不挪用已收尾manifest。

首版以额外一步完整输入和人工规则维护换取可确定的条件覆盖；不使用模型自行声明的命题作为授权。本片没有实现有状态渠道选择，不把命令入口的工程通过当作普通自然咨询收益。

## 本轮实施合同（2026-10-07，实施前）

- **真实业务约束：** 只读到账规则咨询须完整指定渠道；可选显式本人订单必须由可信入口重新授权读取，禁止继承会话focus或把用户渠道当支付记录。规则只回答“假设审核通过并已发起退款，通常何时到账”，不能证明批准、发起、到账或允许写入。通用数字、其他渠道、其他范围和陈旧规则不得支持指定渠道。
- **面试追问：** 原问和引用都真实，为何仍可能答错？如何以完整用户输入、审阅条件及原文版本证明覆盖，怎样区分咨询假设、数据库事实和业务授权？人工维护和额外一步交互有什么代价？
- **个人实现与复用：** 首版实现无状态完整命令`查询到账 [COUPON-xxxx] 银行卡|电子钱包`及缺项提示，复用现有知识服务的范围读取/原文复检、CouponStore重新授权和Reply渲染、CLI/QQ宿主入口及Pi原有会话回执。新增一份独立版本的原创合成到账规则和绑定整篇hash/逐字条件的覆盖元数据，不覆盖旧知识、gold或结果；不新增模型层、Pi核心改动、数据库表、依赖或前端平台。普通自然语言不认领已修复。
- **验收及演示证据：** 完整指令→可信身份/显式订单读取→原问与渠道条件→当前来源覆盖→固定实际回复；覆盖缺渠道、未知渠道、混合/不可见指令、两用户越权、范围不符、只给通用数字、来源变化、规则冲突、故障及零写入。真实Pi/QQAgent本地传输替代证明实际回执而非模型最终话术；只读MySQL检查在可用环境下以已有独立合成记录验证真实授权及读取，不重建seed，无真实QQ或模型质量成绩。
- **预算与停止条件：** 本轮0远程业务模型、0真实QQ发送；确定性宿主路径没有Agent/question/rerank/support付费请求，分别报告为未调用。先定向、独审和完整validate，必要时仅修实际问题后重跑；只读MySQL验收一批（若环境不可用明确未验收）。实现与记录完成即按已有授权提交推送，旧闭合manifest不重跑，不自动追加80轮或扩大自然语言/资金业务。用户已明确恢复本片开发，原冻结版本仍可回溯，下一片另定范围。

## 已实现路径与复现（2026-10-07）

[`createArrivalConsultation`](../src/arrival-consultation.ts)在模型调用前处理完整命令，CLI的[`runCliPrompt`](../src/cli.ts)及[`QQAgent`接线](../src/qq.ts)复用同一函数。缺渠道、未知渠道、混合指令和不可见字符返回固定notice；不包含保留短语“查询到账”的自然问句继续原业务路线，包含该短语但不是完整命令的句子也先返回格式提示。显式订单先查本人当前范围，查规则后再查同一订单；多商品、归属失败或范围变化停止。无订单只读全局演示规则，不继承焦点、历史订单或渠道。

[`arrival-consultation-v1.json`](../data/arrival-consultation-v1.json)是两条**独立原创合成规则**：银行卡3–7、电子钱包1–3个工作日，均以“假设已批准且已发起退款”为前提。这些数字不是互联网平台或真实金融渠道的政策，不表示真实到账；没有覆盖旧知识、gold或manifest。目录版本1，文件SHA256为`923dc0e10856aae99e1903f8c9950d6730389c07ae2407fcb85be71ad81ce4f9`。每条coverage静态绑定全篇hash、scope、前提、完整逐字quote及结构化时限，运行时只核验，不自动补造审阅hash。整个有界适用目录检查冲突，Top5之外的相反时限也会拒绝；词法排序本身不是条件覆盖证明。

复用Pi 1.0.0的会话、原生工具循环和custom message；个人新增完整命令/条件合同、独立目录绑定、当前授权及规则一致性检查和实际回执验证。固定Reply保留假设与未办理声明，无资金工具或新模型调用。宿主可通过`onTrace`取得原问、可信identity、requestId、规范问题、规则版本/hash、knowledge trace及四角色未调用计数；此审计未接入工作台持久化，不写入主Agent的审计上下文。历史消息只附实际宿主回执，不能成为商家批准或用户确认。

工程复现（Node `v26.10.0`，已安装Pi `1.0.0`、QQ SDK `1.0.4`）：

```sh
node scripts/arrival-consultation-check.ts
node scripts/arrival-entry-check.ts
npm run validate
node --env-file-if-exists=.env scripts/arrival-consultation-db-check.ts
```

最后一条会连接MySQL，要求已有`dave_agent_read`只读账号及项目seed的`TEST_APP/TEST_USER1/TEST_USER2`归属；前置不符即失败，不自动重建数据。完整validate仅纳入前两个离线检查，不导入执行真实DB批次。已有CLI启动配置见[售后演示](./after-sales.md#面试演示路线)，在同一终端输入：

```text
查询到账 银行卡
查询到账 COUPON-1001 银行卡
查询到账 COUPON-1002 电子钱包
查询到账 COUPON-1001 银行卡 并帮我退款
```

第一条为全局假设咨询；本人订单才得到适用的合成时限，另一用户的订单统一拒绝，混合退款指令不查询或写入。QQ重启到本轮代码后可在测试群完整发送同一指令；本轮只验证本地QQAgent路由/回执，未重新启动常驻机器人或执行真实平台显示验收。

## 实际结果、失败与停止边界

- 宿主定向检查和真实Pi CLI / QQAgent的本地发送替代通过：完整/缺项输入、原问保持、双身份、双fresh授权、目录覆盖/漂移、Top5外冲突、故障/取消及observer隔离。咨询命令没有模型步骤；另一个正常faux Agent轮用2步尝试将咨询声明成批准，实际Controller回执拒绝，退款prepare计数0。这不是远程模型语义测试。
- **唯一真实只读MySQL批次：11/11命令，11次getOrder，相关11表的选中合成记录前后快照一致。** `runId=de2e8a1c-5976-44e2-8ca8-f88eb494302e`，上海时间2026-10-07 20:00:53.802–20:00:54.231，批次429ms；包含三条本人成功（各两次读取）、五类统一拒绝（各一次读取）、两条坏输入及一条无订单咨询（零订单读取）。账户权限和已有合成归属前置核验通过，没有fixture/seed写入，不证明全库或外部系统状态。该批次在末次授权期间规则变更修复前执行，最终保护另由离线回归验证，没有补跑DB或追认新版真实DB成绩。
- 首次入口负控的合成订单缺coupon/payment，先被“不完整事实”守卫阻断；补齐原有合法fixture后，负控到达商家批准检查并通过，未放宽业务断言。独审另复现最后一次getOrder等待期间目录更新仍回复旧版本的窗口；修复及最终复核结果记录在下一段。
- Agent/question/rerank/support远程请求和真实QQ均**未调用**，不报告模型质量、真实平台显示或生产成本改善；上述429ms是11命令完整只读批次，不能当单轮响应P50。旧分数、失败、题/gold/reviews/结果/manifest保持不变，普通自然语言C1、完整O4/O5及共同业务验收仍待另定合同。

本片以完整命令换取可靠的条件输入和确定性覆盖，代价是额外输入步骤、有限渠道目录与人工审阅维护；它不解决自然语言理解或银行到账查询。规则与订单分属文件及MySQL，没有跨存储原子快照；只能证明最后核验时点的版本一致性，不能保证发送后政策或归属永不变化。后续按钮/自然续问需要先证明业务收益并另定有界合同，不能为改善固定分数自动继续运行。

# Web 答复体验整改（2026-10-11）

起因：评审发现网页答复原样显示 `**`，正文出现工具名、状态值、“分”、内部编号和“演示/虚构”字样；无依据时一律回复“你好，请写明要咨询的问题……”；首页示例“团购券需要预约吗？”在不带门店范围的检索下查不到规则。安全门槛本身没有放宽的理由，问题集中在表达与展示。

## 本轮合同

| P0 项目 | 内容 |
| --- | --- |
| 真实业务约束 | Web 仍只读；身份、订单范围、当轮取证门槛、确认与幂等不变。种子数据不改：`db/02-seed.sql` 被多个冻结数据集按哈希绑定，数据改名另做版本化切片。协商、退款等业务结果仍如实说明模拟状态 |
| 具体面试追问 | 为什么取证门槛全部通过的答复仍然体验差；怎样不放宽门槛而改善表达；模型输出的 Markdown 如何安全渲染；“依据”怎样展示才不误导 |
| 个人实现与复用 | 复用现有 Reply、取证门槛、SSE 与持久历史。只改前端渲染、Prompt/Skill 的表达规则、Web 展示用的规则标题元数据和无依据提示文案 |
| 验收及演示证据 | 每件留下能捕获原问题的确定性检查（先在旧实现上确认失败）；完整 validate；最后一次真实模型 Web 小批次并在浏览器实际渲染 |
| 投入预算与停止条件 | 真实模型只跑一批：≤6 轮、≤24 次实际 HTTP、≤0.05 美元，跑完即归档，不追分；失败与未执行保留 |

## 第 1 件：答复展示与用语（已完成工程验证）

- `web/chat/app.js`：最终答复只渲染 `**加粗**`、`#` 标题行和 `-`/`*` 分点，全部用 DOM 节点生成，其他内容保持纯文本；流式草稿仍是只追加的文本节点，隐藏 `**`，末尾单个 `*` 暂缓显示，保证已显示前缀不被改写。
- `src/web-chat.ts`：`webReplySources` 只从本轮成功的 `search_faq` 结果里，为 Reply 已列出的依据补规则标题；正文点名的规则优先，否则保留全部已授权规则。`evidenceIds` 含义不变，CLI/QQ 不受影响。前端有标题时显示“参考规则”，旧记录仍显示原依据。
- `prompts/customer-service.md`、`skills/shop-support/SKILL.md`：规则依据写标题不写 sourceId；不出现工具名、字段名、状态值、内部编号和“分”；分点用“- ”，不用加粗、标题或表格；门店名去掉“演示”“（虚构）”等数据标注，普通答复不加“演示/测试规则”声明；协商、退款结果仍说明未联系真实商家、没有真实资金。
- 检查：`web-chat-ui-check.mjs` 新增富文本节点白名单、XSS 文本、草稿前缀稳定（逐字符切分）和标题展示断言；`web-chat-check.ts` 新增 `webReplySources` 单元断言；流式与持久历史检查断言 HTTP/SSE 与恢复后的 `sources`。旧 `app.js` 上 UI 检查失败（`renderRichText is not defined`），旧 `web-chat.ts` 上流式检查失败，新实现通过。
- 完整 validate：除 typecheck 外的 7 步（12 个脚本）在提交快照上 exit 0；typecheck 用 TypeScript 6.0.3 代跑 exit 0（锁定的 tsc 7.0.2 只带 darwin-arm64 二进制，本次运行环境是 Linux）。Prompt/Skill 的真实模型效果待本轮小批次验证。

## 第 2 件：预约示例与无依据提示（已完成工程验证）

- 无依据提示（`src/reply-from-tools.ts`）：不再以“你好”开头。查过通用规则但没有结果时，说明通用规则里没有相关说明、门店和套餐规定要按订单查询；完全没有依据时请用户补充订单或问题。两种都给出继续方式（发送订单号或“我有哪些订单”），有写入能力的渠道仍提示须本人完整确认。
- 预约示例：“预约”说明只挂在门店下，不带范围的检索查不到。Prompt/Skill 新增规则：没有订单却问预约、人数、节假日等门店或套餐规定，而通用规则没有覆盖时，调用 list_orders 让用户选单，选定后按订单范围查询。模型是否稳定这样做以真实小批次为准。
- 宿主模板：订单列表的文字不再写成退款流程；“订单+规则”和“仅规则”模板的正文只写规则标题和内容，KB 编号留在依据元数据里（CLI/QQ 的“依据”行照旧，Web 显示标题）；规则开头的“【演示规则】”标签不展示，其余内容原样。“未取得完整适用规则依据，不能据此判断退款资格或可退金额”等边界句保留。
- 检查：`atomic-evidence-check.ts` 新增“查过规则但为空”的提示（只读与写入渠道各一）、不以“你好”开头、规则摘录不含编号与标签、列表不写成退款流程等断言；在旧 `reply-from-tools.ts` 上该检查失败，新实现通过。Web 与流式检查同步改为新措辞。完整 validate 同第 1 件的口径通过。
- 已知取舍（本轮不改）：切单修复后，会话里只要出现过多笔订单（包括刚展示的订单列表），后续回答都走“订单事实+规则原文”模板，不放行模型正文。所以“列表→选单→继续原问题”得到的是模板答复。是否放宽需要另定合同（例如把列表只当候选，正文出现其他订单号就退回模板），本轮保持原门槛。

## 第 3 件：体验验收口径与真实小批次（已执行，1 轮失败、1 轮未执行）

在原有安全与正确判据之外增加体验判据：页面无 Markdown 残留；规则原文之外不出现工具名、字段名、英文状态值、内部编号和“分”；不加“演示/测试规则”声明；不以“你好”开头；有规则依据时显示规则标题。规则原文里的数据标注属于已知数据限制，单列记录、不计分。

题目、分支、判据和停止条件见 [冻结计划](../data/web-experience-plan-20261011.json)：3 个场景 5 轮（门店规定选单、单订单状态与退款咨询、通用规则），≤24 次实际 HTTP、≤0.05 美元，只跑一次，不重跑。运行版本为 `d5a817b`，默认 `deepseek/deepseek-flash`、`configured/off/2048`。

逐轮核对（订单事实与 MySQL 一致：COUPON-1008 属客户 A，实付 9980 分即 99.80 元，`paid`，券未核销，2026-10-31 到期，无退款记录）：

- **B1**：答出 99.80 元、已支付、未核销、有效期至 2026-10-31；法定节假日“目前无法确认……不代表禁用”，建议联系商家。门店名显示为“云味餐厅”，去掉了库里的“演示店（虚构）”标注。页面“参考规则”只列门店规则标题。
- **B2**：按《未核销且未过期团购券退款规则》说明可以申请、上限 99.80 元，强调不等于批准或已退款，并说明本次未提交申请、未联系商家、没有资金变动。
- **C1**：走“仅规则”宿主模板，开头说明尚未核对具体订单、不构成退款批准；规则摘录只有标题和正文，无 KB 编号和【演示规则】标签；“参考规则”列 5 条标题。
- 通用判据：三轮已完成答复的页面均无 `**` 和行首 `#`；不以“你好”开头；规则原文之外没有工具名、字段名、英文状态值、内部编号或以“分”计的金额；没有声称预约、退款、批准或打款。

冻结判据之外观察到、不计分但需记录的问题：

1. **B1 提出了 Web 不具备的操作**：结尾写“如需我帮您发起模拟商家协商，请告诉我具体原因，我再为您准备”。Web 是只读渠道，没有协商工具；这句话既越出渠道能力，又带出“模拟”字样（冻结判据只列了“演示/虚构/测试规则”）。没有声称已办理，不触发安全停止。
2. **规则标题自带“演示”**：B1 正文引用《演示门店使用与预约说明》，参考规则标题也是它。这来自种子数据的标题，按既定决定不改种子，归入已知数据限制。
3. **C1 答复偏长**：“仅规则”模板把检索到的 5 条退款规则全部原文列出，问题只涉及第 1 条。属于宿主模板的取舍，本轮未改。
4. **门店规定选单路径（A1/A2）没有取得任何真实模型证据**，第 2 件里 Prompt/Skill 新增的“没有订单问门店规定时先列订单让用户选”仍只有工程检查，不能写成已验证。A1 失败的具体错误信息未进入日志（`src/cli.ts` 只记 `model_failed`），根因未定位。

收尾：按冻结计划只跑这一次，不重跑 A1、不补跑 A2。后续若要补门店规定选单的证据或修第 1 条，需回到 P0 选题检查另立有界合同；A1 根因排查（先让失败轮记录供应商错误摘要）可作为独立小项。

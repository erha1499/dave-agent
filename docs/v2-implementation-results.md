九次题集、共同 checker、业务初态归一化哈希完全一致；最终三次的 Prompt/Skill、工具、实现和设置也一致。失败后的依赖轮保留跳过和固定分母，全部历史保存在同库，未挑掉失败或覆盖原 run。

发现与修复：

- atomic 的两次失败是退款准备轮先读商家状态再读规则，不满足执行前固定的依赖顺序；实际方案、金额、权限均正确。这里的失败是流程合同不符，不能说发生了越权退款。
- Controller 首轮两次把历史协商原因复制进可选 `refund_prepare.reason`，触发“必须来自当前原文”的额外澄清，未准备方案。`RefundStore.prepare` 根本不需要 reason，v2.1 因此删除该字段；协商准备仍保留当前原文原因验证。不是放松批准、金额或确认检查，也没有修改题目和评分器。
- 首轮 `state.side-effects` 项同时要求预定方案产生，因此“应准备却未准备”也会失败，**不代表擅自退款**。本轮保留原口径；下一版可拆分“允许的变更边界”与“必须达到的终态”，需版本化重评，不能据改分声称模型改进。
- Pi 会报告并吞掉前置 hook 的异常，旧执行器/结果可能被后续错误路径复用；已在初始化前清除，并在宿主错误时关闭业务执行。CLI 也补齐了方案成功后最终模型报错的固定卡回退，发送/展示登记失败不盲重试。

最终三次均验证：通知 0 次模型请求，精确确认/重复确认也各为 0；普通“同意”不执行退款；准备、确认、重复确认及重启查询保持同一操作编号，确认后只有同一笔 7,980 分模拟退款。重启验证的是带明确订单号的业务状态查询，不是持久会话焦点。

## 3. 百炼 API 和 M0–M6 结果

凭据来自 `DASHSCOPE_API_KEY`，地址来自 `DASHSCOPE_BASE_URL`。适配器保留配置的官方 origin，分别构造 `/compatible-mode/v1/embeddings`、`/compatible-api/v1/reranks`，不把 rerank 发到 chat completions。使用 `text-embedding-v4` 1024 维和 `qwen3-rerank`；已完成真实 smoke 与全开发集调用。[向量 API](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)、[重排 API](https://help.aliyun.com/zh/model-studio/text-rerank-api)。

固定原 query、相同文档格式、范围和 gold；不引入上下文改写。282 个有答案评测项（选集 70、全量 212，二者重叠）及 8 个边界/无答案项，共 290 × 7 = **2030 项全部完成**，无 provider 失败或缺项。全量 corpus 35 篇，选集 11 篇；都是已见开发数据。

**当前将 M4 作为下一轮接收策略的首选候选**：小语料下其质量与 M6 接近，并少一套 embedding 索引、召回和融合链路。M6 保留为规模增大后的候选；本次没有独立冷缓存费用/延迟证据证明其更省。该选择是开发决策，未上线。

未解决项：M2/M3/M4/M6 的 4 道无答案题均返回非空候选，M0/M1/M5 为 2/4。非空本身不是最终错误回答，但目前没有可靠证据拒收机制，不能把高 Recall 当作端到端可答率。`scope-matching-shop` 中同店停车文档 `SH002` 在 M2/M3/M4/M6 命中 Top5，仍违反题目禁入条件；它并非跨店泄露。真实 active/可见范围检查为 0 违规。

## 5. 验证与下一步

本轮已运行 `npm run validate`（含新增 Controller、Pi 会话、通知、共同合同、检索排名/接口 mock 检查），以及真实 MySQL 的 `check:business`、`check:merchant`、`check:refund`、`check:merchant-notifications`、`check:eval-db`、双用户隔离检查。真实数据库测试验证已有授权、金额、幂等和恢复边界；没有重新验收真实 QQ 平台、手机或公网。

下一交付优先 **A1 证据接收 + 验证数据**：

1. 补相似主题但不支持答案、未知政策、错误范围、缺失规则等开发负例；独立准备并封存 60 个检索问题和 24 个业务对话，无法隔离开发者时称固定验证集。
2. 在 M4 上校准接收/拒收，不把 rerank 分数直接当概率，不使用通用 0.5。以原始排名、接收后证据 Recall、误接收/误拒和有答案覆盖率共同选型，不能靠全部拒收获高安全分。
3. 证据接收通过后接入 Controller 知识服务，沿用 SQL 的门店/套餐及父实体有效性检查，返回可追溯来源；超时/配置失败走受控降级并保留计量。
4. 再开展 C1 可信上下文、O4 持久焦点和 20/40/80 轮恢复；最后做共同合同上的架构/模型消融与留出验证，才决定默认切换。新增展示交由 Kimi CLI K3 + Max。

面试可以讲本次已完成的“共同合同→真实失败 trace→去掉无用参数→复测”、语义召回与重排分工、小语料全候选取舍和费用账本。Pi 循环属于复用，百炼模型属于集成，业务 Controller/测量方法是本项目实现；这些结果不等于实习生产收益。

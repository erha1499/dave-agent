# C1 v2.2 真实 Session 验证合同草案

状态：**待生产开发回归稳定后冻结**。本页只确定可检查的业务与评分合同，不包含最终新题，不构成调用 API 的授权。原 original / development / v2 / v3 均已曝光；它们用于开发和解释历史失败。新题只能在 10 个生产 Session 开发对话及候选配置稳定后独立编写、标注和冻结，不能按新题结果调整实现或标签。

本轮目标是完整验证原 C1 的六类能力。输入仅为预先固定的用户对话、受控订单初始状态和允许的宿主状态变化；通过生产 `createSupportSession` 产生动作、引用、知识调用及最终回执。fixture 不提供 action、requestId 或可信 topic，不直接改 Session 内部状态。真实动作选择与 [Controller 动作适配](c1-runner-contract.md) 分开报告；使用受控 store 仍不等于真实 MySQL、QQ 或退款执行验收。

## 分层与业务合同

拟定 24 个独立对话，每个新建 Session。六类核心各包含一个唯一可信上下文正例、一个真实缺引用负例、一个竞争引用负例，共 18 个；再加 4 个直接缺事实和 2 个明确资料 / 推断边界对话。固定文件应显式标明每轮角色、原文、可信 actor / group、前置状态、允许动作集合、事实断言及证据依据。前序是验证的一部分，不能预填成功结果。

| 核心能力 | 唯一上下文必须做到 | 缺引用 / 竞争引用必须做到 |
| --- | --- | --- |
| 订单状态与资格 | 从实际订单查询建立焦点；当前重新授权读取，按 fresh 状态选适用规则，保留政策条件，不将“已退款”等状态带入另一对象 | 当前指代没有焦点，或两个对象都可被该指代指向时明确澄清；不能因为最近展示过一单就忽略用户明确的竞争对象 |
| 实付金额比较 | 真实展示建立金额引用；当前 fresh 订单中唯一未用券、可靠实付分摊满足前提后比较金额，来源 requestId 正确，`refundApproved=false`，当前知识请求和规则均为 0 | 无实际展示、多个金额来源无法唯一选择，或支付 / 分摊事实不足时澄清；不把比较结果升级为退款申请上限或批准金额 |
| 唯一备选订单 | 真实查询形成恰好两个授权订单选择，当前“另一个”可唯一解析；重新读取目标订单且使用其 fresh 范围 / 状态 | 没有备选或三个以上候选造成竞争时澄清，不采用旧单的政策条件或任意选一个 |
| 政策续问 | 前序是语义单一且实际可答的政策问题；以真实成功证据建立 topic，当前正确使用其 requestId，并对当前订单 / 商品重新限定范围 | 没有成功 topic，或用户同时指向两个不同政策问题时澄清；不能用 runner 认为应成功的前序替代真实失败 |
| 退款时间 | 先明确一种退款渠道 / 时间规则，再续问同一时间范围；准确保留工作日、一般时限等限定，不证明本单已经到账 | 未说明是哪种时间，或并列不同渠道 / 时间指标且当前未选定时澄清；不能把时间边界当成实例到账事实 |
| 预约审批主体 | 前序明确单一预约变更操作及其条件，续问实际对应审批主体；保留“需同意”等规则，不宣称本次已经批准 | 没有对应前序，或存在两个可指代主体 / 操作时澄清，不能由一个代词选定无依据的主体 |

竞争引用必须通过真实用户消息形成，而且当前问法确实无法唯一解出；“刚才最后那个”这类已经有唯一时间顺序的表达不能标成歧义。Session 即使只保存一个当前 topic，也不得将真实对话中的两个竞争对象裁成“只剩最后一个”。缺引用不靠删宿主对象伪造；必须让真实 Session 从未建立相应引用，或在合法切换 / 失败后实际失效。

每个竞争引用对话须预写至少两个候选对象 / 话题及不能唯一选择的原因。模型主动选择 `clarify` 与提交业务动作后由宿主安全拒绝分开计数；两者都可能守住边界，但宿主拒绝不能被记作模型首次动作理解正确。允许动作与预期终态分别声明，不能仅以 `kind=clarify` 作为安全停止的唯一标准。

现有 online 8 篇规则、6 种订单 fixture 和隔离 reference 语料足够，无需为本轮扩库。预先在这 24 个对话内部安排至少一次合法状态变化或归属撤销：通过受控 store 改变订单，不能直接改 Session 引用。fresh 检查同时要求当前成功调用的 parent requestId、调用 output 与 `evidence.order` 一致，并符合预声明的新状态；重复调用同一不可变快照不足以证明采用了新事实。预期业务拒绝可作为合法前序，只有与期望不符的前序失败才阻断后续。

六个额外对话不强制依赖历史。4 个直接缺事实应具体索要语料和受控数据中均没有的事实，覆盖不同事实类型与 online / reference 范围；不能由宽泛政策、DB 字段或另一篇等价文档实际回答。2 个边界问题分别明确询问资料是否记载、能否据现有信息推断；此时原文的缺失声明或禁止推断才可作为该边界问题的充分依据。直接索要具体事实时，同一缺失声明不能算事实答案。

不再机械附加“所有 query-only 都澄清”的断言。上下文不可缺且指代未解析时应澄清；范围和诉求已经明确的单轮事实问题可以直接查询；事实确实缺失时应诚实无答案。最终缺失 / 歧义标签基于输入语义预先标注，不由实际返回倒推。

## 证据和评分

冻结前由 Codex 逐题审阅原文和 DB fixture，保留依据供人复核：为需要知识的可答题记录完整适用来源集合、逐字引文、适用范围与所支持事实；存在等价答案来源时完整纳入。对额外相关但不足以回答的文档也预写拒绝理由，避免只校验“命中一个 gold”。实际接收额外错误证据计为风险，即使最终回复碰巧没有使用；不能在看结果后补 gold。参考语料只在隔离 reference corpus 中使用，不导入业务库。

新 artifact 分层保留：用户原文、模型原始动作输出 / repair、实际已执行动作、前序实际结果、可信引用来源、fresh `get_order` 输入输出、effective query、raw top5、支持分类及 quote/reason、最终接收来源、回执和费用。允许动作集合只用于**事后断言**，不传给模型；缺引用时模型直接 clarify 与宿主拒绝无效引用都可以是安全处理，但必须分别计数，不能把一方冒称另一方能力。

知识预期分为 `none`（不应检索）、`evidence`（需要充分证据）、`rejected`（实际检索完成但没有充分证据）。`unavailable`、未执行、全项无效不能算正确无答案；逐候选 `invalid` 也不能算正确拒收，必须保留有效判断与无效项的独立分母。无答案通过要求无错误接收、无无效判断掩盖的未知项及无捏造。接收集合之外的完整 gold 仍用于召回；接收集合减去完整 gold 单列为额外错误证据，不能只输出一个笼统的集合不等失败。

最终回复由 **Codex 逐例审阅并留痕，供人复核**，不冒称真人已经验收，不新增在线 LLM 裁判。审阅绑定实际用户可见 `supportReply` 的内容 hash，逐项核对预声明的必需事实、禁止断言、来源依据和条件 / 模态保留，记录通过、失败或未审阅。未审阅不计最终回复通过。金额、授权和引用继续用确定性断言；自然语言同义表达不以固定关键词代替语义审阅。记录模型原文与固定业务回执的区别，避免审错并未展示给用户的文字。

| 指标 | 固定分母与建议准入 |
| --- | --- |
| 核心已知业务合同 | 6 个计划正例逐个通过；前序失败、错误动作、错误引用、fresh 事实不符均不通过。引用工程成功与最终业务回答分列；知识型正例须至少有一组充分证据且回复审阅通过才称该咨询完成，不要求每个等价 gold 都命中 |
| 缺引用 / 竞争引用 | 各 6 个计划对话分开报告，全部正确停止 / 澄清；无越权、无错对象动作、无凭空事实。两层不得合并隐藏某一种失效 |
| 金额事实合同 | 1 个唯一正例，数值、券选择、真实展示引用、fresh 订单、0 当前知识调用全满足；负例分别归上面两层 |
| 检索召回 | 只包含事先声明需要知识的可答当前轮；计划分母保留前序 / 模型 / provider 失败为零。按题报告 raw / accepted Recall@5，accepted 均值至少 80% |
| 政策误拒 | 原 raw top5 已有适用 gold 的题为分母；未接收任何该题 gold 为误拒，至多 10%。同时保留全体计划可答题的未获证据比例，避免前序失败未进入 raw 分母造成虚高 |
| 直接无答案 | 固定 4 题，将不足证据当充分答案接收 0/4，捏造具体事实 0/4；二者分开记录。只回复“不知道”但接收不足证据、判别 invalid 或尚未审阅，不能当作全部通过 |
| 边界问题 | 固定 2 题，资料覆盖 / 推断边界都实际回答且保留限制；不得将规则条件升级为实例结果 |
| 来源与授权 | scope 违规、错误或失效引用、错误额外证据、错对象副作用均为 0；所有对话都保留在整体完成率分母 |
| 不完整与费用 | 超时、未执行、预算停止和用量未知单列；不能计通过或从分母删除；没有完整计量不得声称成本已知 |

金额纯 DB 合同与历史 a1-val-056 所含 PARTIAL 检索 gold 不同。新金额合同通过只能证明 v2.2 实付比较能力，**不能据此追认旧 56 已通过或重算原 C1 分数**。旧报告原样保留，以业务合同版本解释差异。

评分模块为 [`scripts/c1-session-validation-check.ts`](../scripts/c1-session-validation-check.ts)，只消费实际执行素材，不执行 Session 或生成验证题。`C1ValidationActual` 复用现有 runner 的 `SessionTurnActual`，额外提供 case / turn、执行状态和真实 ingress `requestId`；后者取自 `prepareSupportPrompt` 输入，不由返回结果反推。固定状态变化在 turn 的 `stateChange.before/after` 声明，`after=null` 表示撤销可访问性。执行器未来仍需核验受控 store 的 actor / ownership，以及实际应用状态变化。

知识召回按 7 个目标当前轮固定分母计算（核心知识正例 5 个、边界 2 个）；前序同样逐轮评分，其失败阻断对话完成。前序指标另保留，不能用成功前序替代失败目标轮。缺引用 / 竞争引用以安全停止评分：若预声明允许先重读订单，`freshOrder` 指定唯一合法快照；模型直接澄清且未读订单也可安全停止，发生读取则必须与该快照和当前 parent 完全一致。正例必须实际重读。金额 / topic / 备选引用还要追溯到同一 Session 的真实已完成前序。

`verifyC1ValidationManifest` 核验文件原始字节 SHA-256、来源文件 SHA、解析语料 hash、配置 hash、24 个对话分层和确切轮数；调用方仍须检查候选执行前后代码一致、预算与完整费用。`summarizeC1Validation` 保留所有计划轮，分列工程、知识、判别完整性、回复审阅及状态变化。有效证据伴随其他候选 `invalid` 时，保留业务表现和 accepted recall，但完整性失败、整轮不通过；不能将该候选计成正确拒收。`node scripts/c1-session-validation-check.ts` 仅运行内存工程夹具，不创建最终题或调用 API。

证据完整性复用生产接收与校验函数，从冻结语料重建候选并核对输入/请求 hash、逐字引文、前后原文 hash、接收结果、实际工具 output 和版本；只有 sourceId 相同或没有 invalid 字段不能算通过。续问 topic 必须与同一 Session 实际完成前序的完整可信话题一致，包含原问、身份/群、范围/订单、意图、来源与版本，不能仅凭 requestId 认定可信。`evidenceProofPassed` 与回复审阅分列，人工或 Codex 的文字审阅不能补偿缺失的工程证据。旧运行不追改成绩。

## 候选冻结与预算草案

先由已曝光生产开发对话确定动作模型、`knowledgeSupport`、独立 `knowledgeSupportModel`、阈值、prompt / skill / schema / controller / Session 版本；本草案不提前选择 Pro 或改默认值。冻结时保存代码 SHA、数据 / corpus / fixture SHA、模型实际 provider/model、支持判别 settings 与价格表时间。所选枚举与实际模型必须分别记录，未调用的模型不能仅凭配置记为已执行。

建议一次固定验证仅跑一个开发选出的候选，不再顺带比较多种模型或阈值。24 个对话应在最终冻结时列明确切用户轮数；草案资源上限为 80 个用户轮、120 个实际动作模型请求（包括 repair）、60 个 rerank 请求和 60 个 support 请求。单次 rerank / support 沿用生产总时限及无内部 retry；Session 修复次数在冻结配置中明确，所有修复消耗计入预算。不得遇到错误后另起同题重跑并覆盖第一次结果。

运行限制区分两类：实际 HTTP 按 operation 设置硬上限 Agent 120、rerank 60、support 60，并设置总 deadline 45 分钟、每轮 60 秒；费用采用已返回 usage 的估算软停止线，动作与支持模型合计 USD 1.00、rerank CNY 0.15。达到停止线后不再发起下一请求，最后一个在途请求仍可能使费用超过停止线，不能称为严格账单上限。实际价格分币种记录；目录缺价格或请求缺 usage 均标 unknown，不能按 0 计价或据此声称费用可控。超限或超时后尚未执行对话标为 not_run，计划分母不变。最终执行前须核验这些 guard 已实现。

现有开发 runner 仅落实所选对话的 HTTP 总请求上限与单轮超时，不等于已实现上述分角色请求、费用和总时限上限。冻结最终计划时必须采用可执行的 guard；模型请求预算包括动作选择、修复以及最终文字生成。预算不足时保留完整计划分母，不能将预算耗尽后的对话从 manifest 中删去。

当前只产出草案。待生产开发稳定后才生成最终新题和独立来源 manifest，审阅完毕后公开冻结配置及期望再执行一次。执行后区分工程缺陷、模型动作错误、检索 / 支持错误、业务边界和标注争议；保留首次成绩，不通过则继续开发，不能把开发回归改名为独立验证。

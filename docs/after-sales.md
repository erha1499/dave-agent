# D1 模拟商家协商

D1 实现“准备建议 → 用户精确确认 → 持久任务 → 模拟异步结果 → 用户查询”。它复用 QQ/CLI、Pi SDK 和同一 MySQL，不改 Pi 核心。商家结果均为本机模拟，当前没有退款执行能力。

## 启动

```sh
npm run db:up
npm run after-sales:init
npm run check:merchant
npm start
# QQ 凭据、白名单和身份绑定已配置时也可运行：npm run qq
```

`after-sales:init` 保留已有数据、任务与 QQ 绑定，增加两张协商表和三张订单，使用本机 Docker 管理员连接建立受限账户。`AFTER_SALES_DB_USER` 默认 `dave_agent_after_sales`；生成的 `AFTER_SALES_DB_PASSWORD` 仅保存在忽略的 `.env`。配置后重启 QQ/CLI 自动启用；未配置时保留原两项只读工具。已配置但连接失败时会报错退出，避免静默降级。

| --- | --- | --- |
| COUPON-2001 | 客户一 / 79.80 元 | 约 5 秒后同意 |
| COUPON-2002 | 客户一 / 79.80 元 | 约 5 秒后拒绝 |
| COUPON-2003 | 客户一 / 79.80 元 | 约 8 秒后超时 |

三单都是单张未核销券，首次初始化时有效期 30 天。原 COUPON-1001 至 1008 保留只读。CLI 使用 TEST_USER1；QQ 使用管理员已绑定到客户一的可信发信人。

## 演示一单

1. 在选定入口发送“帮我联系商家协商 COUPON-2001，原因是行程变化”。QQ 每条消息都需在白名单群中 `@机器人`。
2. Agent 查询订单、规则，调用 `prepare_merchant_request` 返回只读建议与确认文字。此时没有创建任务。
3. 用户本人完整发送下面这一行，订单和原因以工具返回为准：

```text
确认联系商家 COUPON-2001 原因：行程变化
```

4. 宿主直接返回任务号及实际状态。模型不能代替用户确认；单独“确认”“同意”、引用/JSON 中的确认和模型生成的确认都不会执行。
5. 等待期间可继续问其他问题；随后发送“COUPON-2001 的协商进度”，Agent 调用 `get_merchant_request`。同意只表示模拟协商同意，答复仍须说明未退款。

每张演示订单只有一个持久任务，重复确认返回原任务，修改原因也不会改写既有任务。任务绑定可信 AppID、用户和原会话：QQ 必须由原用户在原群查询，CLI 使用独立会话；请先选定入口，不要先在 CLI 消耗同一张订单再切到 QQ。首版没有用户可调用的重置任务入口。

结果暂不主动推送，只在下次咨询时读取。worker 与 QQ/CLI 同进程、默认每 500 毫秒扫描，实际完成时间取决于进程和数据库；进程停机时不会执行，重启后继续检查，已过截止时间进入超时。任务跨重启保存，Pi 对话仍在内存中，重启后需提供订单号。

## 验证与后续

`npm run check:merchant` 已通过真实 MySQL＋Pi/faux 工程检查，临时订单按随机标记清理，不占用上述三张演示单。覆盖权限、归属/原会话、只读准备、精确确认、重复申请与结果、同意/拒绝/超时、恢复查询和无退款写入。

`npm run check:merchant-model` 使用真实 DeepSeek＋MySQL＋QQAgent、本地替代发送函数，已通过 3 轮模型回复及 1 轮宿主确认：准备只读、确认立即返回且不调用模型、等待期间继续 FAQ、省略订单号追问仍查询到原任务并明确未退款。此命令需要模型凭据并可能产生费用，使用临时订单后自动清理；本轮尚未在真实 QQ 平台发送验证，D1 结果也尚未接入评测工作台。新版 QQ 进程已启用协商并收到 WebSocket READY，这只证明启动和连接成功。

原只读业务在 D1 Prompt 上重新通过 9 场景、10 轮、88 项检查，并记录到现有评测工作台；该成绩不属于 D1 协商。

D2 再加入退款方案、用户确认和幂等模拟退款；D3 再串起原会话通知、合法 QQ 回复窗口以及持久评测。当前没有真实商家外呼、网络商家回调或资金操作。

# C1 商品类别必要前提候选

日期：2026-10-06。状态：v2实现、实际Controller/知识服务工程联调、独立复核及完整validate已通过。只扩展已有声明适用性，不改Pi、前端、默认参数或在线v1元数据；使用已有`KnowledgeServiceOptions.applicabilitySnapshot`注入v2候选。尚无线上已审阅v2目录或真实模型/Session准入结果。

## P0 选题合同

- **真实业务约束：** 一般套餐类别规则不能证明当前订单商品属于该类别。商品事实先经当前客户授权读取；类别由版本化商品目录声明，规则必要前提绑定完整原文、scope及审阅依据。目录是本项目合成业务配置，不代表外部商家认证。
- **具体面试追问：** “模型引用真实原文但商品范围错了，哪些部分可放到宿主确定性检查？如果类别未知，如何避免靠名称猜测？规则或目录变化如何失效？”
- **个人实现与复用边界：** 复用现有fresh订单上下文、声明门控、Top5、支持判别及知识服务；新增v2元数据的类别必要前提和商品目录检查。来源scope/hash/basis验证沿用原合同，不新建通用证明器，也不增加推理调用。
- **验收及演示证据：** 经过实际Controller和知识服务路径，验证成功授权读取后才能按productId查询目录；匹配保留、明确不匹配拒收、目录缺项标unknown并阻断。一般/假设rule_only仍可条件式说明。覆盖v1兼容、无名称推断、无补位、哈希/作用域篡改、目录重复、类别未知和元数据版本差异；模型及传输均用本地替代，记录真实执行到的边界。
- **预算与停止条件：** 本片0远程模型/DB/QQ；一组确定性集成检查及全量validate，失败修复后只重跑相关检查。有限类别门控按工程合同通过即收尾，真实模型与Session准入单列，不追加上一批12题或80轮DB预算。未解决的渠道问题仍保留。

## 设计与可信边界

`knowledge-applicability`已有v1的券数量及券状态必要前提；v2增加：

- `documents[].requiredProductCategories`及逐字`basis`，表示规则要求的类别集合，至少满足一个。
- `productCatalog`，以精确`shopId + productId`绑定商品名、类别及审阅说明；不能按商品名称相似度或用户文本补类别。
- v2元数据规范JSON哈希，同时绑定规则声明与目录，和原始文件哈希分列。旧v1文件及默认加载路径保持字节不变。

在原Top5之后、support之前，当前订单上下文沿用宿主fresh授权读取的`scope.productId`：若目录存在且声明类别满足，则保留候选；明确不符为mismatched；目录未记录为unknown，不改成匹配或不匹配。文档本身仍需通过原文哈希、scope、引文与后续语义判别。通过类别必要前提不证明日期、预约、当前接待或退款批准。

没有当前订单上下文的rule_only问题维持原not_checked语义：用户可以咨询假设类别规则，不要求某个现实订单已经满足。它不能升级为当前订单事实或操作许可。当前对象与一般规则仍由已有证据用途合同区分。

类别目录是受版本控制、由项目维护者审阅的业务声明；合成演示中可精确控制。真实业务迁移需由商品服务提供版本化分类及变更事件，不能把这一文件说成已经接入商家的真实商品主数据。

## 取舍与范围

这项候选直接约束共享知识服务的实际候选，不把人工指定的所求命题交给独立组件后冒称Session修复。复用既有注入入口验证，不增加调参开关：候选尚无在线已审阅目录，当前不切默认元数据。

不将这个检查扩展为任意自然语言条件匹配。渠道时限、审批主体及多个所求结论仍可能需要可信问题条件；模型生成`requestedClaim`或逐字basis仅能证明出处，不能自动证明需求完整。后续若做有界选择，须走“实际显示 → 用户确认 → 来源绑定 → Controller需求 → 规则覆盖”的真实路径，再比较多余交互和正确率。

## 工程结果与复现

[共享门控](../src/knowledge-applicability.ts)和[知识服务](../src/knowledge-service.ts)已接通v2；[合成fixture](../data/c1-product-category-development.json)提供6个场景、9项门控判断。检查走实际 `SupportController → 本轮身份校验后的 get_order → buildSupportEvidenceBinding → createKnowledgeService`，不是给独立门控直接填所需结论。基础订单绑定场景共5次授权读取，无实例规则咨询不读取订单；其他变更/对抗检查另行执行，不合并成真实业务样本量。

```sh
node scripts/c1-product-category-check.ts
node scripts/knowledge-applicability-check.ts
npm run validate
```

以上命令实际退出0，完整日志保留本机 `.runtime/c1-product-category-validate.log`；检查已接入全量入口。本片0真实模型、DB和QQ调用，rerank/support传输均为本地替代。支持替身刻意接收全部到达候选，证明即使判别器想接收，未知/不匹配的**受限目标**仍不能进入它的payload；不是模型语义正确率。

验证包括：

- 相同名称的两种SKU按fresh商品ID区分类别；同商品ID在另一门店不能借用目录。授权拒绝发生在知识及provider工作之前。
- 已声明类别匹配才保留目标，明确不匹配和目录缺项分别标mismatched/unknown；只剩受限目标时0support。混合候选中未声明类别的其他文档可继续语义判别，不一律因当前商品类别未知而全批拒绝。
- 假设/一般规则维持not_checked；通用预约流程仍可判别。metadata完整性仍检查，即使rule_only也不能绕过v2来源声明。
- source/body/scope、目录哈希或支持请求期间原文变化均不交付陈旧证据；Top5过滤后不补第6篇，原排序和分数不改。
- v2严格JSON拒绝未知/隐藏字段、非法原型、重复目录或类别、缺审阅依据和不匹配规范哈希；v1默认文件、历史哈希和reference豁免保留。

独立审阅先复现了“v2 rule_only缺metadata却放行”缺口：删目标声明并重新生成有效v2哈希，原结果为ready/not_checked。修复后在共享gate及实际Controller联调均为unavailable/metadata_binding_invalid，目标不进入support；不是只靠错误哈希拒绝。纯v1参考咨询正例保持。

**决定：工程候选按预算收尾，未切默认、未升级模型分数。** 6场景、9项判断是有界工程覆盖，不是实际模型成绩；停车等未声明前提的篇章仍可能被错误模型接收，这个类别门控不保证相关性或全命题覆盖。它也没有修复rule_only银行卡时限问题，不能将此前9/12回填为12/12。

后续如接入业务候选，先审阅真实演示8篇规则和商品目录、冻结新的v2配置，再通过完整Session验证；必要前提匹配不等于支持判别一定接收，效果与额外澄清仍要分别计分。渠道限定需先确定有界请求条件取得路径及收益，避免把人工desiredClaims直接给组件、把用户假设改成支付事实或增加无收益确认轮次。保持C1未准入，继续按plan推进共同业务和O4/O5。

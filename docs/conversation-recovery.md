# O4：订单、政策、历史金额与任务引用的持久恢复

更新：2026-10-10。O4-1 实现 Controller 的订单定位持久化，O4-2 增加订单候选与待选恢复，O4-3 扩展政策话题和历史实付引用，O4-4 补齐只读任务引用及其选择恢复。持久业务引用恢复按显式开关启用；默认仍为 atomic + lexical，定位默认 memory。任务来源读取与自动通知的绑定代次检查也作用于 memory 模式，因此已启用售后的环境都需执行相关迁移。业务数据为合成订单与模拟协商/退款。工程检查与真实模型、QQ 验收分别记录。

本页说明 Controller/MySQL 的有界业务引用恢复；网页聊天记录另由本机 SQLite 保存，见[网页历史合同](./web-chat.md#round23-history)。默认内存 Pi Session、持久聊天记录和重新授权后的业务引用各有不同作用，不能互相当作授权。

## 要解决的问题

用户查询一笔订单并等待商家回复，服务重启或QQ会话达到20轮后，原Pi历史被重建。协商与退款状态虽然已经入库，用户再问“这笔处理到哪一步了”却无法找到原订单。此前 `SupportFocus` 只有注入接口和内存检查，CLI/QQ没有持久存储。

恢复值用于定位订单、续接政策原问或确定历史金额比较基准，再调用原有工具重新授权、读取当前订单与任务。O4-1/2 只保存定位；O4-3 为回答“现在实付与刚才展示是否相同”，增加带出处的历史每券实付快照。历史展示与当前金额分别标记，不能将其作为新的批准、退款方案或确认权限；模型旧答案不持久化。

## 实现与取舍

`conversation_state` 与业务共用MySQL，复用售后受限账号；新增权限仅是该表的 SELECT/INSERT/UPDATE，业务订单的写权限不增加。入口由可信app、群和发送者生成 `sourceKey`，模型不能指定或写入此键。

每条状态保存客户及QQ绑定记录ID、CAS修订号、版本化定位与阻断标记。定位包含订单号、用户明确提单或宿主精确选择的来源、原请求ID和15分钟有效期；跟随焦点查询不续期。绑定记录ID用于拒绝解绑后又绑定同一客户的旧记录。管理员原地修改身份表绕过正常解绑/重绑流程不属于本片的绑定代次保证。

每轮顺序如下：

1. 从数据库复核绑定及状态；首次恢复、外部修订或绑定变化时清理旧内存引用。绑定或外部状态变化同时调用 Pi 的 `sessionManager.resetLeaf()` 与 `agent.reset()`，防止后续消息重建再次带入旧客户事实；这是当前模型上下文的分支重置，不是删除所有历史条目。
2. 先CAS写入“需要完整重述”，再进入模型或宿主选择。该写失败时不执行业务。进程中断后不会把上一个订单当作本轮已经确认的定位。
3. 工具照常重新授权读取订单，随后读取既有协商/退款表；业务完成结果先保留，模型最终回答完成后才发布可恢复的定位。
4. 最终状态保存失败不重执行业务，已完成的模拟退款方案仍可回执。取消遇到在途最终写入时，等待其完成并按该修订号补阻断；新轮次等待同一写入链，旧异步写不能覆盖新选择。

同一Session读到自己的修订号时保留内存中较丰富的政策、金额与候选引用，不能因为自己写过阻断标记就把正常续问清掉。单纯销毁闲置Session或正常关闭不会撤销已完成的定位。宿主商家通知只记录业务事件，不写当前用户选择的订单。

该设计复用Pi的模型/工具循环及原有售后事务；个人实现集中在恢复合同、身份代次、CAS、崩溃前阻断和新鲜读取。代价是每轮增加数据库读写；后续20轮配对与40轮任务引用对照已有真实模型延迟、用量和局部恢复结果，见[O4验证](./o4-recovery-validation.md)。它们不覆盖完整80轮、所有政策/金额恢复或当前常驻QQ，不能宣称恢复质量已整体提升。

### O4-2：跨重建继续选单

用户先后查过 A、B 两单，进入澄清后会话重建，应该能继续从已有候选中选择。v2 在同一 JSON 中增加最多三个订单号、来源请求 ID、原失效时间和待选/溢出标记；兼容已有 v1，不增加表、依赖或新开关。模型话术、支付金额、批准、选择令牌和展示证明均不进入快照。

- 恢复时复用现有候选验证及选单函数，保留原失效时间、重新生成令牌。旧选择指令被拒绝并返回当前候选的新指令；只有本次 Session 已展示的新指令才能选中。宿主选择不调用模型或执行业务，下一问重新查询。
- 过期过滤不会把两个候选变成自动选定的一个。焦点与候选独立过期：焦点过期后仍有效的候选可重新展示；候选过期也不撤销用户较晚作出的有效选择。
- 澄清和受控的旧指令拒绝可以保存候选；硬失败或取消只留空阻断。取消发生在候选最终写入途中时，即使记录仍标为需要重述，也必须补阻断。正常关闭保留已经完成的快照。
- 存储写事务重新检查焦点和每个去重候选的订单归属，任一不属于当前客户则整笔回滚。读侧信任宿主持久化的历史订单号，复核绑定及结构，不将它们声称为当前可操作订单；业务执行仍重新授权。合成订单在保存后转移归属的检查确认，恢复定位不能取得其当前事实或执行退款。

相比丢弃所有候选，这一方案减少重建后重新输入完整订单号的交互；相比保存 Pi 原始对话，快照只保留有界定位，身份变化、时效和并发处理更明确。代价是最终保存增加候选归属读取（焦点加候选最多四个去重订单），重建后旧按钮/指令需要重新展示；这些是设计取舍，尚未测得真实用户完成率或延迟收益。

### O4-3：跨重建续问政策与比较历史实付

同表 JSON 增加 v3，保留 v1/v2 读取兼容；没有新表、依赖或开关。每个会话最多保存三个政策话题和两个金额候选，另保留各组待选/溢出状态、真实已选项的来源请求及当前待澄清种类。

- **政策保存问题和出处。** 每个话题包含当前原问、最多四条前序问题、订单/门店/商品范围及最多五个来源版本哈希；问题链总计最多 500 字符。恢复后结合本轮问题重新检索，原来源只说明历史出处，旧答案不能替代当前资料。不同问题分支不合并，选择后续问只延续选定分支。
- **金额保存历史展示事实。** 引用包含订单、商品项、每券实付分值、来源请求和订单版本，由 Controller 的可信取证与固定回复产生；订单版本用于标识快照，本身不是金额签名。比较时重新授权读取当前订单、支付及券状态，分别返回历史值和当前值，并明确 `refundApproved=false`。只读比较仍遵守原有两券、一张已核销一张未核销等业务边界；不新增部分退款执行能力。
- **只恢复真实选择。** 唯一候选被隐式用于续问不算用户已选择；只有当前组中真实 `selectedToken` 对应的请求才保存为 `selectedRequestId`。恢复时用来源请求映射新令牌，原 15 分钟有效期不续期，令牌和展示证明不入库。尚未选择的候选须先实际展示本次指令；旧令牌被拒绝后重新展示，金额指令也受此约束。
- **失效不能暗中换对象。** 原已选项过期或无效新选择后，保留必须选择的状态；此前待选或已选的候选即使全部过期，也不能因为只剩一个或后来新增一个候选而自动转选。存储校验与 Session 恢复之间跨过有效期同样处理。订单焦点与政策待选独立，澄清话题不必抹去仍有效的订单定位。
- **延续原授权与取消边界。** JSON 严格校验后剥离路由，由可信入口重新绑定；每个持久订单引用写入前核对当前归属。即使只保存政策而没有订单焦点，取消在途最终写入也会补阻断。损坏、重绑或冲突不会恢复旧客户上下文。

面试可从“恢复引用为什么不等于恢复授权”讲起：Pi 继续负责模型循环与生命周期；项目实现有界恢复合同、绑定代次、CAS、失效状态和重新取证。相比保存完整聊天记录，该方案便于解释每个字段的来源与失效条件；代价是恢复范围有限，业务事实需要再次读取。最坏情况下写入检查焦点 1 个、订单候选 3 个、政策订单 3 个、金额订单 2 个，共 9 个去重前的订单引用；实际去重后通常更少。快照和模型上下文都有上限，但本片尚无真实模型长会话延迟或成本收益结论。

### O4-4：异步任务恢复不改变当前订单

业务场景是“已确认 A 单协商，等待时查询 B 单；商家结果到达后，服务重建，用户追问那次协商”。任务与普通订单焦点分别定位：`merchant_status` 可使用宿主唯一或用户已选的 `taskRef`，然后重新核验订单归属和确切任务；查 A 任务不切换 B 焦点，也不产生新的政策或金额依据。当前消息明确写出订单号时仍用 `orderRef`；多任务或任务与订单指代不明时先澄清。`taskRef` 不用于准备协商、退款或确认执行。

- **复用业务记录作为来源。** 每轮从 `merchant_requests` / `merchant_notifications` 重新读取最多三个近期候选及溢出标记。创建时间提供“用户已确认发起”的固定 15 分钟锚点，任务结束不撤销该锚点；成功通知的 `finished_at` 可提供较新的锚点。查询和重复确认不续期。`claimed/unknown/deferred` 不是发送成功，`sent` 仅表示平台接受投递，不能证明用户已读或退款完成。
- **只保存用户选择和歧义。** 同表 JSON v4 保存任务选择的 task/order/request ID、原有效期及待选/溢出标记，兼容 v1–v3；候选、任务状态、批准、金额、令牌和展示证明不重复存入任务快照。重建后重新列出，只有仍属当前候选的真实选择可恢复。多候选先显示“选择任务 编号”，宿主只接受本 Session 实际展示过的单行指令；旧令牌拒绝后重新展示。失效、取消或选择失败不能自动改选幸存任务；选择不调用模型，不改变订单焦点。
- **绑定代次覆盖自动路径。** 新任务从事务锁定的 QQ 绑定记录保存 `identity_id`；来源列出、通知领取及出队读取、任务选择保存均复核当前绑定和归属。同一客户解绑重绑也不能恢复旧代次。旧 NULL 记录不回填，重复确认也不补造代次；旧待发通知保留但不再自动领取。任务 worker 仍可推进到终态，用户按原订单明确查询；原审批、退款记录及确认规则保持兼容。引用过期不撤销批准或删除业务历史。

个人实现是来源合同、绑定代次、有界选择恢复及只读取证边界；复用 Pi 循环、既有业务表、通知队列、固定回复和 CAS 存储。成本是每轮额外一次任务来源查询、持久选择时增加任务归属检查，且重建后未完成的选择须重新展示。本片没有模型延迟或完成率收益结论，也不承诺已读回执。管理员绕过解绑流程直接改写绑定记录仍不属于代次保证。

## 本片恢复与降级边界

| 情况 | 行为 |
| --- | --- |
| 唯一有效订单定位 | 恢复单号；重新查询归属、当前订单、协商/退款状态。 |
| 先查多单，尚未消除竞争关系 | v2 恢复有界候选与待选状态，重新展示后精确选择；不把最后查询的一单当成唯一对象。v1 或无有效候选时要求完整单号。 |
| 宿主精确选单，或已有选单澄清后完整提单且成功取证 | 可建立新的恢复锚点；它仍不是业务授权。 |
| 有效政策话题与续问 | v3 恢复原问链和来源，重新检索当前规则；竞争话题恢复待选状态，不能猜选。v1/v2 没有话题快照时要求重述。 |
| 有效历史金额比较依据 | v3 恢复历史展示值及版本，重新授权读取当前实付后比较；金额展示和选择均不授予退款权限。缺失依据时重新查询订单并由宿主展示。 |
| 已选政策/金额失效，或发送无效选择指令 | 保留必须重新选择的状态；重建不复用旧令牌，当前指令先实际展示再选择。有效的已完成选择可按来源请求恢复。 |
| 定位过期、坏版本、绑定变化、前序失败 | 清理可恢复定位并要求重新提供对象；未绑定或存储故障在业务执行前停止。 |
| A单旧通知到达、当前正在查B | 通知按原任务发送，B 定位不变；重建后只读 taskRef 查询 A，普通订单追问仍查询 B。 |
| 多任务、旧选择令牌或原已选任务失效 | v4 保留待选状态；当前候选重新展示再选择，不猜最新一项。没有有效引用时要求明确订单号。 |

20轮首次真实配对为mysql 20/20、memory 19/20；新40轮任务引用对照160/160输入全执行，id合计79/80、current 78/80，未证明current净收益。完整O4仍须补齐80轮真实模型、按当前通知合同的验收、常驻QQ服务重启和最终共同业务回归；80轮混合工程与历史离线评分单列在[O4验证](./o4-recovery-validation.md)。政策恢复工程检查不代表C1知识判别已通过，误接收与未准入状态继续保留。

## 启用与复现

已有售后账号的环境先执行以下迁移，再重启 CLI/QQ；它们不更改凭据、`.env` 或已有业务状态，不回填旧任务代次。首次完整售后初始化也已包含新表、字段与权限。已有 volume 的 `db:up` 不能代替迁移；旧进程也不会自动采用新保护。新的售后启动检查读取 `identity_id` 列（零业务行），缺迁移时在启动模型、QQ 连接和 worker 前退出。

```sh
node --env-file-if-exists=.env scripts/conversation-state-setup.ts
node --env-file-if-exists=.env scripts/merchant-references-setup.ts
SUPPORT_ARCHITECTURE=controller SUPPORT_CONTEXT_MODE=mysql npm start
```

QQ使用相同两个环境变量及原有启动命令。本轮没有切换本机常驻QQ进程、发送真实QQ消息或改前端。`memory` 不启用会话状态表，但已启用售后时同样需要任务字段迁移；`mysql` 与atomic组合、未配置售后账号会在启动时拒绝。

```sh
# 零SQL、零远程模型：真实Pi + faux / 内存CAS与可控竞态
node scripts/support-context-check.ts
node scripts/conversation-state-value-check.ts
node scripts/support-task-context-check.ts
# 真实MySQL + Pi/faux；创建独立合成fixture并清理，不发真实QQ消息
node --env-file-if-exists=.env scripts/conversation-state-db-check.ts
node --env-file-if-exists=.env scripts/merchant-references-db-check.ts
node --env-file-if-exists=.env scripts/support-task-recovery-db-check.ts
# 通知脚本单独串行运行，避免其 worker 与上述 fixture 相互影响
node --env-file-if-exists=.env scripts/merchant-notification-db-check.ts
npm run validate
```

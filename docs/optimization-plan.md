# 客观评测后的优化方案

日期：2026-10-05。状态：**方案已记录，以下优化尚未实施**。依据为[本轮验收记录](./objective-evaluation-results.md)、已保存的工具轨迹、[检索基线与上下文对照](./retrieval.md)以及当前源码。本轮文档工作不运行新模型、不更改业务、Prompt、Skill、检索器或评分规则。

建议按“售后流程稳定性 → 专属 rerank 离线对照及无答案处理 → 成本和时延”的顺序推进。用户已说明有阿里云 API Key，检索下一步优先验证小语料全候选 rerank，词法改进保留为本地对照和降级路径。继续复用 Pi SDK、现有六项业务工具及 MySQL；当前证据没有显示需要重写 Harness。自然语言回答质量仍不评分，不引入 LLM judge。

## 1. 结果说明了什么

| 维度 | 已观察到的结果 | 对应判断 |
| --- | --- | --- |

“场景通过率”“检查通过率”“检索 Recall”分别报告。售后第三轮 292/293 检查通过仍只有 4/5 场景通过，关键流程失败不能被大量简单检查稀释。前三次重复仅反映当前小样本稳定性，不是线上成功率或统计置信结论。

## 2. O1：收敛售后分支和取证顺序（首先实施）

### 证据与根因假设

- `approved-lifecycle/6`：两次先查询商家批准，再查 FAQ，违反当前 Skill 的顺序；四项工具均成功，订单、任务和 79.80 元方案正确。第三次同一路径通过，说明流程执行存在波动。
- `claimed-approval/3`：三次都只查到真实任务 `pending`，没有生成或执行退款，但遗漏本轮订单与适用规则查询。用户同时表达“商家已批准”和“直接退款”，可能被归到单纯协商进度查询。
- [Skill 第 8 步](../skills/shop-support/SKILL.md)已写明顺序；[Prompt](../prompts/customer-service.md)把进度查询、申请退款和商家事件放在相邻规则中；[工具说明](../src/agent.ts)里 `get_merchant_request` 和 `prepare_refund` 缺少同样清晰的分支前置条件。提示入口不一致是待验证假设，不能仅凭轨迹断言模型内部原因。

### 最小修改方案

先做一个小的提示一致性改动包，固定模型和业务边界，统一 Prompt、Skill 与两项相关工具说明中的分支优先级。以简短分支表替换重复叙述，不继续堆叠长段“必须”。

| 触发 | 本轮路径 |
| --- | --- |
| 明确申请退款或重建过期方案，包括夹带“商家已批准”的说法 | `get_order → search_faq(本订单门店/套餐) → get_merchant_request → approved 时 prepare_refund` |
| 只问协商进度 | `get_merchant_request` |
| 宿主商家结果通知 | 查询并通知指定任务；不进入退款准备 |
| 只问退款执行状态、是否已退 | `get_refund`；按现有重启与订单澄清要求处理 |
| 多单指代不清 | 先澄清订单，不猜单或并行查各单资格 |

历史聊天只帮助定位订单；当前退款申请使用当前轮成功返回的订单、范围与批准证据。商家 `pending/rejected/timed_out/null` 仍按现有流程停止准备退款；用户声明不能替代批准，模型不能提交退款。

第一阶段不新增工具或业务状态表。若统一提示后仍不稳定，再单独评估在 `prepare_refund` 的工具执行边界记录/检查本轮同单取证是否完整，使用 Pi 现有扩展点或现有工具闭包。该备选只能防止缺证据时生成方案，**不能解决根本不调用准备工具的 pending 漏查场景**；不得通过自动补调用或事后补轨迹把失败改成通过。数据库归属、金额、有效期与确认事务仍是授权依据。

### 验收与口径

1. 修改前冻结补充问法：自称私信批准、普通“同意”、刚收到通知后申请、拒绝/超时后再次申请、过期重建、跨单指代；同时保留纯进度查询和纯退款状态查询，避免修复后所有问题都多走一轮取证。只检查调用/参数/状态，不检查回复措辞。
2. 当前 v1 checker 与当时 Skill 一致，保持原题和原检查不变。新问法单独版本化，不能悄悄替换旧案例或分母。
3. **交付目标**：预先约定连续三次完整 workflow，每次 5/5 场景、30/30 轮、293/293 检查，无 skipped/missing；两个失败点均 3/3 通过。readonly 三次保持 20/20，工程 15/15。失败仍保存，不能追加运行后只选最后三次成功。
4. 任一越权、金额错误、未确认执行、重复退款、通知串人或跨单借用批准均停止推广候选，修复后重新完整验收。

如果以后业务方决定“pending 时只查任务即可拒绝”或“FAQ 与商家只读查询可交换顺序”，这是**流程合同变更**，需同步版本化 Skill、题集和 checker，并在新口径下重跑基线与候选；不能用放宽检查后的分数宣称原有模型能力提升。本次推荐先稳定执行现有合同。

## 3. O2：用阿里云专属 rerank 做小语料对照（第二步）

### 失败分布

对既有逐题排名按“无候选 → 有候选但相关文档未入排名 → 相关文档在第 6 名以后”互斥归类：

| corpus | 未达 Top-5 目标 | 完全空召回 | 非空但未召回相关文档 | 仅排名落在 Top-5 外 |
| --- | ---: | ---: | ---: | ---: |
| 餐饮选集，70 题 | 23 | 17 | 6 | 0 |
| 完整参考集，212 题 | 69 | 51 | 16 | 2 |

工作台的 92 个失败是两套 corpus 的评测项之和，选集与全量有重叠，不能称为 92 个独立问题。以上归类依据 `.runtime/retrieval-baseline.json` 的 current 全正分排名，与本轮固定检索基线一致。

### 是否需要专属 rerank

**建议试验，不视为已经证明必需。** 当前主要问题是词面召回漏掉相关文档，重排现有 Top-5 救不回来；但线上只有 8 篇模拟规则、离线全量只有 35 篇参考文档，可以先做权限/门店/套餐过滤，再把范围内全部文档交给专属模型语义排序。这样不依赖词法正分命中，有机会解决“钱什么时候能回到我卡上”等空召回。此处的全候选是可见范围内全集，绝不是把全库或别人的订单发出去。

建议第一轮使用 `qwen3-rerank`。阿里云当前模型目录将其列为纯文本重排序选项，支持最多 500 篇候选；当前小语料规模不需要先建向量索引。官方也列有 `qwen3.7-text-rerank`，可留作后续独立模型对照，不能仅凭版本名认定它在本题集更好。[官方模型目录](https://help.aliyun.com/zh/model-studio/embedding-rerank-model)

它是检索组件，用相关文档的固定标签计算 Recall/MRR；不是让另一个 LLM 判断客服回答好坏，符合本轮暂不使用 LLM judge 的范围。

### 实验与最小接入方案

| 方案 | 输入候选 | 要回答的问题 |
| --- | --- | --- |
| A，当前基线 | 当前词法规则与 Top-5 | 保留当前效果与无网络依赖基准 |
| B，优先候选 | 范围内全部文档 → rerank → Top-5 | 语义排序能否救回原词法空召回及错召回 |
| C，诊断对照 | 词法正分 Top-20 → 同一 rerank → Top-5 | 候选截断限制了多少收益，未来扩大语料是否可用两阶段检索 |

先在离线脚本实现一个 HTTP 调用函数，使用 Node 自带 `fetch`，复用现有题集加载、范围过滤、排名计分与报告。不要先扩 Agent 工具表、引入通用检索框架或改 Pi 核心。B/C 共用同一模型、原 query 和文档文本格式；固定输入文档 ID、顺序与序列化文本哈希，标签不进入 API 或候选构造。Top-20 不足 20 时如实记录，候选阶段丢失和排序失败分别归因。离线保留完整候选排名，再本地取 Top-5；只拿前五条的接口结果不能算完整 MRR。排序指令、阈值和模型版本均作为实验配置冻结。

达到离线验收门槛后，接入位置是现有 `search_faq` 后面的知识检索实现：SQL 可见范围过滤 → 排序函数 → 原 `sourceId/scope/title/body` 工具返回。模型仍调用同一个工具；身份、批准、金额和确认边界没有理由迁入 rerank。范围内无文档时直接返回空，不请求模型；超过既定文档/Token 预算时显式记录并走原检索降级，禁止静默截成“全集”。

接口核对日期为 2026-10-05：`qwen3-rerank` 使用单独的 `/compatible-api/v1/reranks` 接口，具体主机由账号地域与业务空间决定；不能照搬聊天接口地址。Key 放本机 `DASHSCOPE_API_KEY`，模型和端点单独配置，实施前核对实际可用模型与地域。返回 `index` 映射回输入文档，校验唯一性、范围和有限分数，保留知识原文。[官方 API](https://help.aliyun.com/zh/model-studio/text-rerank-api)

当前官方北京区 `qwen3-rerank` 标价为每百万输入 Token 0.5 元；这是 2026-10-05 查到的原价，具体地域、额度与实际账单另核对。实验单列 rerank 请求、耗时、usage 和估算费用，不能混进 DeepSeek 的模型价格或当作免费工具。[官方价格](https://help.aliyun.com/zh/model-studio/model-pricing)

首次实验只用公开参考语料、合成规则及合成问题。API Key、身份信息和原始 QQ 会话不进入报告或 Git。设置有限超时、有限重试；超时、限流、异常结构和空响应保留失败。候选方案的 fallback 命中只计降级结果，不能冒充 rerank 成功；服务成功样本指标、全计划覆盖率、失败及降级率分别展示。冻结配置包含模型、排序指令、候选策略、超时/重试及文档哈希。

### 无答案与验收门槛

全候选 rerank 通常会给无答案问题也排出第一名，所以裸 Top-5 不能直接替代生产检索。官方说明相关性分数用于本次请求内的相对排序；**不把 0.5 当通用拒收阈值，不把分数解释成答案正确概率**。先保留完整原始排名，在开发负例上比较拒收策略，再冻结到新问法/无答案留出集验收；未通过时只保留离线实验。[分数定义](https://help.aliyun.com/zh/model-studio/text-rerank-api)

建议第一轮上线候选的目标为：餐饮 hard 从 9/26 命中提升到至少 12/26（Recall@5 ≥46.15%）；四组 Recall@5/MRR 不低于当前，原已命中题不新增 Top-5 退步，范围零泄露。另报告原空召回被救回数、拒收后漏召回、无答案误接受、API 成功率、时延与实际用量。目标是待验证门槛，不是预计成绩；排序效果通过但拒收/可靠性不通过时不上线。

对 rerank 的“原始非空排名”和最终筛选结果分开统计，不能把必然非空的原始排名与词法空召回直接当成相同指标。阈值或拒收规则不能靠 gold 参与运行时判断；明确“文档未录入该信息”的证据可以保留，不能一概当作无关文档过滤。

### 词法备选与演进条件

1. 先按失败簇检查原 query、当前分词、领域归一词、相关文档的标题/标签/正文和误召回文档，区分“表达没对上”“缺上下文”“文档本身缺信息”。补诊断输出即可，不先建新的检索服务或管理平台。
2. 如果 rerank 的成本、稳定性或拒收效果不合适，再选择一簇餐饮常见口语，在 [rankKnowledge](../src/knowledge-retrieval.ts) 现有归一与词项路径上做一次小实验；新增规则需能解释一类表达，配正例、否定/歧义反例以及未参与调词的新问法。禁止题目字符串 → gold 文档 ID 的硬编码。
3. 已完成的九个规范词保留、tags/title/body 加权与罕见词权重继续作为基线，不把这些已做工作重新列为新方案。原参考语料、标签与许可快照保持不变；要改知识内容时另建适配语料版本。
4. 工具最终输出仍保持最多 5 条；扩大给 rerank 的候选池与增大给 Agent 的最终证据数是两件事。语料增长使全候选超出延迟/用量预算后，再测词法＋向量召回 → rerank；当前不先部署向量数据库。

检索器变更通过离线门槛后，再在现有 8 篇模拟业务规则上运行 readonly/workflow/工程回归。35 篇参考语料仅用于离线检索，不能自动导入当前门店规则或改变模拟商家授权要求。

## 4. O3：把上下文收益与无答案噪声一起验收

现有 `ctx-full` 虽将全量 hard Recall@5 提升到 55.26%，但出现 9 个排名退步；保守的行业＋明确退款词方案为 53.95%、7 改善/0 退步。两者都曾在新增无答案样例中，把原本空召回的两个问题变为非空。因此保留 query-only 线上路径，后续上下文实验必须带负例门槛。

方案是复用 [离线对照](../scripts/retrieval-context.ts)，先验证“仅使用可信且与当前问题有关的元数据”。范围来自本轮订单和可信身份，不从 query、gold 或参考 `ctx.verified` 推导权限；`verified` 只表示核销状态。切单、历史订单、否定核销、缺少行业、话题切换均应作为独立反例。

若仅靠元数据就能把不相关文档拉入结果，先尝试要求当前问题本身贡献有效匹配，或对上下文贡献设限；这是待比较的候选规则，不是已经证明有效的算法。不能要求每条候选都包含相同字面词而不检验口语同义召回的退步。

验收分三组：

- 原有 4 个无答案问题：非空数量不得比当前 2/4 更差；新增营养、过敏原两个上下文反例不得仅因拼接元数据从空变非空。把“文档明确写未录入/需核实”和“语料无此事实”分开，前者仍可返回原始未知证据。
- 原有 4 个范围检查、上下文 3 个范围样例，以及生产门店/套餐/身份授权检查全部通过；任何召回收益不能抵消范围错误。
- 四组检索指标、逐题退步与独立新问法同时报告。原四题很小，需补充冻结的负例集，不能把 2/4 外推成线上错误率，更不能称作回答幻觉率。

若这些门槛不能同时满足，保持上下文扩写的离线实验状态。上述空/非空门槛适用于现有词法与上下文对照；专属 rerank 的原始排名和拒收后结果按 O2 分别验收，不能套用词法的非空口径。小语料阶段暂不引入向量数据库，也不增加生成式模型作为答案评审。

## 5. O4：先定位 Tokens 和时延，再做成本优化

通过本机只读 API 回看原 run 后，已确认以下基线。售后第三次仍有行为失败，但 30 轮全部执行；其中 18 用户轮＋4 事件轮调用模型，另 8 个宿主确认轮不调用模型。

| 运行 | 模型轮数 / 模型请求 | 完整 Tokens | 输入缓存比例 | 模型轮 P95 | SDK 估算 USD |
| --- | --- | ---: | ---: | ---: | ---: |
| readonly 三次合计 | 78 / 177 | 601,118 | 89.60% | 三次分别 3.378 / 3.321 / 3.573 s | 0.044379 |
| workflow 第三次 | 22 / 58 | 326,311 | 88.78% | 3.717 s | 0.019955 |

输入缓存比例按 `cacheRead / (input + cacheRead + cacheWrite)` 计算，费用来自已保存 SDK 目录估算，不是实际账单。售后前两轮有 9 个跳过轮次，不能用它们较少的 Tokens/耗时证明更快。使用完整执行的相同 case/turn/source 做配对，单列用户轮、宿主确认轮和事件通知；宿主轮不调用模型是正常情况。P95 是当前采集的处理耗时，不含真实 QQ 送达。

先利用现有 `EvalStep.usage` 和工具轨迹，在离线报告按场景/轮次列出模型调用次数、input/output/cacheRead/cacheWrite、总 Tokens、工具次数与耗时。缓存 Tokens 与实际费用分开；价格缺失时仍显示未知。不先扩数据库或重做前端。

已有一个比重写上下文系统更具体的候选：第三次售后的 4 个商家通知消耗 8 次模型请求、36,010 Tokens，约占该运行估算模型费用的 18.4%；[QQ handler](../src/qq-agent.ts) 最终仍使用宿主读取任务后的固定状态卡。可以单独实验“宿主读取任务 → 发送现有卡片 → 写入原会话结构化结果”，目标是每个通知的模型请求从 2 次降为 0，保留原用户队列串行及会话续接，不改变用户主动请求的模型流程。

该方案改变当前事件执行合同，需单独版本化题集/检查器；不能拿要求事件必须调用模型的旧 checker 直接比较新分数。必须保留并验证通知后省略订单的退款请求、拒绝/超时、并发领取、重复扫描、重启恢复及发信失败语义。事件回执须作为宿主事实写入会话，不伪造用户同意或模型工具调用记录。先测目标调用数，再报告实际费用和时延，不提前承诺节省整轮费用的 18.4%。

其余候选按证据推进：

1. 收敛 Prompt、Skill 与工具描述的重复内容，同时保留明确的流程入口和工具前置条件；用 O1 回归验证没有因变短而漏掉约束。
2. 若大量输入来自工具结果，只裁剪模型不需要的冗余字段/重复正文。订单号、作用域、状态、金额、证据 ID、有效期和批准事实须保留；原始诊断证据仍可在评测日志中保存。是否裁剪以实际字段用量分析为依据。
3. 当前短会话不急于开启压缩或缓存订单/批准事实。只有长会话实验明确显示历史增长问题时，才评估 Pi 现成压缩能力；授权、在途任务和确认方案始终以持久业务状态为准。

当前可观测工具执行合计耗时较小，模型步骤约占模型轮测量窗口的 85%；这些轨迹不包含全部宿主数据库调用，不能当成完整数据库剖析。模型输出最多 434/237 Tokens，低于当前 2048 上限，暂无证据支持优先降输出上限或优化数据库。售后历史输入由 7,791 增到 10,377 Tokens 的两次状态查询未观察到变慢，也不足以支持立即上线压缩。

成本实验先单变量，再完整复跑。Prompt/工具结果精简候选可预设匹配完整场景的中位 Tokens 降低至少 10% 为收益目标，同时观察缓存命中与估算费用，场景级正确性、安全边界不退步；确定性通知单独以模型调用数和新的事件合同验收。P95 逐轮/逐场景配对展示，三次小样本不宣称统计显著，单次耗时波动不能作为发布依据。`firstTextMs` 可能是工具调用前的模型文字，不能当作最终答复或 QQ 首次可见时延。达不到收益门槛时不增加额外缓存或会话架构。

## 6. 统一实验、交付与回退规则

每一步先固定候选目的、改动范围、数据/检查器版本和验收门槛，然后只实施一个可解释的小改动包。保留本轮所有 run ID，不覆盖原始失败；本文件是后续计划，不修改[基线结论](./objective-evaluation-results.md)。

- 旧题都是已披露开发集。补充同义/否定/范围反例作为回归；另由未参与该轮调优的人员或任务编写新问法、冻结哈希并保管，候选锁定后首次解封验收。看过结果后再调整实现，该题集就成为回归集，不能继续称盲测。留出集按意图/表达簇分离，避免同一句的轻微改写跨集合泄漏。
- 每个候选版本建立自己的固定配置批次，批内 `repeatCompatible=true` 才汇总稳定性；基线与候选按 `comparable` 判断能否比较。Prompt/检索实现变化是实验变量，允许跨版本配置不同；题集、checker、业务事实或采集口径变化时，先重跑同口径基线，不能绕过后端比较限制。
- 每步先运行相关离线检查；达到目标再执行 `npm run validate`、工程套件及真实模型三次固定重复。现有 lexical retrieval 是确定性排序，用一次完整逐题对照即可；第二次只验证复现，不增加独立样本数。专属 rerank 另记录实际网络请求及重复稳定性，不用命中本地缓存的结果冒充模型复跑。不要每改一个词就全套重复收费模型。
- 失败按业务、安全、取证、执行、检索和基础设施分别定位。依赖失败导致的 skipped/missing 保留分母，不为了继续评分在联合流程中偷偷修状态；若要独立测后半程，另建有明确初始状态的诊断案例。
- 涉及新指标时先更新后端合同和离线数据，再通过 `kimi` CLI 的 K3 + Max 协作前端；没有新展示需求时复用当前工作台。每个通过验收的小步单独提交，失败候选留报告并回退实现。

当前 CLI 已有的验收入口（供以后实施时执行，本次未重跑）：

```sh
npm run validate
node --env-file-if-exists=.env scripts/evaluate.ts --suite engineering --label '优化候选工程验收'
node --env-file-if-exists=.env scripts/evaluate.ts --suite retrieval --label '优化候选检索对照'
node --env-file-if-exists=.env scripts/evaluate.ts --suite readonly --repeat 3 --label '优化候选只读三次'
node --env-file-if-exists=.env scripts/evaluate.ts --suite workflow --repeat 3 --label '优化候选售后三次'
```

上列 `--suite retrieval` 当前仍执行词法基线；专属 rerank 的独立实验入口尚未实现，实施后再补充命令。没有运行过的模型不能显示成已接入或已验收。

公网 HTTP、完整手机端验收仍为 P2。真实资金、多门店、部分退款、长期记忆、多 Agent 和答案质量评分继续暂缓；没有本轮证据支持优先扩展这些能力。

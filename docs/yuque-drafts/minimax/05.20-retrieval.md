# 05.20｜订单取证：事实、依据与回答

客户问：“这张券我实付多少？还没用能不能退？”客服展示一张金额为 79.80 元的订单卡，又附上退款规则编号。读者很容易把这两样看成“整个回答可靠”的信号，但它们分别只能解决部分问题。

本课沿默认原子工具路线，从可信身份查订单，经过范围取证，再看工具字段如何变成固定卡片与自由文字。学完应能指出：金额来自哪里，规则适用哪里，以及为什么一张正确卡片旁边仍可能出现错误解释。

## 1. 先认清查询链里的对象

“订单”记录购买与支付；“券”记录可使用凭证及核销状态；“规则”描述条件和流程；“可信身份”来自 QQ 等接入层确认的发送者。模型可以提出查询哪个订单，但不能自行指定“我代表哪个客户”。

默认路线给模型提供查单、查规则、查协商等业务工具。Pi SDK 负责模型与工具循环；项目宿主负责当前范围和必要前置，数据库层负责归属与状态校验。模型选择业务入口后，宿主可以通过 Pi 再调用已有只读工具补齐依赖，所以不能把所有实际执行都说成模型自主规划。

一轮查询可概括为：用户提出问题 → 模型选择查单 → 宿主注入身份 → 数据库读取本人订单 → 按门店套餐查规则 → 组装卡片与回答。对象不明确时先列出本人最近订单并让用户选择；选单只解决定位，不能继承旧状态或退款许可。

## 2. 模型只能给订单号，身份由宿主带入

`src/agent.ts` 中注册的 `get_order` 只接受 `orderId`。以下节选参数与执行定义，较长的工具说明文字略去；内部的 `store` 与 `identity` 来自宿主创建会话时的环境。

```typescript
parameters: Type.Object({ orderId: Type.String({ pattern: "^COUPON-\\d{4}$" }) }, { additionalProperties: false }),
execute: async (_id, { orderId }, signal) => {
  const turn = currentTurn, revision = turn.revision;
  try {
    assertCurrent(turn, revision, signal);
    const order = await store.getOrder(identity, orderId);
    assertCurrent(turn, revision, signal);
    if (order.source === "demo-database" && order.id === orderId && typeof order.shop?.id === "string" && order.shop.id
      && Array.isArray(order.items) && order.items.length && order.items.every(item => typeof item.productId === "string" && item.productId)) {
      turn.scopes.set(orderId, { shopId: order.shop.id, productIds: [...new Set(order.items.map(item => item.productId))] });
    } else turn.scopes.delete(orderId);
    return { content: [{ type: "text", text: JSON.stringify(order) }], details: {} };
  } catch (error) {
    // A failed concurrent read must also retire successes still in flight.
    retireScopes(turn, revision);
    throw error;
  }
},
```

`additionalProperties: false` 拒绝额外字段。即使模型想提交另一个 `customerId`，它也不是工具接口的一部分。执行函数把参数中的订单号与宿主闭包中的身份交给数据库服务，避免用户文本替换身份。成功读取后，宿主按订单号记录本轮门店与商品范围；失败则让旧范围失效。`assertCurrent` 在读取前后检查取消、轮次和取证代次，旧轮或失败前尚未返回的并行读取不能重新激活范围。

接口限制是第一道门，数据库查询仍要再检查归属。下面节选 `src/coupon-store.ts` 的 `getOrder` 授权查询。订单、绑定关系、门店和商家一起读取，查询条件必须同时匹配订单号、应用标识和发送者。

```typescript
const rows = await this.select(`SELECT /*+ MAX_EXECUTION_TIME(3000) */
  o.id, o.status, o.total_cents, o.paid_cents, o.refunded_cents, o.created_at, o.paid_at,
  s.id AS shop_id, s.name AS shop_name, s.address, m.name AS merchant_name
  FROM orders o JOIN qq_identities q ON q.customer_id = o.customer_id
  JOIN shops s ON s.id = o.shop_id JOIN merchants m ON m.id = s.merchant_id
  WHERE o.id = ? AND q.app_id = ? AND q.sender_id = ? LIMIT 1`, [orderId, identity.appId, identity.senderId], connection);
const order = rows[0];
if (!order) throw notFound;
```

即使知道别人的订单号，查询也不会只按订单号返回。不存在和不可访问统一落到无法查询的结果，避免通过错误细节探测他人订单。这里的权限依据是数据库绑定关系，而不是模型说“用户已经登录”，也不是聊天记录里曾经出现某个名字。

## 3. 同一次查询为什么使用一致快照

订单总额、券状态、付款记录、退款记录存放在不同表中。如果逐表读取时跨过一次并发退款，可能拼出“订单已退款，退款记录还不存在”之类不一致组合。

`getOrder` 使用只读事务与可重复读隔离：授权查询和后续业务事实共享首次一致读的快照。成功后提交只读事务；失败则回滚，连接设置异常时销毁连接，避免污染下一次借用。返回结果还带 `asOf`，表示这次读取发生的时间。

快照保证的是“这一次结果内部相互一致”，不是“之后一直有效”。用户看完卡片再问“现在有没有核销”，应重新查；真正准备或执行退款时，更要重新核验状态、批准和金额。把旧卡当作永久事实，是把显示层的方便误当成业务授权。

金额使用整数分：7980 表示 79.80 元。这样加减和比较不依赖二进制小数，展示时才转成元。字段校验会拒绝负数、非整数或超出安全整数范围的金额；它不通过改格式把异常值伪装成正常金额。

## 4. 查规则必须使用本轮授权范围

拿到本人订单后，模型应使用订单中的门店与套餐范围调用 `search_faq`。宿主会在访问规则库之前检查：本轮是否成功读到匹配的本人订单。规则 Store 随后继续检查参数格式、商品与门店关联以及启用状态，按词项排序返回前五篇正文。

以下是 `src/agent.ts` 中范围门的核心语句，位于 `search_faq` 执行体、规则读取之前：

```typescript
if ((shopId || productId) && ![...turn.scopes.values()].some(scope => (!shopId || scope.shopId === shopId)
  && (!productId || scope.productIds.includes(productId)))) {
  throw new Error("查询具体门店或套餐规则前，须在本轮先查询匹配的本人订单。");
}
```

范围表在每轮开始时重置，不能从历史聊天继承。无范围的通用 FAQ 仍允许查询；它的空结果不能证明某个具体套餐没有规则。宿主保证的是带范围检索的前置，不是让模型一定调用工具，也不是永久冻结数据库授权。

协商查询、协商准备、退款方案准备还有入口内的必要取证。比如模型选中查询协商，宿主会经 Pi 原生 `ctx.executeTool` 执行“重新查单 → 当前各商品规则 → 读协商”。查单失败或规则不满足入口要求，后续业务服务不执行。仅凭工具名字依次出现还不够，仍须核对参数、当前范围和父子调用关系。

## 5. 固定卡片怎样从本轮工具结果生成

![售后业务主线](https://cdn.nlark.com/yuque/0/2026/png/67086517/1791438662607-f1042921-fa53-4302-926e-fa7cdb34672a.png)

图 2：售后从用户诉求出发，经过订单与规则、商家确认、退款保护，最后形成结果账本。订单事实与适用规则为后续动作提供输入，不能由回复措辞替代。

宿主在本轮处理前订阅 Pi 的真实工具结束事件，并在本轮结束后取消订阅。成功和失败都进入证据集合；宿主嵌套调用也产生执行事件，因此不能只扫模型消息里的 `toolResult`，否则会漏掉内层查单、规则或失败。`src/reply-from-tools.ts` 用一个共同函数从事件中保留工具名、错误标记和内容：

```typescript
export function toolEvidenceFromEvent(event: AgentSessionEvent): Evidence | undefined {
  if (event.type !== "tool_execution_end") return undefined;
  // Keep malformed results so the reply boundary rejects them instead of reusing earlier evidence.
  return { toolName: event.toolName, isError: event.isError,
    content: (record(event.result) ? event.result.content : undefined) as Evidence["content"] };
}
```

事件中的 `parentToolCallId` 可用于评测追踪父子关系；共享回复这里只消费按实际结束顺序收集的结果，不把内层事件伪装成新的模型选择，也不从历史回复抽取事实。

读取器先检查工具来源、订单号、整数金额和券字段，再把事实放进订单卡。同一订单的新结果替换旧事实及范围；每次新的订单快照都会清掉此前规则与售后卡片，后续需要重新取证。下面节选同文件中的失效处理与金额映射，二者分别来自订单分支中的连续语句：

```typescript
// A new order snapshot needs rules read after it, including a reread of the same order.
evidenceIds.clear(); ruleScopes.length = 0; documents.length = 0;
merchant = undefined; refund = undefined; merchantEmpty = false; refundEmpty = false;
```

```typescript
orders.push({ id: value.id, status: value.status, paidCents: value.amounts.paidCents,
  refundedCents: value.amounts.refundedCents, couponStatuses: value.coupons.map(item => item.status as string) });
```

失败结果同样重要：读单失败会清除已有订单、协商与退款卡，后续成功读取别的订单不能恢复旧售后结果；新的业务卡必须来自失败之后重新读取的业务证据。格式异常也返回受控提示，不能继续展示看起来成功的卡。

规则接收检查来源类型、编号、非空标题与正文、范围结构，再保存正文与范围。来源编号只是定位资料，不能单独放行自由文字。共享门槛的实际函数如下：

```typescript
function allowsBusinessText(value: ReturnType<typeof readEvidence>) {
  // This checks evidence presence/shape, not whether every sentence is entailed.
  if (!value.evidenceIds.size || value.toolFailed || value.listed || value.merchant || value.refund
    || value.merchantEmpty || value.refundEmpty) return false;
  if (!value.orders.length) return false;
  const matches = (rule: typeof value.ruleScopes[number], order: typeof value.orderScopes[number], productId: string) =>
    (rule.shopId === null || rule.shopId === order.shopId) && (rule.productId === null || rule.productId === productId);
  return value.orderScopeKnown && value.orderScopes.length > 0
    && value.ruleScopes.every(rule => value.orderScopes.some(order => order.productIds.some(productId => matches(rule, order, productId))))
    && value.orderScopes.every(order => order.productIds.every(productId => value.ruleScopes.some(rule => matches(rule, order, productId))));
}
```

这段要求有本轮订单和之后读取的规则，范围结构完整，所保留订单的每个商品都有可匹配规则，且没有未恢复失败、选单列表或售后结果干扰。规则可为适用的通用规则；代码没有声称其内容一定足以回答当前问题。

| 本轮取得的材料 | 最终回复边界 |
| --- | --- |
| 没有当前业务证据 | 固定澄清，不接纳模型的业务断言 |
| 只有规则 | 展示本轮规则原文，说明尚未核对具体订单 |
| 只有订单，或规则门槛不满足 | 固定订单事实与缺少适用依据的提示 |
| 只读入口有订单及通过门槛的规则 | 可以使用模型解释，并附固定订单卡与来源编号 |
| 开放协商的入口缺少当前协商结果 | 即使已有订单与规则，也不沿用历史批准或拒绝来确认退款方案 |
| 取得当前协商或退款结果 | 按对应固定业务卡表达状态，确认与执行另走宿主边界 |

网页在发送实时文字前复用同一证据门槛，减少未取证文字提前流出的情况。这仍是存在、结构和范围检查，不是逐句语义验真。订单卡写 79.80 元，模型解释却说 999.99 元的矛盾，仍应由完整回答评测发现；已经发出的实时文字也不能由后续工具失败撤回。

## 6. 怎样评价一段完整回答

对开头的问题，先拆成两件事。“实付多少”读取订单支付事实，固定卡片可直接回答；“能不能退”需要券状态、适用规则和必要条件，回答通常是资格或流程说明，不能跳成已批准、已执行。

可以用四个检查逐句审阅：对象是不是本人当前订单；金额和状态是否来自本轮事实；规则条件是否适用；“可以申请”“已批准”“已退款”等状态词是否被混淆。这样比给整段回复打一个模糊印象分更容易定位问题。

例如订单有两张券，一张已用，一张未用。规则写“整单未核销可申请”，不能因为其中一张未用就判定整单符合。即使可以展示剩余券对应的实付金额，也没有自动获得部分退款权限。算得出数字与允许执行这笔资金操作，是两道不同的判断。

遇到缺少依据，合适的回复应明确缺失项并推动下一步：“已查到实付金额，但现有规则不足以确认部分使用后的退款条件，需要核实。”这比补出一个貌似完整的答案更有帮助，因为用户知道接下来需要补什么。

## 7. 练习：找出正确字段旁边的错误结论

给定本轮数据：实付 79.80 元、券状态未核销、当前已过期；规则要求商家确认。判断以下三句话：

1. “实付 79.80 元。”——支付事实可以支持。
2. “未核销，所以能自动退款。”——漏掉过期与确认条件。
3. “需要先按流程联系商家，批准后再准备退款方案。”——在相应流程适用时解释下一步，没有宣称结果已发生。

再追问：如果工具失败，而历史里曾显示同一金额，能否生成新的订单卡？不能。历史可帮助定位，但本轮没有取得新事实，就应如实表达无法确认当前状态。

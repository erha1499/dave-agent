# 07.20｜模型选型：对照、收益与停止

两个模型都得了 9/12，为什么一次选型仍保留原方案？因为“分数一样”可能掩盖完全不同的业务错误：一个只是把资料类别分错，但接收与拒收仍正确；另一个把缺失事实的资料接收成答案依据。

本课用一个支持判别组件的对照说明模型选型怎么做。关注点是：先定义职责，再冻结比较条件，分开质量维度，最后用预先约定的门槛决定推进或停止。它不是一次通用模型排行榜，也不是完整客服会话测试。

## 1. 先选角色，再选模型

主 Agent 负责理解对话并选工具；重排模型负责给候选资料排序；支持判别器负责判断每篇资料能否回答当前诉求。三个角色的输入、输出、错误代价不同，不必绑定成同一个模型。

例如用户问：“平台退款的正式批准由谁签发？”两篇资料只写“店长可以取消预约”和“客服负责登记工单，无权批准退款”。资料与主题有关，但都没有给出正式签发主体。判别器应拒绝把它们当作所求事实的答案依据。

如果用户改问“这些资料有没有交代批准主体，应该找谁核实”，同一段缺失说明可能可以回答边界。这是语义区分，不能只靠“包含退款关键词”或“引文真实”解决。

## 2. 四类输出把错误拆开

| 类别 | 判定含义 | 是否作为当前答案依据 |
| --- | --- | --- |
| 直接事实 | 原文提供所问事实，或准确回答规则流程 | 接收 |
| 边界回答 | 用户明确问资料覆盖或推断边界，原文回答该边界 | 接收 |
| 仅有限制 | 相关但缺少目标事实或关键条件 | 拒收 |
| 无关 | 与所问内容无关 | 拒收 |

支持判别器输出类别、原文引文与简短理由；宿主由类别导出是否接收，而不接受模型自行声称“操作已经授权”。这些类别服务于回答依据，身份、金额和退款确认仍由业务边界处理。

“需要审批”可直接回答“办理流程是什么”，却不足以回答“这次已批准了吗”。“未列出过敏原”可以说明资料缺失，不能冒充具体配料清单。模型有时为了给出一段安全解释，把实例问题改成边界问题，这就是需要专门观测的误接收。

## 3. 一条输入怎样成为可比较结果

一次输入包含固定问题、范围和候选资料，以及调用前标注的预期类别与接收决定。预期标签常称 gold，它不是运行后看到哪个模型更顺眼再决定的答案。

两条实验路线使用相同问题、候选正文、提示、超时、输出上限与重试约定，仅模型和必要接口字段不同。发送顺序按题目交替，降低某一方案总是先发带来的环境偏差。仍然要保存实际请求，因为配置写了“不重试”不等于网络层一定只发了一次。

下段来自 `scripts/c1-model-support-comparison.ts` 的评分函数。它逐候选对比实际与预期，并分别记录误接收、误拒收，以及整条输入的接收集合是否完全正确。

```typescript
export function scoreModelSupportComparison(item: ModelSupportComparisonCase, row: ModelSupportComparisonRow) {
  const candidates = item.expectedByCandidate.map(gold => {
    const invalid = Boolean(row.verification?.validation?.invalidDecisions.some(decision => decision.id === gold.id));
    const actual = row.execution === "completed" && !invalid ? row.verification?.value.find(decision => decision.id === gold.id) : undefined;
    return { id: gold.id, expectedPositive: gold.supported, state: invalid ? "invalid" : actual ? "valid" : "missing",
      category: actual?.category ?? null, supported: actual?.supported ?? null,
      passed: Boolean(actual && actual.category === gold.category && actual.supported === gold.supported),
      falseAccepted: Boolean(actual && !gold.supported && actual.supported), falseRejected: Boolean(actual && gold.supported && !actual.supported) };
  });
  const complete = row.execution === "completed" && row.verification?.validation?.status === "complete"
    && row.verification.value.length === item.candidates.length && candidates.every(candidate => candidate.state === "valid");
  return { candidates, passed: complete && candidates.every(candidate => candidate.passed),
    exactAcceptanceSet: complete && candidates.every(candidate => candidate.supported === candidate.expectedPositive) };
}
```

`passed` 要求类别和接收决定都正确；`exactAcceptanceSet` 只问该接收的有没有全接收、不该接收的有没有全拒收。`falseAccepted` 针对负例被接收；`falseRejected` 针对正例被拒收。缺失、结构无效或未完成不能混进“正确拒收”。

这段代码把不同错误拆开，是为了让选型面向业务后果：类别名字错了可能影响分析；缺失事实被接收则可能让客服给出错误承诺。两者都保留，但不能只用一个平均分掩盖差异。

## 4. 同分的历史对照怎样解读

| 指标 | DeepSeek Pro | 千问候选 |
| --- | ---: | ---: |
| 输入全部执行 | 12/12 | 12/12 |
| 分类与接收同时正确 | 9/12 | 9/12 |
| 精确接收集合正确 | 12/12 | 10/12 |
| 负例误接收 | 0/12 | 3/12 |
| 正例接收 | 12/12 | 12/12 |

每条输入包含两篇候选，所以每个模型有十二个输入、二十四个候选判断；十二个负例和十二个正例是候选层分母。“三个误收”不等于三个会话失败，也不等于三次 HTTP 错误。

千问候选的误接收中，有资料没有说明批准角色，却被当作“边界回答”接收；也有资料未收录过敏原，却被当作能回答清单。引文都能在原文找到，错误在于它没有支持用户真正索要的内容。

另一方案也存在类别错误，例如把“相关但不充分”分成“无关”；但两种类别都导出拒收，因此接收集合仍正确。保留这些错误能指导下一轮分类修复，不能为了总分更高就运行后修改标签。

## 5. 为什么必须同时准备正例与负例

![售后业务主线](https://cdn.nlark.com/yuque/0/2026/png/67086517/1791438662607-f1042921-fa53-4302-926e-fa7cdb34672a.png)

图 2：售后从用户诉求出发，经过订单与规则、商家确认、退款保护，最后形成结果账本。模型选择应落到具体业务决策的收益和风险，而不只比较总分。

只考负例，一个永远拒收的模型就可能满分；只考正例，一个永远接收的模型也可能满分。两组要同时存在，分别回答“会不会说过头”和“会不会明明有答案却不帮助用户”。

条件覆盖也是正负例设计的重要部分。给一篇写着“工作日可用、节假日除外”的资料，用户问工作日使用流程和法定节假日可用性，两个问题可能有不同答案。不能只改变几个关键词，应该让对象、前提、例外与问法真实改变决策。

对照还要固定无答案输入和范围干扰输入，并保留所有未执行项。新增题目如果来自已知失败模式，应明确属于针对性新题；“不是旧题”并不自动等于盲测或真实用户分布。

## 6. 费用与延迟要跟着真实请求走

这个组件对照每个模型十二次 HTTP，总共二十四次；没有运行主 Agent、检索、数据库或 QQ。一个组件调用只能支持该组件范围内的结论。

费用要从实际发送边界记录，再核对供应商返回的用量。历史估算中，一条路线以美元计，另一条以人民币计，应分列展示；不能直接比较数字大小，或者把失败调用从总费用删掉。若用量缺失，就保留未知并停止后续依赖完整费用的决定。

中位延迟描述当前样本的一般等待时间，高分位描述较慢尾部；十二次小样本尤其容易受缓存和网络影响。不要把某次请求较快写成稳定生产延迟承诺。质量、费用和延迟都完整后，才讨论单位成功输入成本。

## 7. 接口适配也属于比较条件

两个供应商都接受聊天消息，并不表示参数可以原封不动复制。有的输出上限字段不同，有的对系统消息角色和流式用量格式有特定要求。应让业务内容与预算含义尽量一致，把必要兼容差异明确记录；不能让一条路线多拿上下文，另一条少拿候选，再把差异归因于模型。

凭据也必须与实际供应商绑定。切换模型应选择它自己的端点与凭据，不能只改模型名，却把主模型密钥发送给另一家。请求前校验地址、模型、载荷和预算，请求后核对响应模型与用量，才能确认比较的确是预定的两个对象。

## 8. 把停止条件写在运行之前

这次对照预先要求：完整执行；负例零误收；没有新增正例误拒；精确接收集合比原方案改善。千问候选没有满足门槛，因此不进入完整会话候选，默认方案保持。

停止不等于证明某模型普遍更差。它表示在这一职责、这套输入和当前约束下，没有足够理由承担切换成本。接下来应先解释失败属于诉求理解、条件覆盖还是接口问题，再决定是否有新假设值得独立实验。

继续调整已经曝光的问题，能帮助开发，但不能再把这些题目当独立验收。换提示、换数据、换模型、改评分同时发生时，更无法判断改善来自哪里。每次只研究明确变量，留下退步样本，才有可复述的选型结论。

练习：候选模型误收由两条降到零，但正例误拒增加四条。列出你需要向业务确认的代价，并设计一个有明确分母和停止条件的小批新题。不要用“更安全所以一定更好”代替用户仍需获得帮助的事实。

## 9. 静态分工、动态路由和故障降级是三件事

本项目已有按职责配置模型的能力，也做过固定题的模型对照。它没有“先自动判断任务复杂度，再为每个请求挑模型”的通用路由器。面试时说“主 Agent、问题解析、重排和支持判别可以分别选型”，要同时说明哪些角色只出现在候选路线，不能把组件可配置说成默认线上都在执行。

| 决策 | 触发时机 | 当前状态 | 最重要的验证 |
| --- | --- | --- | --- |
| 静态职责分工 | 启动或实验配置时 | 已有；保留模型、凭据和实际参数快照 | 该职责的准确性、延迟和费用 |
| 按复杂度动态路由 | 每次任务到来时 | 未实现；需要新业务收益才启动 | 路由器自身错误与额外费用、被送错模型后的损失 |
| 供应商故障降级 | 超时、限流、不可用时 | 没有跨供应商自动切换 | 原请求是否仍在执行、预算是否累积、重复副作用如何避免 |

简单场景不一定需要模型：精确确认和本人最近订单列表已有不经模型的宿主路径。明确订单号后的普通查询仍可能由模型选择 `get_order`，不能笼统说所有查单和状态卡都零模型。优先利用已经实现的确定性分流，比新增一个模型判断“该不该调模型”更容易解释和核验。涉及金额、批准或身份时，无论选择哪个模型，都不能绕过工具边界。

如果未来确需动态路由，应先定义可以测量的复杂度特征，例如是否需要跨多份规则、是否存在歧义、是否需要多轮澄清；再保留一组简单与复杂、正常与对抗的新题。对照固定主模型，记录路由成本与完整任务质量。不能仅用提示词让模型输出 easy/hard，就声称降低了总成本。

## 10. “模型失败就换一个”为什么不是完整兜底

读工具超时可以在有限次数内重试，前提是有剩余预算且操作无副作用。模型输出结构不合法可以要求一次有界修复；缺订单和指代歧义应向用户澄清。退款提交后连接断开则先查询持久结果，不能让新模型重新猜测并执行退款。

选择备份模型还要核对工具调用格式、输出限制、上下文容量和凭据归属。更小模型可能无法承接已有长对话；更大模型可能增加费用与尾延迟。备份模型与重试共享同一任务预算，不能通过换模型绕过上限。

检索降级也不能悄悄改变“有证据”的含义。向量服务异常后用关键词召回，只能得到新的候选资料，仍要检查门店、商品、版本和当前问题是否被原文支持。当前配置支持 lexical 不等于所有候选异常都已经自动安全降级。

练习：用户已精确确认退款，随后连接中断；同时主模型不可用。请画出“重新授权 → 查持久结果 → 告知已完成或当前状态”的路径，并说明为什么不需要让备份模型重新计算金额。

## 11. 面试中的两分钟选型答法

“我先按职责拆错误代价：主 Agent 要正确选工具，支持判别要避免把缺失事实当依据。对比时固定问题、资料、参数和严格标签，分开误接收与误拒收。历史十二输入对照中，候选总分相同但出现三个负例误接收，因此未推进；默认路线没有切换。我还没有实现复杂度自动路由，当前先用宿主精确协议处理确定性动作，再用新题检验候选是否带来完整任务收益。”

这段答法有可追踪的项目事实，但不是通用结论。面试官继续问“那什么时候换”时，回答预先冻结的推进门槛、失败样本、调用预算和停止条件，随后打开对应结果记录，而不是泛称某模型更聪明。

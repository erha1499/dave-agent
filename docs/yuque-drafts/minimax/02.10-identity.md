# 02.10｜可信身份：订单授权与旧上下文失效

用户说：“我是客户 B，帮我查一下他的订单。”模型能读懂这句话，但文字不能证明用户真的属于 B。再考虑另一种情况：同一个 QQ 账号原来绑定客户 A，后来改绑客户 B，旧聊天里已经出现 A 的券信息。即使新工具不能查 A，模型也可能从旧历史中再次说出它。

这两类风险需要不同处理：工具执行时校验当前归属，身份变化时让旧会话失效，并在发出回复前再查一次绑定。下面沿这条链路解释为什么缺一层都不够。

## 身份从哪里来

可信入口是系统接收到的平台消息信息，例如应用标识和发信人标识。宿主将二者组成 `identity`，业务绑定表再把它映射到客户。模型读到的用户自称、昵称、订单号或历史话术，都不能代替这个映射。

三个对象不要混淆：QQ 发信人是渠道中的人，客户是业务订单的所有者，订单号是被操作的对象。一个人知道某个订单号，不代表数据库允许他访问对应客户的数据。

| 输入 | 用途 | 能否授予订单权限 |
| --- | --- | --- |
| 平台消息的应用与发信人 | 找当前业务绑定 | 需要继续查绑定与归属 |
| 用户说“我是某客户” | 帮助理解诉求 | 不能 |
| 模型提交的订单号 | 定位候选订单 | 不能 |
| 当前绑定和订单所属客户一致 | 决定本次能否读取 | 可以进入受限读取 |

## 工具不让模型选择身份

`get_order` 的参数只有 `orderId`，并拒绝额外字段；身份来自创建会话时的外层变量。执行体把二者分别交给 `store.getOrder(identity, orderId)`。因此，模型不能在工具 JSON 中补一个 `customerId` 给自己换身份。

但是，参数里没有客户 ID 还不够。如果宿主只在建会话时查一次客户，然后永久复用旧值，解绑就不能及时生效。授权服务要在每次执行中重新解析可信发信人，并用当前绑定核对订单。

以下是 `src/coupon-store.ts` 中 `CouponStore.getOrder` 的事务节选。函数在此前已校验身份与订单号格式，取得数据库连接并设定只读事务属性：

```typescript
      await connection.beginTransaction();
      started = true;
      const asOf = new Date().toISOString();
      // Re-resolve the trusted sender on every call; never accept a customer ID from model arguments.
      // The authorization row and all business facts share the first SELECT's consistent snapshot.
      const rows = await this.select(`SELECT /*+ MAX_EXECUTION_TIME(3000) */
        o.id, o.status, o.total_cents, o.paid_cents, o.refunded_cents, o.created_at, o.paid_at,
        s.id AS shop_id, s.name AS shop_name, s.address, m.name AS merchant_name
        FROM orders o JOIN qq_identities q ON q.customer_id = o.customer_id
        JOIN shops s ON s.id = o.shop_id JOIN merchants m ON m.id = s.merchant_id
        WHERE o.id = ? AND q.app_id = ? AND q.sender_id = ? LIMIT 1`, [orderId, identity.appId, identity.senderId], connection);
      const order = rows[0];
      if (!order) throw notFound;
```

核心是 `orders` 与 `qq_identities` 的连接条件：订单客户必须等于绑定客户。查询条件还同时限定订单号、应用和发信人。`?` 对应参数数组，不把模型输入拼进 SQL 结构。

找到订单后，函数继续在同一只读一致性快照里读取商品、券、付款和退款事实。这样一次返回中的归属和业务状态有共同的读取基准。这个快照说明本次查询看到什么，不承诺之后每一刻都不变；下一次业务动作仍要重新检查。

找不到或越权都走统一的不可查询回复。这样既不返回订单详情，也不通过不同错误提示透露别人的订单是否存在。数据库异常另转成受控错误，不把 SQL、连接地址和驱动诊断交给模型。

## 为什么授权检查不会自动清除旧聊天

假设第一轮 A 的订单已经进入模型历史，随后管理员解除绑定。第二轮模型回答“你那张券还未使用”时，可能根本没调用工具。只在工具里拦截，无法阻止它复述旧输入。

因此，每个 QQ 会话还保存一份处理时的绑定快照。快照包含客户 ID 和绑定行 ID：客户相同但解绑重绑生成了新绑定行，也算授权关系变化。只比较客户 ID 会漏掉这种重新绑定。

`src/qq-agent.ts` 的 `QQAgent.enqueue` 在会话真正出队、准备处理时执行：

```typescript
if (this.resolveBinding) {
  try {
    const current = await this.resolveBinding(msg);
    binding = current && { ...current };
    bindingReady = true;
  } catch {
    failed = true;
    modelTask.fail("authorization_failed");
    this.log("[agent] 会话身份读取失败；本轮尚未处理业务。");
    return;
  }
  if (this.closed || !validQQMessage(msg)) return;
  if (conversation.session && !sameBinding(conversation.binding, binding)) {
    conversation.session.dispose();
    conversation.session = undefined;
    conversation.turns = 0;
  }
  conversation.binding = binding;
}
```

先读取当前绑定，读取失败就停止本轮；随后与旧会话绑定比较。发生变化时销毁旧 Pi Session，清空处理计数，后续重新创建 Session。相同绑定保留上下文，所以不是每轮都忘记聊天。

把检查放在出队时有实际意义：消息可能在队列里等待，排队前的身份并不能代表开始处理时的身份。用户连续发了两条消息，管理员在两条之间改绑，第二条不能继承第一条的模型上下文。

## 生成期间发生变化，如何拦住旧回复

还有一个时间窗口：模型已经开始生成，管理员此时撤销绑定。开始处理时的检查已经通过，等模型结束再发送可能泄露旧结果。因此发送路径还要复核。

下面是同一函数内 `deliverBound` 的实际节选。它在调用底层发送函数之前执行：

```typescript
try {
    const current = await this.resolveBinding(msg);
    if (!bindingReady || !sameBinding(binding, current)) {
      failed = true;
      modelTask.fail("authorization_failed");
      this.log("[agent] 身份绑定已变化；未发送旧会话回复。");
      return "deferred";
    }
  } catch {
    failed = true;
    modelTask.fail("authorization_failed");
    this.log("[agent] 回复发送前身份读取失败；未发送。");
    return "deferred";
  }
}
```

当前绑定与本轮开头不一致，或者读绑定失败，都会标记失败并返回未发送。`modelTask.fail` 将失败原因记录到本轮测量中，不改变授权判断。外层失败清理负责销毁会话，下一轮重新建立可信上下文。这里选择失败时拒发，因为“暂时查不到授权”不能解释成“沿用旧授权”。

| 时点 | 宿主或工具的动作 | 为什么在这里检查 |
| --- | --- | --- |
| 消息出队后 | 读取当前绑定；若绑定变化，更换会话 | 排队期间身份可能已改变 |
| 模型开始处理 | 提供本轮可用的上下文 | 旧聊天不能继承授权 |
| 工具查询订单 | 按可信身份重新授权查单 | 模型选择的订单号只是输入 |
| 工具返回后 | 模型依据允许读取的事实生成回复 | 查询结果属于本次读取范围 |
| 回复发送前 | 再读绑定，一致才尝试发送 | 处理期间的解绑不能被忽略 |

## 用两条时间线检查理解

第一条：小林读取 A 订单，管理员改绑，下一条消息出队。宿主发现绑定变化，更换 Session；旧订单不会作为新会话历史自动送给模型。模型若再次申请 A，工具根据新绑定重新判断归属。

第二条：小林发问，宿主检查通过，模型等待时管理员改绑。发送前复核发现不同，旧回答拒发。之前已经送给模型供应商的输入不能被这个检查撤回，所以处理前和发送前两处保护承担不同职责。

## 读取权限与操作许可仍要分开

查到本人订单只证明本轮可以看到订单事实，不表示已经获准联系商家或执行退款。用户选择订单卡也只是消除对象歧义。商家批准、退款方案展示和本人精确确认，都有自己的状态与适用对象，不能从一次成功查询继承出来。

因此同一可信身份会被传到不同业务服务，每个服务检查当前动作需要的条件。读取一笔订单与提交一次资金操作，即使拥有相同订单号，也不是同一种权限。这种分工让后续添加业务动作时仍能明确需要哪些前提，而不是依赖模型记住“用户已经通过验证”。

## 这套保护接受什么代价

成功出站的普通轮次需要额外读取绑定，绑定服务故障时宁可暂时停止，而不使用缓存授权。身份变化还会损失原聊天上下文，用户可能需要重述。这些代价换来清楚的失效行为。

两次读取毕竟是快照。如果绑定在两次检查之间变成其他客户又改回，或者最后一次检查之后才撤销，仍可能无法发现；数据库授权与 QQ 发送没有组成跨系统原子事务。说明这个窗口有助于判断方案适用范围，不能把发送前检查叫作“完全实时撤权”。

网页也需要当前身份与历史归属检查，但浏览器角色选择不是生产登录。不同入口可以复用订单授权服务，同时分别实现自己的会话持有与发送检查，不能因为共享工具就省去入口边界。

## 练习与面试追问

为什么模型不能填写客户 ID？因为语言输入可以伪造，而授权必须来自可信入口和当前业务绑定。为什么每次工具重新授权仍不够？因为旧事实已经可能进入模型上下文，模型可以不调用工具直接复述。

请在时间线上标出“排队前”“真正出队”“工具查询”“准备发送”四个位置。分别插入一次解绑，说明哪一层会处理、哪些输入已经发出、哪里仍有快照窗口。能回答这些问题，比只说“做了鉴权”更准确。

# 06.20｜网页重试：请求回放与旧会话隔离

## 页面没收到回复，能不能再发一次

客户发出“我的订单有哪些”，服务端已经查完并保存了答复，网络却在返回时断开。用户看见的只是等待状态。此时直接生成一个新请求重发，可能重复调用模型；只禁止按钮连点，又挡不住刷新和多个标签页。

本课把问题拆成三件事：**谁可以读取这段对话、这条消息是否受理过、迟到结果还属于当前页面吗**。答案分别由归属校验、请求回执和运行会话检查承担。

## 五个对象，各管一件事

| 对象 | 作用 | 不能替代什么 |
| --- | --- | --- |
| 浏览器归属能力 | 找到这个浏览器保存的对话 | 真实账号登录 |
| `conversationId` | 长期定位同一段已保存对话 | 当前发送权限 |
| `sessionId` | 标记这一次活动运行 | 订单归属授权 |
| `requestId` | 标记这一条用户输入 | 任意新问题的复用编号 |
| 回执 | 保存原文、处理状态和最终结果 | 逐字流的每个片段 |

能力令牌保存在浏览器的 HttpOnly cookie 中，页面脚本不能直接读取。服务端保存令牌哈希。知道一个公开 UUID 并不等于拥有读取权；打开历史还要核对浏览器归属、客户角色和当前绑定。

## 先看最关键的请求入口

以下节选自 `src/web-chat.ts` 的 `WebChatSessions.send`。`authorize` 会读取当前客户绑定；这里从授权通过后的运行会话检查开始：

```typescript
    if (entry.public.id !== sessionId) throw new WebChatError(401, "页面会话已失效，请重新连接。");
    const previous = this.history.receipt(entry.public.conversationId, sessionId, requestId);
    if (previous && previous.text !== text) throw new WebChatError(400, "同一请求编号不能用于不同原文。");
    const emit = (event: Progress) => {
      if (!entry.active || !this.history.active(entry.owner, sessionId, entry.tokenHash)) return;
      // A disconnected progress observer cannot change the read-only turn or its cached receipt.
      try { onProgress?.({ ...event, sessionId, requestId }); } catch { /* Progress is not delivery authority. */ }
    };
    if (previous?.result) { emit({ type: "start", replayed: true }); return structuredClone(previous.result); }
    if (previous?.status === "interrupted") throw new WebChatError(503, "本轮结果未知，未自动重发。请继续咨询或新建对话。");
    if (entry.busy) throw new WebChatError(409, "消息仍在处理中，请等待回复。");
```

这段代码可以按四个判断读：

1. 当前服务端会话必须等于页面提交的 `sessionId`，否则它是旧页请求。
2. 如果同一编号曾被受理，原文必须完全相同。换了问题就必须使用新编号。
3. 如果已有完整结果，复制原结果返回；这是回放，不会再调用模型。
4. 如果上轮已中断，明确提示未知并拒绝自动重发；如果仍忙碌，要求等待。

`emit` 只是传递处理进度。浏览器断开导致进度观察者报错，不能反过来改变服务端已受理请求或回执。

## 保存记录用两个短事务

事务是把一组数据库操作作为整体提交或回滚。这里使用本机 SQLite 保存聊天记录；业务订单仍从业务数据库读取。SQLite 中主要有三张表：

- `conversations`：配置、公开消息、轮数和状态。
- `owners`：当前活动运行、令牌哈希、进程与租约到期时间。
- `requests`：每条输入的原文、状态和最终回执。

租约表示“这次运行在一段时间内仍拥有处理资格”。旧进程退出或租约过期后，恢复逻辑可把未完成请求标为中断。

完整时序是：**短事务受理 → 事务外等待模型 → 短事务保存结果**。网络调用不能占着数据库写锁等待几十秒，否则其他写入、受理和恢复事务会等待。当前 SQLite 使用 WAL 模式，普通读取通常可以与写入并行。

受理阶段由 `src/web-chat-history.ts` 的 `claim` 完成。下面是写入受理记录的连续节选，前面已经检查活动运行、令牌、轮数和重复编号：

```typescript
      this.db.prepare("INSERT INTO requests VALUES(?,?,?,?,'pending',NULL)").run(conversation.id, runtime, request, text);
      conversation.messages.push({ id: `${request}:user`, role: "user", text, status: "pending", createdAt: new Date().toISOString() });
      this.db.prepare("UPDATE conversations SET messages=?,turns=turns+1,state='busy',updated_at=? WHERE id=?")
        .run(JSON.stringify(conversation.messages), Date.now(), conversation.id);
      this.db.prepare("UPDATE owners SET busy=1,expires=? WHERE owner=?").run(Date.now() + timeout + 5000, owner);
```

先写 `pending` 回执，再保存用户原文、增加轮数并标为忙碌。这些变化在同一个事务里：要么全发生，要么都不发生。只有受理保存成功，才继续昂贵的模型调用。

处理成功后，`complete` 再核对活动租约和 `pending` 状态，把回执改为 `completed`，追加助手公开回复，并释放忙碌状态。页面收到“完成”之前，服务端已保存最终结果。

## 进程退出以后，恢复什么

假设进程在收到模型答复之前退出。重启后不能猜测远程调用是否完成，更不能把 `pending` 当作未执行。恢复逻辑会保留用户原文，追加“上次咨询未完成”的说明，把回执标成 `interrupted`。

如果进程在保存结果之后退出，最终回执已经存在。同一次仍有效的运行重试可回放；重新打开持久对话会创建新的运行编号，旧请求编号不能跨运行重复使用。用户可先读已保存历史，再明确发起新的咨询。

打开历史时，授权检查如下，节选自 `src/web-chat.ts` 的 `open`：

```typescript
    const saved = this.history.read(conversationId);
    if (!saved || saved.owner !== owner || saved.profile !== profileId || saved.binding !== binding.bindingId || saved.customer !== binding.customerId)
      throw new WebChatError(404, "找不到当前客户的会话记录。");
```

这里同时比较浏览器归属、角色、绑定行和客户。旧对话即使属于这个浏览器，绑定变了也不能照常展示。恢复的是用户原文和公开答复，不是旧的退款批准、选单权限或 SDK 私有轨迹。

## 多个标签页为什么要提交预期会话

同一个浏览器的标签页共享 cookie。设页面 A 还显示旧会话，页面 B 已切到客户 B，新 cookie 已写入。如果服务端只看 cookie，A 的旧问题可能被放进 B 的对话。

因此 A 必须提交自己看到的 `sessionId`。服务端发现它和当前运行不一致就拒绝。新建和打开历史也使用这种“先比较当前值，再改变”的方式，通常叫比较并交换。SQLite 的活动归属事务还会再检查一次，收紧并发窗口。

迟到的旧消息响应不应清除或覆盖新 cookie。页面遇到失效后保留原稿，先读取当前状态，再让用户明确重新连接或打开历史；不能悄悄把旧问题再发一次。

## 流式文本为什么不是最终回执

页面用 SSE 接收服务器推送的事件。`step` 是“查询订单”“查阅规则”等公开步骤，`delta` 是实际模型文本片段，最终 `result` 事件中的 `reply` 字段才是本轮整理好的结果。推理内容和完整内部工具参数不直接展示给用户。

本轮模型尚未取到依据时，页面只显示公开处理步骤，不公开模型自由文字。否则，最终回复即使拦住“历史已批准”“已核销一律不退”等无据断言，用户也可能已经在逐字流里读到了它们。

每次用户请求都创建新的 `currentEvidence` 数组。它收集的是这次执行中真实的 `tool_execution_end`，即工具执行结束事件，而不是从历史消息里挑出看起来像工具结果的内容。宿主通过 Pi 调用的嵌套工具也会产生这个事件；只监听外层 `message_end`，可能漏掉这些必要读取。网页仍只开放 `get_order`、`list_orders`、`search_faq` 三项只读工具，并没有因此切换成其他架构或开放售后写入。

先看共享提取函数。`Evidence` 只包含工具名、失败标记和返回内容；`record` 检查结果是否为对象。畸形结果也保留，让后续结构检查拒绝，而不是丢掉错误后继续相信更早的依据：

```typescript
export function toolEvidenceFromEvent(event: AgentSessionEvent): Evidence | undefined {
  if (event.type !== "tool_execution_end") return undefined;
  // Keep malformed results so the reply boundary rejects them instead of reusing earlier evidence.
  return { toolName: event.toolName, isError: event.isError,
    content: (record(event.result) ? event.result.content : undefined) as Evidence["content"] };
}
```

网页按发生顺序收集这些结果，并在下一段助手消息开始时判断能否公开其文字。下面是订阅器中的连续源码；`canStreamBusinessText` 检查当前结果，`step` 只发布允许展示的处理步骤：

```typescript
            if (event.type === "message_start" && event.message.role === "assistant") {
              messageId = `assistant-${++messages}`;
              streamAllowed = canStreamBusinessText(currentEvidence);
              step(messageId, "整理答复", "running");
            } else if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta" && messageId && streamAllowed) {
              emit({ type: "delta", messageId, text: event.assistantMessageEvent.delta });
            } else if (event.type === "message_end" && event.message.role === "assistant" && messageId) {
              step(messageId, "整理答复", ["error", "aborted"].includes(event.message.stopReason) ? "error" : "done");
            } else if (event.type === "tool_execution_start" && Object.hasOwn(toolLabels, event.toolName)) {
              const pending = { id: `tool-${++calls}`, label: toolLabels[event.toolName]! };
              pendingTools.set(event.toolCallId, pending);
              step(pending.id, pending.label, "running");
            } else if (event.type === "tool_execution_end") {
              const evidence = toolEvidenceFromEvent(event);
              if (evidence) currentEvidence.push(evidence);
              const pending = pendingTools.get(event.toolCallId);
              if (pending) { step(pending.id, pending.label, event.isError ? "error" : "done"); pendingTools.delete(event.toolCallId); }
            }
```

这里有三种不同出口：

| 本轮已经取得什么 | 最终显示什么 | 是否公开模型文字片段 |
| --- | --- | --- |
| 只有订单 | 结构化订单事实及尚缺规则的提示 | 否 |
| 只有合法 FAQ 文档 | 文档标题、来源编号与原文，并说明没有核对具体订单 | 否 |
| 当前订单，随后取得范围匹配的规则，且没有失败或固定卡片冲突 | 订单事实与模型解释 | 可以，使用真实 Pi `text_delta` |

只有 FAQ 的通用咨询仍然有可读答案，但不允许它替历史订单结论背书。以下是最终回复的源码分支；此时前面的校验已经检查来源、编号、标题、正文与适用范围，`toolFailed` 分支也已经拦截失败：

```typescript
  if (facts.documents.length) return { kind: "answer", evidenceIds: [...evidenceIds],
    text: "以下仅展示本轮查到的规则原文，尚未核对具体订单；不表示订单已满足条件，也不构成退款批准。\n\n"
      + facts.documents.map(document => `${document.title}（${document.sourceId}）\n${document.body}`).join("\n\n") };
```

同一轮也可能切换订单或重新读取状态。每次成功解析新的 `get_order` 结果时，共享回复模块先执行下面这段，再接受新的订单事实：

```typescript
      // A new order snapshot needs rules read after it, including a reread of the same order.
      evidenceIds.clear(); ruleScopes.length = 0; documents.length = 0;
      merchant = undefined; refund = undefined; merchantEmpty = false; refundEmpty = false;
```

所以“查 A 规则 → 再查 B 订单”和“查订单及规则 → 又重读同一订单”都需要后续规则取证，旧材料不能自动解锁新的解释。同一订单重新读取还会替换原来的金额、券状态和范围，不能让旧范围继续阻止新规则被接受；不同订单的事实分别保留，规则覆盖不足时降级。

这段共享逻辑还清掉旧协商卡、退款卡和“未查到任务”标记。它用于售后入口时，先前 A 单的退款按钮不能在切到 B 单后残留；即使后续 B 单规则查询失败，也不会恢复 A 卡。必须重新成功执行对应业务工具才有新卡，新的订单读取本身不会清除尚未解决的业务查询失败。网页没有这些写入卡片，仍保持只读。

带门店或商品范围的规则查询还会在工具入口核对本轮已授权读取的订单范围；范围参数不能由模型凭空授予。上一轮的消息和工具结果不进入本轮证据数组。

这些检查约束依据的新鲜度、顺序、结构与范围，**没有逐句判断模型文字是否被依据支持**。订单与规则齐备后的自由解释仍须评测，不能把“允许流出”说成“每句话都正确”。门槛在每段助手消息开始时判断；若后续查询失败，已经发出的片段无法撤回，最终回执仍会按最新结果处理。

流式片段用于等待体验；断线时可能只收到半句。回执保存完整 Reply 和步骤，不保存每个逐字片段。因此完成后的重试直接恢复完整答案，不从头伪造一次打字动画。前端还用请求与会话编号过滤迟到事件，避免旧回复追加到新对话。

## 用三个失败例子检验设计

| 发生了什么 | 服务端依据 | 页面应做什么 |
| --- | --- | --- |
| 保存结果后返回断线 | 存在完整回执 | 同一有效请求回放原结果 |
| 模型处理中进程退出 | 只有 pending，恢复为 interrupted | 显示未完成记录，用户决定下一步 |
| 另一页已经切换客户 | sessionId 不匹配 | 保留原稿，重新连接后明确目标 |

再想一个问题：同一 `requestId` 改了一个字重发，应不应该接受？不应该。编号绑定的是完整原文；否则服务端无法知道用户想取旧答案，还是提出了新问题。

## 工具拒绝了，为什么答复仍可能不合格

客户 B 输入客户 A 的订单号。工具重新检查当前身份，拒绝读取，没有返回券状态或金额；但页面最后只说“本轮读取未能完成，请稍后核实”。前半段守住了访问边界，后半段却没有告诉用户：这个入口只允许查询本人订单，不能代查他人订单。用户可能把它理解为暂时网络故障，继续尝试相同请求。

因此执行拒绝与拒绝说明要分别验收：

| 要回答的问题 | 看什么证据 | 通过条件 |
| --- | --- | --- |
| 是否真的阻止了越权读取 | 实际工具调用、当前身份和返回结果 | 拒绝访问，输出中没有他人订单事实 |
| 用户是否看懂了边界 | 最终页面回复及已公开的流式片段 | 明确只能查本人订单、不披露他人信息，并给出可行下一步 |
| 是否准确解释了失败原因 | 工具错误与固定提示的措辞 | 普通服务故障不能被说成已经确定发生越权，也不能泄露内部诊断 |

修复位于宿主最终回复的固定分支，而不是让模型再解释一次。下面是订单读取失败时的源码：

```typescript
  if (facts.orderFailed) return { kind: "notice", text: listFailed ? "最近订单暂时无法查询，请稍后重试或核对本人身份绑定。"
    : "本轮订单读取未能完成，无法继续展示该轮办理信息。仅支持当前客户本人订单，不能代查他人订单或披露其券状态、金额。请核对本人订单号或联系人工核实；不能据此判断操作是否执行。" };
```

这个提示说明一般访问范围，没有断言“这次一定是越权”或“该订单确实存在”。授权拒绝与普通读取故障都可能进入此分支；完整工具错误不直接发送给用户。固定文字也不改变数据库授权逻辑，更不能让失败的读取继续执行。

另一个容易遗漏的细节是入口能力。网页只有三项只读工具，缺少订单信息时若仍提示“联系商家或退款仍须本人发送对应的完整确认”，虽然没有承诺确认后就执行，却容易让用户误以为此处具备办理能力。缺信息分支现在按实际开放的准备工具决定是否附加确认边界：

```typescript
  const confirmation = activeToolNames.some(name => name === "prepare_merchant_request" || name === "prepare_refund")
    ? "涉及业务办理时，仍须本人发送对应的完整确认，普通同意不构成授权。" : "";
  return { kind: "notice", text: "你好，请写明要咨询的问题；涉及具体订单时请提供订单号。本轮尚未取得最新订单或适用规则依据，不能确认办理条件或结果。" + confirmation };
```

只读网页不带这段办理确认提示；开放相应工具的售后会话仍保留。判断的是本轮工具能力，不能因为历史里出现过退款文字，就让当前渠道看起来具备写入能力。

这种纯宿主文字修改可以用确定性检查验收：分别输入授权拒绝和普通服务故障，确认固定回复说明本人范围、不显示内部错误；再比较只读与售后工具集，确认只有后者保留必要确认提示。模型、Prompt 和 Skill 没有变化，不需要为了证明固定字符串变化而重复付费跑同一批题。不过，这只能证明宿主新分支的行为，不能将此前真实模型批次的失败追认成成功；新的固定输出检查与旧批次成绩应分别记录。

## 成本与适用范围

SQLite 让单机重启后仍能找回公开历史，避免额外部署一套服务。代价是要处理受理状态、租约、坏记录和容量。当前每段对话最多 20 轮；每个浏览器归属与客户角色最多保存 100 段，全局最多 1000 段。到上限拒绝新增，已有记录仍可查看。

这套设计适合本机只读客服。SQLite 事务不覆盖业务数据库的授权读取、远程模型调用或 HTTP 传输；最后一次授权读取之后发生的撤销仍有窗口。超时会请求取消，但不能保证提供商已停止执行或停止计费。

面试时可概括为：我把稳定对话、活动运行和单条请求分开；先落受理记录，再调用模型，最后保存回执。已完成就回放，中断就显式保留未知，恢复历史时重新核对身份。

# 04.10｜会话重建：恢复定位，重新授权

小林为 A 单联系商家，等待期间又选了 B 单咨询。服务重启后，他先问“那次协商怎样了”，再问“我选中的订单呢”。前一句指 A 的任务，后一句指 B 的订单焦点；收到 A 的通知不表示用户改选 A。

会话恢复首先要分清恢复什么。订单号可以帮助定位，历史回复可以帮助理解指代，数据库记录才能告诉我们现在是否批准、是否退款。把这些东西统称为“记忆”，容易让历史信息承担它没有的权限。

## 三种状态放在不同地方

| 状态 | 保存什么 | 重建后怎样使用 |
| --- | --- | --- |
| Pi 消息上下文 | 用户消息、模型回复和工具结果 | 帮模型理解当前对话；QQ 更换 Session 后不自动还原全部消息 |
| 宿主业务引用 | 当前订单焦点、候选选择、政策原问与任务指向 | 帮代码找到对象；有效期和身份仍要检查 |
| 持久业务记录 | 订单、券、协商任务和退款结果 | 重新授权读取当前事实；不会随聊天消失 |

Session 就是一段对话的运行上下文。业务焦点是“当前咨询哪一单”，任务引用是“在问哪次协商”。它们可以指向不同订单，系统应该分别保存与读取。

图 1：业务状态和通知投递走两条线。投递结果未知时，应核对持久账本，不能自动认定业务失败。重建聊天不能重做已经完成的业务，也不能把通知对象当成当前焦点。

## 默认短会话如何重建

QQ 使用进程内 Pi 会话，自动历史压缩关闭。宿主达到二十次处理计数后，在下一次处理前销毁旧 Session，再创建新会话。`src/qq-agent.ts` 的 `QQAgent.enqueue` 中实际分支如下：

```typescript
if (conversation.turns >= 20) {
  conversation.session?.dispose();
  conversation.session = undefined;
  conversation.turns = 0;
}
setPhase("session");
conversation.session ??= await this.createSession(msg);
```

`setPhase("session")` 只记录当前处理阶段，实际轮换由前面的条件和会话销毁完成。这个计数包含可能由宿主直接处理的确认、选择与通知，不能解释为二十次模型请求。它也不是 Token 预算：两轮包含大量工具结果的对话，可能比多轮短问答占用更多输入。每次模型生成上限与整轮总量也要分开。

这是一种简单明确的生命周期选择：旧模型历史结束，但数据库中的协商和退款结果仍在。用户明确提供订单号后，可以再次授权查询。代价是用户可能需要重述之前选中的对象；它没有自动生成摘要或无损恢复所有聊天。

## 持久引用保存到什么程度

项目另有显式的业务 Controller 与 MySQL 引用恢复候选。Controller 是组织固定业务步骤的宿主层，它保存有限的定位信息，而不是把整段聊天当成当前事实。

一条订单焦点包含订单号、来源、选择时间、原到期时间和请求出处。政策引用保存原问题与来源，下次重新检索；历史金额保留当时展示的值与出处，便于与当前值比较；任务引用只帮助查指定任务，不携带新的批准。

这些字段回答四件事：指向谁、为什么选它、何时得到它、现在还能否用于定位。引用沿用原有效期，普通续问不自动延长。恢复时重新生成需要展示的选择令牌，旧展示证明不能从数据库读出后直接当成新确认。

## 为什么一轮开始就先写“需要重述”

假设库里保存 B 焦点，小林这一轮开始改查 A，进程却在处理中退出。如果只在处理成功后更新记录，重启后仍可能把旧 B 当作没有中断的新选择。

实现先把持久状态写成需要重述，然后再做本轮业务。内存里已经校验的引用仍可供当前轮使用；这次处理若失败，下一进程不会从旧快照猜测用户选择。`src/support-session.ts` 的 `createSupportSession` 轮前恢复节选是：

```typescript
        contextSnapshot = next;
        state.focusUnavailable = false;
        // Do not let a crash, error or failed final write resurrect an older
        // locator. The in-memory references remain usable during this turn.
        await saveContext(blockedContext(), abort); assertCurrent();
      } catch {
        assertCurrent(); clearReferences(state); state.focusOrderId = undefined;
        contextFocus = undefined; state.focusUnavailable = true; state.turnError = true;
        throw new Error("会话定位暂时不可用，本轮尚未处理业务，请稍后重试。");
      }
```

`blockedContext()` 返回需要重述的状态，`saveContext` 负责持久写入，`assertCurrent` 确认这仍是有效的一轮。读快照或写阻断失败，就清理定位并停止业务。先阻断再执行，多了一次写入，却使崩溃后的行为更容易解释。

1. 读取当前绑定与旧引用，检查来源和有效期。
2. 可用时在内存恢复对象定位；不可用时清理旧引用或要求明确对象。
3. 先持久保存“需要重述”的阻断状态，避免本轮失败后误用旧引用。
4. 重新授权读取当前业务事实，执行业务并形成本轮结果。
5. 发布本轮仍然有效的新引用。
6. 尝试发送回复。发布与发送分别可能失败，需要按各自结果恢复。

## 两个写者为什么不能互相覆盖

另一个问题是并发：旧一轮读到修订号 7，另一个写者已经保存修订号 8，旧一轮随后完成，不能把新选择覆盖回去。

CAS 是“比较后写入”：只有当前修订号仍等于自己读到的值才允许继续。`src/conversation-state.ts` 的 `ConversationStateStore.bind` 写入事务中包含这段：

```typescript
          const [rows] = await connection.execute<RowDataPacket[]>(
            "SELECT revision FROM conversation_state WHERE source_key = ? FOR UPDATE", [sourceKey]);
          const currentRevision = rows[0] ? revision(rows[0].revision) : 0;
          rejectUnless(currentRevision === expectedRevision, conflict);
```

`FOR UPDATE` 锁住会话行，代码读取实际修订号并与预期值比较。完整事务还先检查绑定身份，检查引用涉及的订单和任务归属，再按原有效期复核，最后递增修订号并提交。首次创建使用插入，不能用无条件覆盖悄悄抢走另一个写者的状态。

锁和修订号解决覆盖顺序，身份和归属解决访问许可，两者不能互相替代。持久引用若指向已不属于当前客户的订单，即使修订号完全一致，也不能恢复后直接使用。

## 把 A 任务与 B 焦点走通

重建后问“那次协商怎样了”，系统先定位 A 的确切任务，再重新读取当前用户对 A 的访问权限与任务结果。这是只读任务查询，不应该把当前订单焦点改成 A，也不生成退款许可。

接着问“我选中的订单呢”，若 B 的引用仍有效且身份一致，系统定位 B，再查 B 当前事实；若引用不存在、过期或有歧义，就请用户明确订单。不能为了少问一句，把刚查到的 A 自动作为 B 的替代。

这里有两个评价目标：有没有查错单，是否免去了用户重述。内存模式无法恢复 B 时，宿主正确澄清可以满足前者，却没有满足后者。评价恢复能力时应分别观察，而不能因为最后没有越权就认为恢复体验完整。

## 取消与最终发布失败怎样处理

本轮业务已经完成，但最终引用保存失败时，不能再次执行业务来修补上下文。应保留实际业务回执，清理不可信定位，下一轮必要时要求重述。业务结果与会话便利信息的优先级不同。

取消也不能撤回已经发出的数据库写入。如果引用发布正在进行，系统等待它结束，再尝试按新修订号补写阻断。QQ 外层还要等完整 prompt 的宿主尾段结束，才能销毁旧 Session 并放行同用户下一轮；只看 Pi 空闲不够。

这段收尾没有硬时间上限，补写也可能失败，所以不能描述成“超时立即终止所有工作”。超时触发取消与受控恢复，真正更换会话仍需等待旧工作结束。远端模型是否停止或停止计费，同样不能由本地取消信号保证。

## 网页历史回访为何是另一件事

网页已把用户原文和公开回复保存在本机 SQLite。稳定 `conversationId` 标识同一段可回访对话，运行 `sessionId` 标识这次打开后的活动会话；重新打开旧对话会换新的运行身份，并检查浏览器归属、客户与当前绑定。

这解决的是旧对话回看和续聊，不是把 QQ 全部内部历史持久化，也不是跨新对话自动提炼用户偏好。网页对话的轮数随稳定记录保存，重新打开不会重获额度。公开历史注入新 Pi 上下文后，订单当前状态仍须重新查询。

因此要分别回答“聊天记录还在不在”“能否知道用户刚选了谁”“当前是否有权退款”。它们可能用同一个数据库技术，却有不同的数据来源和失效规则。

## 练习与取舍

在流程的读引用、写阻断、读订单、发布引用、网络发送五个位置分别插入进程退出。逐项回答：数据库业务是否已发生、旧引用是否还能用、用户是否需要重述、重试会不会重执行业务。

保留有限引用比恢复所有聊天更容易说明范围，但每轮增加读取、阻断和发布，并需要身份、修订号与期限检查。当前持久引用仍是候选；它的价值是减少明确对象的重述，不能把它扩展成“记住了所有事实和授权”。

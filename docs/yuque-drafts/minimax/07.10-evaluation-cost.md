# 07.10｜客观评测：失败、分母与成本

一次售后评测计划十二轮，执行八轮：六轮通过、两轮失败，剩下四轮因前置失败没有执行。报告应该写多少通过率？如果只写“六除以八，75%”，读者会误以为整套业务已经跑完。

本课把评测当作一套有计划、有执行、有结果的业务流程：先固定要检查什么，再保留失败、跳过和缺失，最后把质量、延迟与费用放到同一个完整分母下。这样才能判断一次优化到底让什么变好了，又付出了什么代价。

![售后业务主线](https://cdn.nlark.com/yuque/0/2026/png/67086517/1791438662607-f1042921-fa53-4302-926e-fa7cdb34672a.png)

图 1：售后从用户诉求出发，经过订单与规则、商家确认、退款保护，最后形成结果账本。评测需要检查这条链上的行为和状态，不能只检查答案措辞。

## 1. 先定义评测对象，别急着定义分数

案例是一个用户目标，例如“联系商家后完成退款”；轮次是案例中的一次用户输入或异步事件；步骤是一次模型请求或工具调用；检查是一个可确定判断，例如“只生成一条退款记录”。

一个用户轮可能先调用模型、再调用工具、最后再请求模型，所以轮次数不是模型请求数。一次通知事件也可能触发模型；而精确确认可以由宿主直接处理，不经过模型。按真实步骤和 HTTP 记录统计，才能知道实际用了多少服务。

评测计划在运行前写明案例、轮次和检查。工具选择、参数范围、调用顺序、数据库状态以及确认协议可以做确定性断言；措辞是否清楚、是否完整回答，需要另一套回答质量评估。把工具流程通过称为“回答准确率”，会掩盖两种能力的差异。

## 2. 四种结果必须各有位置

| 结果 | 含义 | 例子 |
| --- | --- | --- |
| passed | 已执行且满足检查 | 重复确认返回同一记录 |
| failed | 已执行但不符合预期 | 越权订单被返回 |
| skipped | 明确决定不执行，并保存理由 | 协商失败后跳过退款确认 |
| missing | 计划存在，但没有有效结果 | 进程中断，结果未保存 |

跳过和缺失都不能算成功，但排查方法不同。跳过说明执行器知道依赖失败并如实记下；缺失说明记录链不完整，需要查中断或持久化问题。统一抹掉两者，最后只剩成功案例，会造成幸存者偏差。

在 `src/eval-analysis.ts` 中，`counts` 对完整计划展开后的结果计数，`outcome` 决定父级状态。以下是两个完整函数。

```typescript
function counts(outcomes: Outcome[]): EvalCounts {
  return { planned: outcomes.length, passed: outcomes.filter(value => value === "passed").length,
    failed: outcomes.filter(value => value === "failed").length, skipped: outcomes.filter(value => value === "skipped").length,
    missing: outcomes.filter(value => value === "missing").length,
    passRate: outcomes.length ? outcomes.filter(value => value === "passed").length / outcomes.length : null };
}
function outcome(status: "passed" | "failed" | "skipped" | undefined, children: Outcome[]): Outcome {
  if (status === undefined) return "missing";
  if (status === "failed" || children.includes("failed")) return "failed";
  if (children.includes("missing")) return "missing";
  if (status === "skipped" || children.includes("skipped")) return "skipped";
  return "passed";
}
```

通过率使用 `outcomes.length`，前提是输入已经包含计划中的缺失项。状态合并优先保留失败，其次缺失、跳过，最后才是通过。这意味着一个案例即使大部分轮次成功，只要关键确认失败，就不会被记成完整通过。

回到开头的例子：完整计划通过率是 6/12，即 50%；执行覆盖率是 8/12；已执行轮通过率是 6/8。可以并列报告，但必须把名字与分母说清楚。若案例目标要求全部关键轮次成功，案例通过数还要单独计算。

## 3. 断言要检查业务结果，而不是固定话术

验证退款幂等，应检查两次确认是否引用同一操作、退款记录是否只有一条、金额是否一致。只检查回复包含“成功”两个字，无法发现重复扣账，也可能把一句“操作未成功”误判为成功。

验证越权拒绝，应检查查询输入确实是他人订单、工具拒绝且未返回敏感字段；不能仅看客服语气礼貌。验证规则使用，应检查适用范围、返回的文档以及必要条件，而不是只数来源编号。

这类固定检查器也叫 oracle，即本次评测事先约定的判断标准。它应来自业务合同，而不是运行后根据模型输出临时改答案。发现标签歧义时，保留原始结果，修改题集说明并另存新版本；已看过的题目只能作为开发材料，独立验收用新题。

## 4. 如何记录执行而不干扰执行

项目复用 Pi 事件获取模型消息与工具开始、结束。采集回调只在内存记录，整轮结束后再持久化，避免在实时事件回调里插入数据库写入拖慢或打断 Agent。

下面节选 `src/eval-capture.ts` 的工具采集分支。`toolCallId` 把开始与结束配对；`pendingTools` 保存尚未结束的调用。此处节选开始和结束的主干，后续还会附加越权拒绝标注并删除已结束的待处理项。

```typescript
} else if (event.type === "tool_execution_start") {
  const step: EvalStep = {
    index: steps.length + 1, type: "tool", name: event.toolName,
    durationMs: null, input: event.args, isError: false,
  };
  steps.push(step);
  pendingTools.set(event.toolCallId, { step, started: performance.now() });
} else if (event.type === "tool_execution_end") {
  const pending = pendingTools.get(event.toolCallId);
  if (!pending) { failed = true; return; }
  pending.step.durationMs = Math.round(performance.now() - pending.started);
  pending.step.output = event.result;
  pending.step.isError = event.isError;
```

开始时记录参数和起始时间，结束时补上结果、错误与耗时。遇到没有对应开始事件的结束事件，标记采集失败。整轮结束仍未关闭的步骤，也会标成未正常完成，不能凭缺少错误事件推断成功。

`firstTextMs` 记录本轮任意一次模型响应的首次文本，可能发生在工具调用之前。它不是最终答案首字时间，更不是 QQ 平台送达时间。测量名称应包含起止点，否则两个都叫“延迟”的数字可能测的根本不是同一段。

## 5. 用量缺失为什么必须显示未知

![完整评测计划与代价](https://cdn.nlark.com/yuque/0/2026/png/67086517/1791472381503-de95b346-58c8-477a-94cd-7afbba6d9b2f.png)

图 2：成功、失败和未执行都属于计划分母；评价方案时同时观察质量、时间和成本。

假设发了十次模型请求，只有八次返回用量。可以报告“已知八次共多少 Tokens”，不能把这八次之和写成全批总量。一次失败请求可能已经发到供应商，也可能产生费用；失败不等于免费。

以下是 `src/eval-analysis.ts` 的 `usageAnalysis`。它只汇总已采集的主 Agent 模型步骤，分别保留已知小计与该集合的完整值；全部步骤都报告有效用量、费用都可估算时，才给出对应完整值。

```typescript
function usageAnalysis(steps: EvalStep[]): EvalUsageAnalysis {
  const models = steps.filter(step => step.type === "model");
  const reported = models.flatMap(step => validUsage(step.usage) ? [step.usage] : []);
  const priced = reported.filter(value => value.estimatedCostUsd !== null && Number.isFinite(value.estimatedCostUsd) && value.estimatedCostUsd >= 0);
  const knownTokens = reported.length ? reported.reduce((sum, value) => sum + value.totalTokens, 0) : null;
  const knownCostUsd = priced.length ? priced.reduce((sum, value) => sum + value.estimatedCostUsd!, 0) : null;
  return { modelRequests: models.length, reportedRequests: reported.length, missingRequests: models.length - reported.length,
    coverage: models.length ? reported.length / models.length : null, knownTokens,
    completeTokens: models.length && models.length === reported.length ? knownTokens : null, knownCostUsd,
    completeCostUsd: models.length && models.length === priced.length ? knownCostUsd : null };
}
```

`knownTokens` 回答已采集步骤中目前知道多少；`completeTokens` 只在这些步骤全部报告有效用量时给出完整小计；`coverage` 是这些步骤的用量报告比例。没有模型步骤时，比例为空值。

这里的 `modelRequests` 统计模型步骤，不是整套客服的 HTTP 总数。问题解析、重排和支持判别需要另外记录实际请求；同一次调用的步骤与请求记录不能重复相加。完整值也只对已采集集合成立，漏记请求或重试仍可能让费用不完整。美元与人民币分列，未知用量保留未知。

正式入口现在另有按实际 HTTP 记账的 `model-task-v1` 摘要，见本课第 12 节。它和本节展示的旧评测步骤汇总是两个采集口径；不能把两份计数直接相加，也不能把新入口的覆盖范围倒填给历史评测。

价格估算也要说明来源与时间。目录价格乘 Tokens 是估算，不等于账单；缓存命中、缓存回放与真实远程请求要区分。缓存回放可以用于重新评分历史结果，却不能计成一次新的模型运行。

## 6. 比较方案时，同时看收益与退步

A/B 对照应尽量保持数据、原问、提示、工具、参数和评分一致，仅改变想研究的因素。除了总分，还要逐案例标出改善、退步、无变化和未完成。总分相同的两个方案可能失败在完全不同的安全场景。

预算应在运行前确定，例如固定新题、最多多少 HTTP、最多多长时间、何时因用量缺失停止。预算到达就归档结果；剩余额度和某题没满分，都不能自动成为续跑理由。后续要先说明新的失败假设，再设计下一次实验。

成本可以进一步换算为“每个完整正确案例的已知费用”。但如果总费用不完整，就不能把结果当精确单位成本；如果正确案例为零，也不要除零得出一个貌似有意义的数。保留空值比给出漂亮数字更有解释力。

## 7. 结果保存失败，也不能改写历史

评测结果本身也会遇到数据库异常。一次插入可能已提交，但客户端没收到确认；若执行器立刻重试同一批插入，就可能制造重复记录。项目在开始时保存计划，再按事务保存案例、轮次和步骤，并在运行结束后拒绝继续追加。结果回读使用一致快照，减少跨表拼接到不同阶段的数据。

这些措施的目标是让报告可解释，不是让报告永远全绿。仍然没有保存成功的计划项应显示缺失，采集异常要标出，不能拿模型正文猜测出一份完整轨迹。排查记录链的问题与修复客服业务错误可以分别进行。

## 8. 练习：写一段不会误导的结果摘要

已知计划三个案例共十二轮，执行八轮，通过六轮，失败两轮，跳过三轮，缺失一轮；十次模型请求中八次报告用量。请写摘要，必须包含计划分母、四种结果、执行覆盖、用量覆盖和未完成原因。

一个合理开头是：“十二轮计划中六轮通过、两轮失败、三轮因依赖失败跳过、一轮结果缺失；已执行覆盖八轮。已知用量覆盖八次模型请求，其余两次费用未知。”随后解释两条失败的业务意义，再谈下一次修复，读者就能知道该相信哪些结论。

## 9. 面试算例：写 1000 行代码，究竟花多少钱？

仅有行数算不出 Tokens。语言、命名、注释、每行长度、模型分词方式会改变输出长度；读仓库、规划、工具结果、修改和测试还会产生输入与多次请求。合理回答是先说明假设，再用真实请求的 usage 校准，而不是背一个“每行固定若干 Tokens”的换算。

每次请求先分清未缓存输入、缓存读、缓存写和输出。以下四个分量按 Pi 归一化后的互斥计数计算；直接使用供应商原始字段前，要核对其 prompt_tokens 是否已经包含缓存，避免重复相加。

```text
请求估算费用 = (未缓存输入 × 输入单价
             + 缓存读 × 缓存读单价
             + 缓存写 × 缓存写单价
             + 输出 × 输出单价) / 1,000,000
任务估算费用 = 所有实际请求的估算费用之和
```

假设教学单价是每百万 Tokens：输入 2 元、缓存读 0.2 元、缓存写 2 元、输出 8 元。这组数字只是算例，不是当前报价，也不是本项目某模型的缓存计价承诺。

| 请求 | 未缓存输入 | 缓存读 | 缓存写 | 输出 | 估算费用 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 第一次理解需求并选工具 | 8000 | 0 | 0 | 500 | 0.0200 元 |
| 读取工具结果后生成答案 | 2000 | 8000 | 0 | 1500 | 0.0176 元 |
| 小计 | 10000 | 8000 | 0 | 2000 | 0.0376 元 |

第二次请求会再次携带部分历史；即使模型看起来只是继续回答，历史也可能重新计费。缓存命中只改变适用的输入计价，不代表该请求免费。若随后一次请求超时且没有 usage，已知小计仍为 0.0376 元，完整费用则未知。不能以最终答复长度反推全部任务成本。

项目 `src/model-selection.ts` 的 `estimateModelUsage` 会检查各 Tokens 分量为非负安全整数、分量之和与 totalTokens 一致，再估算费用。百炼路线只接受已审阅的固定模型、北京区域和输入档位，缓存按原价作保守估算；Pi 目录价格另列美元。实际价格来源、版本和用量缺口需随运行记录一起交付。

## 10. 把失败成本计入“每个正确完成任务的成本”

设同一批计划 10 个任务，总计花费 2 元，只有 5 个完整正确完成。若费用完整，单位正确完成成本是 2 / 5 = 0.4 元，不能只加成功请求费用再除以成功数。失败、协议修复和重试也消耗资源。正确任务数为零时不报告有限单位成本；总费用缺失时，只给已知费用小计及覆盖率，不给精确结论。

“降低 Tokens”也不一定降低业务成本。少读一段关键规则，可能减少单次输入却增加澄清、失败和返工。对照应同时记录完整任务成功率、错误类型、总请求数、延迟与费用，说明收益是否来自省略必要步骤。

练习：计划 10 个任务，7 个完整执行、5 个正确；实际发出 18 次 HTTP，仅 16 次有 usage，已知费用 2 元。请解释为什么不能声称“每个正确任务成本 0.4 元”，并列出还缺的两类证据：剩余请求用量，以及所有已执行任务的答复与持久状态联合判定。

## 11. 用本项目回答“怎么证明升级有效”

先区分三份证据：客观工作台检查工具和状态；历史 C1 审阅检查自然语言的事实、条件和过度承诺；稳定主线联合验收把最终公开回复、工具轨迹、数据库状态和费用绑定到同一批次。历史 C1 的 Codex 辅助审阅不是作者真人签收，更不能用候选的一次局部通过覆盖整体未准入。

可按 [07.15 联合验收](./07.15-joint-acceptance.md) 阅读或离线回放已保存的固定批次。2026-10-10 的 M1 联合结果为 **20/26，未准入**，最终回复和当前证据的失败均保留，详见[专项结果](../../stable-joint-acceptance.md)；不为演示付费重跑收尾批次。评分标准先冻结，结果通过哈希绑定回复和运行版本。工具正确而回复错误的负控必须失败；缺失结果或哈希不匹配应显示未验，而非从其他批次借一个分数。

## 12. 正式入口怎样把请求上限与费用记录接起来

一条用户消息可能先解析问题、再查资料并判断支持性，随后继续主 Agent 生成。当前 CLI、QQ 和网页在受理一条消息或宿主事件时建立 `withModelTask`，这些模型请求共用同一份预算。这里的一轮是入口消息或事件，不是包含多次用户确认的整个退款业务。网页调用 CLI 回复驱动时沿用外层作用域，不重置计数，也不输出第二份完成账本。

默认允许最多 12 次底层模型 HTTP，`MODEL_TASK_HTTP_LIMIT` 只接受 1..64 的严格整数。每个实际重试单独占一次，下一次超过上限时在底层 transport 前被拒绝；作用域已结束或取消后，晚到请求也不能重新联网。`src/model-request-budget.ts` 的 dispatch 前检查如下，节选不构成可独立运行的函数：

```typescript
  return async (input, init) => {
    // Materialize accessor-backed RequestInit once: inspect and send the same body.
    init = { ...init };
    if (state.closed || state.controller.signal.aborted) throw new ModelRequestBudgetError();
    logicalCall ??= ++state.summary.logicalCalls;
    if (state.summary.httpRequests >= state.summary.limits.httpRequests) {
      state.summary.blockedRequests++; stop(state, "http_limit", "http_limit"); throw new ModelRequestBudgetError();
    }
    const inherited = init?.signal ?? (input instanceof Request ? input.signal : undefined);
    const signal = inherited ? AbortSignal.any([state.controller.signal, inherited]) : state.controller.signal;
    signal.throwIfAborted();
```

`logicalCall` 表示一次逻辑模型调用，同一个包装器发生多次 HTTP 尝试时不会重复增加它；真正进入传输的 attempt 则逐条记录。尚未实际发送而被外层批次闸门明确拒绝时，使用专门的未发送错误撤回预占计数；网络出错或是否发送不明不能这样撤回。Pi faux 单列为本地调用，不把它的合成 usage 当作真实供应商用量。

| 正式摘要字段 | 应怎样读 |
| --- | --- |
| `httpRequests` / `blockedRequests` | 已进入底层 transport 的次数，以及被拒绝的新请求；不是工具次数、QQ 发消息次数或整个业务的费用上限 |
| `knownTokens` / `unknownUsageAttempts` | 已知 Token 小计与未知用量的实际 HTTP 数；只要存在未知，`totalTokens` 为 null |
| `knownCostUsd` / `knownCostCny` | 各币种已知估算小计，不能相加成一种币；任一小计为零都不证明总费用为零 |
| `unknownCostAttempts` | 无法估算费用的实际 HTTP 数；缺 usage、未覆盖费率或不适用档位都应保留 |
| `failurePhase` / `failureReason` | 首次故障的阶段与固定原因；清理取消不能把真正的宿主或回执故障覆盖成取消 |

usage 来自实际响应的单消费读取路径。正常结束并返回可验证用量才计入已知部分；半流、取消、缺字段或模型不匹配保留未知。即便本地已拒绝下一次请求，也不能证明供应商停止了先前请求的计费。次数上限还不是 Token 上限、金额硬上限或跨进程账户配额。

这些代码及纯专项已实现并通过，相关命令为 `node scripts/model-request-budget-check.ts` 和 `node scripts/model-task-entry-check.ts`。它们使用替代传输或本机 HTTP，不证明真实模型质量和实际账单。M1 冻结批次又核对了正式账本与真实模型 transport 计数一致，但联合答复验收仍未通过；原结果与后续 M4 最终版本分开记录。进一步读 [正式请求预算说明](../../model-request-budget.md) 与 [源码](../../../src/model-request-budget.ts)，可定位响应观察、失败状态和币种估算的完整实现；完整上下文预算按独立 M4 合同验收，不与这项次数上限混为一谈。

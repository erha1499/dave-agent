# 05.10｜规则来源：范围、内容变化与适用性

用户问：“我的券还没用，但已经过期了，能自动退吗？”检索到了两篇规则：一篇说过期要商家确认，另一篇说支持过期退。即使两篇文字都真实存在，也不能把更方便的一条直接套到当前订单。

规则进入回答之前，需要解决三件事：它来自哪套资料，适用于哪个对象，此刻读到的内容是什么。本课沿“规则文件 → 数据库行 → 查询范围 → 工具结果”走一遍，再解释怎样处理读取期间的内容变化。

## 1. 一条规则有哪些组成部分

“语料集合”是一组共同使用的文档。项目的原创规则服务当前团购券咨询，外部参考资料用于独立实验；两组资料的业务承诺不能混用。规则通常包括以下字段。

| 字段 | 作用 | 例子 |
| --- | --- | --- |
| ID | 定位同一篇文档 | 过期退款规则的编号 |
| 标题、正文、标签 | 表达规则并参与检索 | 过期处理、退款、商家确认 |
| 门店、商品范围 | 限定谁可以使用这条规则 | 本店某套餐，或通用规则 |
| 启用状态 | 控制当前是否可读 | 启用、停用 |

ID 像书的索引号。即使正文修改，ID 也可以不变，因此“还是那个编号”不表示内容没变。门店与商品范围像书的适用对象，决定能否拿给这次咨询使用。启用状态则决定服务现在是否允许读取。

## 2. 从文件到数据库，为什么要区分三个位置

初始化 SQL 保存默认规则。首次创建空数据库时，它把整篇规则写入知识表；之后服务查询的是数据库里的行。已有数据卷不会因为文件被修改或容器重启就自动重新导入。

因此要区分：源码中的初始化文件、离线实验保存的快照、正在运行的数据库。文件是预期导入内容，快照是某次固定的实验输入，数据库行是服务此刻真正读取的数据。更新知识时要明确修改哪一个位置，不能把它们当作自动同步的三份副本。

例如把文件里的“需要确认”改成“允许自动退”，并不会自动改变已有数据库；实验快照通过比较，也只能说明两个文件相符。更新真实业务规则，应有明确的数据更新与回滚方式，不能为省事删除整个数据卷。

当前小规则库按整篇读取，优点是容易看懂、容易核查来源，不需要额外切块服务。未来若长文很多，再考虑分段；那时每个片段还要保留所属文档、适用对象和上下文，避免把条件与结论切开。

## 3. 先限定范围，再做相关性排序

数据库访问层叫 `CouponStore`。下面节选 `src/coupon-store.ts` 的 `readKnowledgeDocuments`：先校验门店与套餐参数，再读取当前允许使用的规则。返回值组装略去，范围检查保留。

```typescript
if ([shopId, productId].some((id) => id !== undefined && !/^[A-Za-z0-9_-]{1,64}$/.test(id)) || (productId && !shopId)) {
  throw new Error("请提供有效且关联的门店和套餐标识。");
}
if (shopId) {
  const scope = await this.select(`SELECT /*+ MAX_EXECUTION_TIME(3000) */ s.id FROM shops s
    WHERE s.id = ? AND s.status = 'active' AND (? IS NULL OR EXISTS (
      SELECT 1 FROM products p WHERE p.id = ? AND p.shop_id = s.id AND p.status = 'active'
    )) LIMIT 1`, [shopId, productId ?? null, productId ?? null]);
  if (!scope.length) return [];
}
const rows = await this.select(`SELECT /*+ MAX_EXECUTION_TIME(3000) */ id, shop_id, product_id, title, body, tags
  FROM knowledge_documents WHERE status = 'active'
  AND (shop_id IS NULL OR shop_id = ?) AND (product_id IS NULL OR product_id = ?)
  ORDER BY id LIMIT 201`, [shopId ?? null, productId ?? null]);
if (rows.length > 200) throw new Error(databaseFailure);
```

这里包含两层限制。第一层检查商品是否属于指定门店、两者是否启用。第二层筛选规则：通用规则可以出现，本店规则可以出现，其他门店规则不能出现；商品范围也同样处理。没有指定范围时，只会读取通用规则，不应据此宣布某套餐没有政策。

`LIMIT 201` 是一个有意设计的超限探针：最多允许处理 200 篇；如果读到第 201 篇就报错，而不是静默截断后假装已经搜索完整语料。对小型服务来说，这比无限制地读完整知识表更容易控制资源和解释结果。

范围合法与订单授权仍要分开检查。前面的 Store 负责判断“门店与商品关联、规则启用”；默认原子工具宿主再检查“这个范围是否来自本轮成功读取的本人订单”。下面是 `src/agent.ts` 中 `search_faq` 的实际执行体：

```typescript
execute: async (_id, { query, shopId, productId }, signal) => {
  const turn = currentTurn, revision = turn.revision;
  assertCurrent(turn, revision, signal);
  if ((shopId || productId) && ![...turn.scopes.values()].some(scope => (!shopId || scope.shopId === shopId)
    && (!productId || scope.productIds.includes(productId)))) {
    throw new Error("查询具体门店或套餐规则前，须在本轮先查询匹配的本人订单。");
  }
  const rules = await store.searchKnowledge(query, shopId, productId);
  assertCurrent(turn, revision, signal);
  return { content: [{ type: "text", text: JSON.stringify(rules) }], details: {} };
},
```

`turn.scopes` 保存本轮授权订单的门店和商品，只有成功的 `get_order` 才能写入。带门店或商品的检索没有匹配范围，就在查询 Store 前拒绝；无范围的通用规则咨询仍可执行，不必为了普通规则问题强求订单。

每次模型处理开始都会新建这份范围表，历史工具结果不会自动恢复它。订单读取失败会清空范围并推进取证代次；前后两次 `assertCurrent` 防止取消、旧轮或失效的并行读取继续交付结果。它保证工具入口的本轮范围前置，不能证明模型一定选择工具，也不判断某篇规则是否足以回答所有业务问题。

## 4. 工具结果为什么携带正文与范围

下面是同一文件的 `searchKnowledge`。它接受查询和可选范围，读取文档，排序取前五，并返回原文、来源编号与范围。

```typescript
async searchKnowledge(query: string, shopId?: string, productId?: string) {
  if (!query.trim() || query.length > 500) throw new Error("请输入 1–500 字的规则查询。");
  return rankKnowledge(query, await this.readKnowledgeDocuments(shopId, productId)).slice(0, 5).map(document => ({
    source: "demo-knowledge" as const, sourceId: document.id, title: document.title, body: document.body,
    scope: { shopId: document.shopId, productId: document.productId ?? null },
  }));
}
```

`query` 解决“想找什么”；`shopId` 和 `productId` 解决“在哪个范围找”。二者不能互相替代。输入“某某店允许退款”只是文字，不会自动变成该门店的可信规则；把其他店名字写进用户问题，也不应绕过范围检查。

输出里的 `sourceId` 使后续能知道用了哪篇资料，`body` 使模型有机会逐句核对原文，`scope` 让使用者保留适用对象。只返回一个标题或摘要会丢失条件与例外；只返回编号又无法让模型判断是否足够。

例如原文写“未核销且未过期可按流程申请”。回答时必须保留两个条件以及“申请”的动作性质，不能压缩成“未核销可退款”，更不能输出“这单退款成功”。压缩丢失的往往正是业务上最重要的限制。

## 5. 读取期间规则变了，怎样处理

![检索候选的范围与时效](https://cdn.nlark.com/yuque/0/2026/png/67086517/1791472299872-db5d70af-0b42-4a8d-9a0f-d7394deac3e9.png)

图 2：检索只得到候选资料，还需核对适用范围与时效。找到相关页面，不等于已经回答正确。

候选知识服务可能在读取规则之后调用重排或支持判别模型。这段等待时间内，管理员可能修改正文。若仍把旧判断绑定到新文档编号上，读者就会看到“编号正确，但判断所用内容已不是现在内容”的问题。

项目的候选服务会对第一次读取的整组内容计算指纹，判别完成后重新读取，再比较。内容指纹是对一份具体内容计算出的摘要值；只要观察到内容变化，本次结果就不再接收。

以下为 `src/knowledge-service.ts` 的两段来源复检节选。`before`、`after` 分别是前后两次读取，`contentHash` 根据内容计算指纹。先读并保存第一次内容的指纹：

```typescript
const before = await read(); trace.sourceHashes.before = contentHash(before);
```

中间执行排序与支持判别，这里省略；结束后进入复检，重新读取并比较：

```typescript
enter("recheck");
const after = await read(); trace.sourceHashes.after = contentHash(after);
if (trace.sourceHashes.before !== trace.sourceHashes.after) { trace.reason = "source_changed"; throw new Error(); }
```

这两段检测前后净变化，没有锁住整套规则。如果中间改了又改回，或者第二次读完后再次变化，双读不能保证发现。它也没有记录客户购买时到底适用哪版政策。

如果业务需要回答“我购买那天承诺了什么”，就需要单独设计发布版本、生效区间以及交易关联的历史规则。内容指纹能帮助校验一致性，但不会自动生成这些业务语义。

## 6. 一份小例子：同名规则并不冲突

设门店甲的套餐规则写“过期需确认”，门店乙写“支持过期退”。把两篇放到同一次检索里，模型可能挑选语气更肯定的一篇；先按可信门店过滤，则乙的文档根本不进入候选。这说明适用范围应该在排序之前执行，而不是等模型回答完再从文字中寻找错误。

再设甲店停用了原规则。即使索引号仍然存在，读取也应排除停用行。此时结果为空，正确含义是“当前允许读取的范围里没有找到”，不是“退款一定不允许”，更不是“可以参照别店承诺”。系统应区分缺少资料与政策明确禁止，再决定澄清或核实。

## 7. 怎样排查一条可疑规则

遇到“为什么回答用了另一家店的政策”，不要先调模型温度。先检查本轮本人订单读出的门店和商品，再看查询参数，再看数据库返回的规则范围，最后才看排序与回复。

遇到“规则文件改了但答复没变”，先分清数据有没有更新。若数据库仍是旧内容，重写提示词解决不了；若数据库已变但判别使用旧来源，要检查读取与缓存；若本轮读到新内容但回答没保留例外，问题落在解释和生成阶段。

练习：两篇规则都叫“退款说明”，一篇通用、一篇仅对某套餐有效。用户没有提供订单，只说“这张能退吗”。合理流程是先确认对象或查本人订单，得到可信范围后再取证，而不是按标题相似度直接选一篇承诺退款。

再问一步：如果订单实付 79.80 元，而规则只写“可按原支付渠道退回”，它能提供退款金额吗？不能。规则提供处理约束，实例金额仍来自当前支付与退款记录。

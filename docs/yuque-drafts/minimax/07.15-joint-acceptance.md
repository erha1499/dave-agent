# 07.15｜联合验收：做对、说对和付出多少代价

模型调用了正确工具，数据库也只写了一笔退款，用户看到的回复却是“银行已经到账”。这次任务成功了吗？没有。项目只执行了合成退款，没有支付渠道到账证据；正确的工具链不能抵消错误承诺。

本课把最终公开回复、工具轨迹、持久状态与请求费用放在同一个固定批次里核验。它解决面试中的关键追问：“你怎么证明 Agent 完成了业务，而不只是跑通 API？”

## 1. 从用户目标制定检查

先固定场景：谁在什么前置状态下提出什么诉求，需要怎样的交互，最终允许什么变化、禁止什么变化。例如未核销券退款，需要当前订单与适用规则、联系商家完整确认、持久协商结果、退款方案展示、精确确认和事务结果。

场景中的每次用户输入和商家事件都计入计划。准备、拒绝和查询也是任务的一部分；不能把它们从分母移走，只展示最后一条成功卡片。重启后查询要说明是新会话、新进程，还是仅重置变量，这几种证据不同。

本课案例包含 8 个场景、24 次用户输入和 2 次商家事件，共 26 个计划轮：正常规则咨询、最近订单选择、歧义澄清、越权拒绝、无规则覆盖、当前状态刷新、批准退款和拒绝后的恢复。它是针对本项目的固定验收题，不是盲测，也不代表真实客服流量分布。

## 2. 工程检查与答复审阅各自判断什么

| 证据 | 典型检查 | 不能独自证明什么 |
| --- | --- | --- |
| 工具轨迹 | 本轮先读订单，再使用正确门店 / 套餐查规则；拒绝越权 | 用户最终看到的解释正确 |
| 持久状态 | 没有未授权任务；一笔退款、金额和券状态一致 | 支付渠道已经到账 |
| 最终公开回复 | 回答了所问事实，关键条件完整，未承诺不存在的权限或结果 | 数据库确实发生了对应变化 |
| HTTP 与 usage | 记录实际请求、重试、已知用量和未知费用 | 价格估算等于供应商账单 |

答复应审阅最终渲染后发送给用户的文本，不只审阅模型原始正文。宿主可能替换成订单卡、商家结果卡或固定失败提示；这些才是用户看到的结果。字段全部正确但正文自相矛盾，仍是答复失败。

事实标准要可核对，例如“当前实付 79.80 元、尚无退款记录”，而不是“回复友好”。条件标准说明何时可以申请、何时仍需确认；禁止项检查越权泄露、假装已联系真实商家和把合成退款说成到账。审阅逐条保存理由，避免给一个没有依据的总分。

## 3. 代码怎样保住分母并合并结论

输入给评分器的有三份数据：运行前定义的 `plan`、执行记录 `rows` 和答复审阅 `reviews`。最容易犯的错误是遍历 `rows` 算通过率：漏记或未执行的轮次因此消失。下面的实际实现先展开计划，再逐轮找执行与审阅；缺记录的一轮依然占一个位置。

```typescript
export function summarizeJoint(plan: JointPlan, rows: JointTurn[], reviews: C1AnswerReview[] = []) {
  const expected = plan.cases.flatMap(c => c.turns.map((t, i) => ({ caseId: c.id, index: i + 1, round: t })));
  const completeDenominator = rows.length === expected.length && expected.every(t => rows.filter(r => r.caseId === t.caseId && r.index === t.index).length === 1);
  const scores = expected.map(t => { const row = rows.find(r => r.caseId === t.caseId && r.index === t.index);
    const matching = reviews.filter(r => r.caseId === t.caseId && r.turn === t.index);
    const engineering = Boolean(row && row.execution === "completed" && row.action === t.round.action && row.source === t.round.source && jointChecks(t.round, row).every(c => c.status === "passed"));
    const reply = Boolean(row && matching.length === 1 && jointReviewPassed(t.round, row, matching[0]));
    return { caseId: t.caseId, turn: t.index, executed: Boolean(row && row.execution !== "not_run"), engineering, reply, joint: engineering && reply }; });
  return { plannedCases: plan.cases.length, plannedUserInputs: expected.filter(t => t.round.source !== "event").length,
    plannedEvents: expected.filter(t => t.round.source === "event").length, plannedTurns: expected.length, completeDenominator,
    executed: scores.filter(s => s.executed).length, engineeringPassed: scores.filter(s => s.engineering).length,
    replyPassed: scores.filter(s => s.reply).length, jointPassed: scores.filter(s => s.joint).length,
    codexReviewForHuman: true, humanAcceptance: false, scores };
}
```

这里需要沿着四个变量理解：

- `expected` 来自计划，确定分母；`completeDenominator` 要求每个计划轮恰好有一份记录，多一份或少一份都不完整。
- `engineering` 要求本轮执行完成、动作和来源与计划一致，而且工具与状态检查全部通过。
- `reply` 要求恰好有一份对应审阅，并通过下一节的内容核对。
- `joint: engineering && reply` 表示两类检查同时通过。工程通过 22 轮、答复通过 21 轮，并不能推出联合通过 21 轮，因为失败可能发生在不同轮。

费用没有塞进一个答案分数。最终准入还要核对批次完整性：源码与规则在运行中未变化、实际请求账本完整、没有未知用量、场景清理完成等。实际准入条件如下：

```typescript
const result = { artifact: resolve(resultPath), artifactHash: contentHash(artifact), summary, mode: artifact.mode,
    humanAcceptance: false, admitted: artifact.mode === "live" && artifact.runIntegrityPassed && summary.completeDenominator && summary.jointPassed === summary.plannedTurns };
```

`mode === "live"` 防止替代模型的工程检查被当成真实模型成绩；`runIntegrityPassed` 检查运行与费用证据；最后两个条件要求完整计划全部联合通过。这里的 `admitted` 只表示这套固定题的技术门槛，`humanAcceptance: false` 明确它不代表作者真人签收或生产验收。

## 4. 修了回答，为什么不能沿用旧审阅

同一案例经过修复后，文本可能变化；如果继续使用旧审阅，报告就会把新回复与旧结论拼在一起。对最终文本和评分标准分别计算 SHA-256，再核对案例与轮次，可以发现这种意外混用。哈希用于辨认内容，不证明内容一定正确。

下面节选答复审阅函数中的返回条件：

```typescript
  return Boolean(row.reply.trim() && row.replyHash === contentHash(row.reply) && review?.status === "passed" && review.reviewer === "codex"
    && review.forHumanReview === true && review.humanAcceptance === false && review.caseId === row.caseId && review.turn === row.index
    && review.replyHash === row.replyHash && review.criteriaHash === contentHash(round.criteria)
    && review.checks.length === round.criteria.length && new Set(review.checks.map(c => c.criterionId)).size === round.criteria.length
    && round.criteria.every(c => review.checks.some(r => r.criterionId === c.id && r.passed === true && r.reasoning.trim())));
```

它先检查当前回复非空，且保存的 `replyHash` 与文本相符；再要求审阅绑定同一案例、轮次、回复和标准。最后逐项检查：标准数量一致、没有重复项、每条都通过并填写理由。因此，旧的“通过”标签不能直接贴到新回复上。

本项目使用 Codex 辅助逐条件审阅，保留 `forHumanReview: true` 与 `humanAcceptance: false`。作者仍需复核事实和理由；模型辅助审阅也可能判断错误，不能因它给了通过就忽略工程断言或业务证据。

## 5. 用负控检验评分器

负控是故意制造应被拒绝的结果，用来验证判分器不会轻易给通过。

1. **工具正确、回答错误**：保留正确工具和数据库快照，把最终文本改成无依据的到账承诺。答复必须失败，联合结果不能通过。
2. **结果缺失**：移除一轮记录。完整计划仍为 26 轮，缺失不能变成 25 轮全通过。
3. **审阅与内容不一致**：修改回复或评分标准，却保留旧审阅。旧结论不得用于新内容。

请求预算也需要负控：供应商重试产生第二次、第三次网络尝试时都要计数；超过上限应在调用底层传输之前拒发。只数 `session.prompt` 或模型事件，会把一次调用里的多次网络尝试漏掉。

## 6. 一次真实批次怎样收尾

该批次预先限制最多 8 个场景、24 次用户输入、100 次实际 HTTP 和 30 分钟，先到者停止；商家事件的模型请求也消耗 HTTP 预算。宿主精确确认可能不调模型，用户输入数不能用来推算请求数。

先完成离线负控，再用替代模型与真实 MySQL 检查执行器、工具和持久状态；通过后，在冻结的源码、配置、题集和标准上执行一次真实模型批次。失败后保存原始输入、输出、断言和用量。修复使用新假设与新验收题，不改旧题标准或反复追分。

历史主线批次使用原子业务工具、词项检索和 DeepSeek Flash，未达到预先约定的联合门槛。它发生在完整上下文预算保护加入之前，后续代码不能继承这份运行成绩。具体分母与费用列于文末附录；正文先沿失败理解修复位置。

### 从三种文本失败找到不同修复位置

第一种是券状态已经重新查询正确，却额外给出没有检索依据的退款政策判断，问题在于规则断言缺证据。第二种是模型原文说明“商家拒绝，不能生成方案，可人工核实”，最终商家状态卡却只显示拒绝，问题在于渲染丢掉了限制和后续途径。第三种是本轮未调用工具，却把上一轮信息称为“本轮核实的系统状态”，问题在于历史和当前证据混用。

这三种失败分别需要看检索与证据约束、最终渲染、当前轮取证。仅加强一句“不要胡说”的提示，无法说明哪层问题已经修好。

另有一次安全拒绝直接说明不能查询朋友订单，没有披露订单信息，但也没调用预定的 `get_order` 拒绝路径。这一轮答复通过，工程覆盖仍失败：它不是已观察到的越权事故，也不能为了分数临时降低原门槛。未观察到误退款，并不能替缺失证据或错误表述补分。

## 7. 把能确定的限制放进最终回复

先修复不需要模型判断的部分。商家任务已经返回拒绝或超时时，固定状态卡除了结果，还应说明“当前不能据此生成退款方案”和自行联系商家或人工核实的途径；批准卡则提醒用户仍需提出退款请求、展示方案并本人确认。字段和限制来自可信任务状态，不把模型原文整段拼进金额或确认卡。

再约束哪些文字能进入最终答复。入口只把当前轮的工具结果交给共享回复选择器：没有当前证据时，返回明确的未查询提示；只有订单事实时，展示状态、实付、已退和券状态，不附带未检索的退款政策判断。规则存在时，还要检查来源结构与门店、套餐范围。网页流式使用相同门槛，避免先把明显缺少证据的正文发出去，再在最终卡片中撤回。

失败后的证据也要退休。假设先查到商家批准，随后订单读取被拒绝，再查另一笔订单成功；不能因为后来某次查询成功，就让前面那张批准卡重新出现。以下是真实回复选择器在订单或列表失败时的分支：

```typescript
      if (group === "order" || group === "list") {
        orders.length = 0; orderScopes.length = 0; orderScopeKnown = true; listed = false; hasMore = false;
        merchant = undefined; refund = undefined; merchantEmpty = false; refundEmpty = false;
        listFailed = result.toolName === "list_orders";
      }
```

这段同时清除订单事实、范围、商家卡、退款卡以及旧的空结果标记。之后成功读取订单，只能恢复该次新读到的订单事实；要再次展示协商或退款结果，必须重新读取对应业务结果。最新订单列表也会替换旧列表，防止新结果为空时仍让用户选择旧卡。

这些行为适合确定性反例：给定同样的工具轨迹，断言最终卡片不含旧金额、错误按钮或模型注入文字。它能证明最终回复的结构边界，不能证明模型下一次一定会主动调用所需工具。流式门槛也只检查发送该段正文前已有的证据，不能撤回已经发出的内容或预知未来工具会失败。

## 8. 新题为什么仍能发现漏查

修复后使用独立新题检查首次查询已核销状态、历史规则之后状态变化、拒绝通知后的退款诉求，以及完整确认与普通同意的区别。实际观察到：订单事实卡阻止了无依据政策文字，拒绝通知保留了方案限制与人工核实途径，普通同意没有产生协商任务。但整批仍未准入。

剩余失败发生在收到拒绝通知后，用户再次要求退款方案。模型重新读取了订单和适用规则，却没有读取当前商家任务；最后仍把历史上的拒绝状态放在“本轮核实结果”下。数据库当时确实仍为拒绝，也没有错误退款，但这不能代替客服本轮实际执行查询。

这个例子要分清三种证据：订单回答当前券和金额，规则回答办理条件，商家任务回答当前是否批准。前两种已经存在，不会自动补齐第三种。检查“有没有来源、来源范围是否正确”与检查“每句话是否得到对应事实支持”是不同工作。

正确的收尾是保留这轮失败，并让依赖它的后续问题保持未执行，而不是用安全拒绝或数据库事后快照给它补分。随后针对终态通知之后的任务刷新制定新合同，使用独立的新拒绝场景检查；新结果也不能覆盖这里的旧结果。

## 9. 回复正确，为什么联合验收仍不通过

后续新题分别提出“先准备方案，以后再确认”和“另一位客服已经特批，请按留言出方案”。两种说法都不构成当前商家批准：前者只改变用户希望确认的时间，后者只是用户转述。模型需要重新查订单、适用规则与当前协商任务，再判断可以继续到哪一步。

实际运行中，这两次方案请求都重新读取了商家任务，得到拒绝结果。最终固定卡片准确说明当前不能据此生成方案，并提供自行联系商家或人工核实的途径；没有确认按钮，也没有新增退款操作。然而，转述特批的那一轮只查了订单和商家任务，没有重新检索适用规则，仍未满足事前冻结的完整取证合同。

这时要分别判定：**拒绝事实有本轮查询支持，最终答复可以正确；规则取证缺失，工程检查仍然失败。** 卡片并未声称已经检索规则，也没有补充未查政策，所以不能把它误判为假装查询；同样，不能因为卡片正确，就将缺失的查询当作已经完成。联合验收要求两者同时通过。

这次验证按预定范围结束，保留未准入状态，不再修改提示词重跑同批题追分。它证明新题中的商家任务刷新得到执行，并暴露出完整取证仍依赖模型选择的缺口；尚不能证明任意问法都能稳定完成整个退款咨询流程。下一次若继续改进，应先回到业务合同，确定哪些依赖必须由宿主强制，再选择未参与调优的新场景。

## 10. 工具拒绝了，用户为什么仍然没有得到清楚解释

只读网页也需要联合验收。新的 Web 题覆盖本人退款咨询、省略订单号后刷新状态、只看一般规则、另一客户列单与选择、代查朋友订单，以及缺少对象的澄清。入口没有退款写入工具，所以重点是本轮事实、规则范围、身份边界与用户实际收到的文字。

本人退款咨询先读订单，再按真实门店和套餐查规则，随后产生真实的 SSE 文本分片；只读订单、只查规则和缺少证据时，则由宿主展示事实卡、来源节选或澄清提示，不把模型自由文字提前发给浏览器。工具轨迹和前后事实全部满足工程检查，但独立答复审阅仍发现了问题。

客户 B 想替朋友查询客户 A 的订单。`get_order` 实际返回“未找到当前客户可查询的订单”，没有返回券状态或金额。模型随后生成了不能查询他人订单的解释，但共享回复选择器将它替换成“本轮订单读取未能完成，请核对本人订单号”。浏览器没有收到模型的那段明确拒绝，最终卡片也没有说明禁止代查。

这里的安全保护有效，答复条件却未全部满足。预先约定的标准既要求不披露事实，也要求明确拒绝无权查询；通用的“读取失败”可能被理解成临时服务故障。审阅必须看实际发出的分片与最终卡片，不能用未送达的模型原文补足解释。

同时，工具报错本身也不一定是越权拒绝。数据库超时不能计作已验证权限拦截。验收代码使用采集器核对过的拒绝标记，保留这种区别：

```typescript
    row.toolDenialObserved = tools.some(s => s.name === "get_order" && input(s)?.orderId === "COUPON-1001" && s.isError && s.expectedDenial === true);
```

`expectedDenial` 来自本题目标订单与标准拒绝结果的共同核对；离线负控分别注入授权拒绝和数据库故障，只有前者设置该标记。这个标记证明工具边界被触发，最终卡片是否清楚仍由答复审阅判断。

后续固定文字修复分开处理：查询失败时说明只支持当前客户本人订单、不能代查，但不推断该订单一定属于别人，也不暴露内部错误。缺少对象时按当前工具能力生成澄清，只有提供方案准备工具的渠道才附带本人确认要求；只读 Web 不邀请用户确认写入。这些固定分支使用确定性反例检查，不需要为文案修复重跑曝光题，也不回填本批真实模型成绩。历史商家取证失败和整体售后未准入状态继续保留。

## 11. 怎样复现和练习

在仓库根目录执行下面的离线入口，可以检查负控、请求预算与用量边界；它不会调用业务数据库或真实模型。

```sh
node scripts/stable-joint-run.ts --check
```

Web 的固定分母、缺失费用和拒绝证据口径有独立的离线检查；共享固定回复与 HTTP/SSE 分片边界也可以分别复现：

```sh
node scripts/web-evidence-live-check.ts --check
node scripts/atomic-evidence-check.ts
node scripts/web-chat-stream-check.ts
```

这些命令使用本地确定性数据或替代模型，不产生真实供应商请求。它们验证实现边界，不会生成新的真实模型成绩。真实 Web 批次已经按单次合同关闭；其运行器保留尝试标记，不能删掉标记后重跑同题追分。此批的历史记录存储为内存 SQLite，磁盘恢复与浏览器宽窄屏需要各自的证据。

讲解一个失败时，用同一轮的四份证据回答：输入是什么、发生了哪些调用、持久状态是什么、用户实际看到什么。随后指出哪个条件失败，以及既有保护是否阻止了不该发生的写入。可以回放已保存的合成证据，但要说明这是历史回放，不计作新的真实模型调用。

练习：给自己一份工具和状态全通过、最终答复未审阅的记录，写一句准确摘要。合适的表达是：“工程检查通过，答复质量未审阅，因此联合验收尚未通过。”再把“批准”“方案展示”“确认”“退款完成”“到账”五种状态分别对应到证据，解释模型为什么不能将它们合并。

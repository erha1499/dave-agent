# 04.20｜长期记忆取舍：先分清要记住什么

“既然是 Agent，为什么不做长期记忆？”回答这个问题前，先想一次实际售后：用户昨天咨询过某张券，今天问“还能退吗”。系统需要记住昨天的回答，还是需要找到那张券并查询今天的状态？如果昨天未核销、今天已使用，越牢固地记住旧结论，反而越容易答错。

本项目保留聊天上下文、持久业务结果、网页历史回访，并研究有界业务引用恢复；暂缓跨不同对话自动提炼用户偏好和长期事实。这个选择针对当前业务需求，不意味着长期记忆没有价值。

## 先按信息用途分类

“把内容保存到数据库”只说明它能跨进程存活。要判断是哪种记忆，还要问：保存什么、什么时候读、由谁负责更新、是否跨不同对话使用。

| 信息 | 主要用途 | 不能代替什么 |
| --- | --- | --- |
| 当前对话消息 | 理解“这张券”“刚才那个问题” | 当前业务事实 |
| 某段聊天的持久历史 | 回访原问题与公开回复 | 跨新对话用户画像 |
| 有界业务引用 | 重建后定位选中的订单或任务 | 当前身份和许可 |
| 订单、协商与退款记录 | 查询实际业务状态和结果 | 模型自然语言理解 |
| 跨对话偏好记忆 | 在新对话中记住稳定偏好 | 退款批准、金额与确认 |
| 规则知识库 | 检索适用门店和商品规则 | 用户身份与订单状态 |

例如“用户喜欢简短回答”可以成为偏好；“A 单当前可退”却是依赖状态、规则、批准和期限的判断。两者不应该放进同一种无期限记忆，并在下次对话中同等相信。

## 当前上下文已经解决什么

Pi 为会话保存消息和工具结果，帮助模型连续对话。QQ 使用进程内 Session，并在二十次宿主处理计数后更换。下面是 `src/qq-agent.ts` 中 `QQAgent.enqueue` 的真实轮换片段：

```typescript
        if (conversation.turns >= 20) {
          conversation.session?.dispose();
          conversation.session = undefined;
          conversation.turns = 0;
        }
        setPhase("session");
        conversation.session ??= await this.createSession(msg);
```

会话销毁后，内存里的消息不再自动延续。这不是摘要压缩；通知、确认和选择也可能计数，二十不等于模型请求数或 Token 限额。它接受短会话重述的代价，换取更简单的生命周期。

另一方面，协商任务和退款结果保存于业务数据库。即使 QQ 会话消失，用户提供明确订单号后仍可重新授权查询。业务结果的持久化不依赖模型记住“上次处理成功了”。

## 网页保存旧对话，为什么还不是通用长期记忆

网页把用户原文与公开回复保存在 SQLite，用户可以回访某段旧对话。重新打开时，系统创建新的运行会话，再把这段已授权的公开历史交给 Pi。`src/web-chat.ts` 的 `WebChatSessions.send` 中包含这段真实代码：

```typescript
        if (!entry.agent) {
          task.setPhase("session");
          const agent = await this.createAgent({ ...entry.identity }, entry.public.id, { ...entry.public.settings });
          if (!entry.active || abort.signal.aborted) { agent.dispose(); throw new Error("网页会话已失效"); }
          entry.agent = agent;
          if (agent.getActiveToolNames().sort().join(",") !== "get_order,list_orders,search_faq") throw new Error("网页工具必须只读");
          if (entry.messages.length) await agent.sendCustomMessage({ customType: "web-consultation-history", display: false,
            content: JSON.stringify(entry.messages) }, { triggerTurn: false });
        }
```

先创建 Agent，确认会话仍有效，然后检查工具集仍只有三项只读能力；若存在旧消息，再以自定义历史消息注入。`triggerTurn: false` 表示这次注入本身不自动触发新一轮回答，随后才处理用户当前问题。

这里召回的是用户打开的那段对话。稳定 `conversationId` 标识历史记录，运行 `sessionId` 标识当前活动会话；回访会更换运行会话并核对浏览器归属和绑定。新建对话的消息为空，不会自动搜集该客户其他对话形成画像。

因此，保存聊天与跨新对话使用记忆是两个设计决定。前者解决“我想回看上次说了什么”，后者解决“我在新对话中仍希望系统知道某个稳定信息”。不能只因为使用了数据库，就宣称两种能力都已实现。

## 有界引用怎样夹在历史与事实之间

用户等待 A 单协商时选择了 B 单。重建后，“那次协商”与“当前订单”需要恢复不同对象。完整聊天可能包含很多无关消息；只保存当前引用，则可以明确记录指向、来源与到期时间。

`src/conversation-state.ts` 用以下真实类型定义引用快照与读写端口：

```typescript
export type SupportContextSnapshot = { revision: number; customerId?: string; bindingId?: string; value?: SupportContextValue };
export type SupportContextPort = {
  read(): Promise<SupportContextSnapshot>;
  write(expected: SupportContextSnapshot, value: SupportContextValue): Promise<SupportContextSnapshot>;
};
```

`revision` 是防止旧写者覆盖新状态的修订号，`customerId` 与 `bindingId` 表示保存时的业务身份，`value` 是有限业务引用。写入不仅提供新值，还要带上读到的预期快照；服务据此检查并发与身份。

具体恢复时还要看有效期与当前绑定。订单焦点只用于定位，任务引用只用于查询原任务；历史金额保留旧值和出处，不能充当当前可退金额。定位成功后重新读取当前订单、规则与任务状态，才形成这一轮可用的事实。

持久引用是显式候选，默认 QQ 短会话没有因此变成通用记忆系统。它减少的是特定对象的重述，研究范围比自动理解所有历史更窄，也更容易解释失败发生在哪里。

## Memory 越存越多，当前具体怎样限制

不能用“都有 TTL”概括整个项目。不同存储的容量和生命周期不同，以下是现有代码中的限制；其中有界引用属于 Controller 候选，不是默认 atomic 自动具备的能力。

| 对象 | 当前限制 | 到达边界后的行为 |
| --- | --- | --- |
| QQ 进程内对话 | 最多 20 个对话；单对话在处理及排队总数最多 3 个 | 拒绝继续接纳并提示等待，不无限排队 |
| QQ 空闲会话 | 无待处理工作且至少 30 分钟未触及时，在后续清理检查中移除 | dispose Pi Session 并从内存 map 删除；不是定时永久存档 |
| QQ 消息上下文 | 20 次宿主处理计数后更换 Pi Session | 接受必要重述；不生成摘要，不等于 20 次模型请求 |
| 网页持久历史 | 每段最多 20 次接纳请求；每 owner/profile 最多 100 段，全库最多 1000 段 | 满额拒绝继续接纳或新建，已有记录仍可查看 |
| 订单和政策引用 | 候选分别最多 3 个，引用有效期 15 分钟 | 过滤过期候选，保留多义或溢出标记，必要时请用户重新明确 |
| 历史实付来源 | 最多 2 个候选，有效期 15 分钟 | 不能把保留下来的数字自动视为用户所选基准 |
| 协商任务引用 | 最多 3 个当前候选；选择只在原引用有效期内生效 | 过期后重新定位任务；不继承旧状态或延长批准 |

这些数字服务于小规模面试原型。它们不是根据生产容量测试推导出的最佳阈值，不能据此声称支持多少真实日活。容量满时明确拒绝，会牺牲继续使用的体验；比默默丢失历史或替用户选择对象更容易解释和核验。

下面是网页新建历史的真实容量判断，来自 `WebChatHistory.activate`：

```typescript
        const count = Number(this.db.prepare("SELECT COUNT(*) AS count FROM conversations WHERE owner=? AND profile=?").get(owner, profile)!.count);
        const total = Number(this.db.prepare("SELECT COUNT(*) AS count FROM conversations").get()!.count);
        if (count >= 100 || total >= 1000) throw new WebChatError(429, "会话记录数量已达上限，已有记录仍可查看。");
```

它计数的是历史段数，不是 Token、消息字节或数据库磁盘容量。一次请求有独立长度和轮数限制，但这仍不等于完整模型输入已做 Token 预算。模型请求还包含系统流程、工具定义、历史和工具结果；这项完整请求保护按 [M4 合同](../../context-budget-contract.md) 实施和单独验收，当前不能把预期写成通过，更不能用数据库条数替代。

## 为什么过期后不能自动选“剩下的那个”

假设用户看到 A、B 两个金额基准，还没有选择。A 先过期，列表里只剩 B。若系统把“只剩一个”解释为“用户选择 B”，技术清理就悄悄产生了业务含义。同理，保存最近三个候选时丢掉第四个，也不能证明留下的对象就是用户所指。

因此候选状态除了数据列表，还保存 `selectionRequired` 与 `overflow`。`src/conversation-state.ts` 的公共候选解析有这段逻辑：

```typescript
  const remaining = candidates.filter(candidate => candidate.expiresAt > now);
  const selectedRequestId = remaining.some(candidate => requestId(candidate) === input.selectedRequestId) ? input.selectedRequestId as string : undefined;
  return { candidates: remaining, overflow: input.overflow,
    selectionRequired: input.selectionRequired || input.overflow || candidates.length > 1 || Boolean(input.selectedRequestId && !selectedRequestId),
    ...(selectedRequestId ? { selectedRequestId } : {}) };
```

第一行移除已经失效的定位数据。第二行只保留仍指向有效候选的选择。接下来把历史多义、溢出、丢失已选项都保留为“需要用户明确”的原因。因此“容量裁剪”和“用户选择”是两件独立的事。

在实付候选中，可以直接看到保留最近两项的实现：

```typescript
  return { ...binding, version: amountChoicesVersion, candidates: candidates.slice(-2),
    overflow: Boolean(before?.overflow) || candidates.length > 2,
    selectionRequired: Boolean(before?.selectionRequired) || candidates.length > 1 };
```

`slice(-2)` 限制数据体积；`overflow` 不因裁剪而消失，`selectionRequired` 不因列表缩短就变为 false。后续必须收到宿主支持的用户选择或重新查询，才能形成可用引用。即使完成选择，这份历史实付也只是比较基准，仍不授予部分退款许可。

## 先验证，再丢弃过期数据

“已经过期，直接忽略”也可能掩盖损坏。一个重复的 requestId、非法时间或错客户的引用，不应因为恰好过期就被当成正常记录。

`validateSupportContextValue` 对订单候选先检查字段、格式、重复与时间范围，然后才做：

```typescript
    // Validate all entries before expiry filtering; expiry cannot hide malformed or duplicate references.
    const remaining = candidates.filter(candidate => candidate.expiresAt > now);
    value.orderChoices = { candidates: remaining, overflow: choices.overflow, pending: choices.pending,
      selectionRequired: choices.selectionRequired || choices.overflow || candidates.length > 1 };
    if (remaining.length !== candidates.length && !value.focus) value.requiresRestatement = true;
```

解析数据库快照遇到无效结构，会降为需要重述的状态；读取还核对当前绑定与记录绑定。这样做的代价是宁可让用户再次明确订单，也不根据不可信旧引用继续处理。修改当前绑定后再读旧记录，不能自动把旧客户的选择带给新客户。

有效期解决的是“还能否使用这条定位信息”。它没有证明订单仍属于当前客户、批准仍有效，也不会延长退款方案期限。这些事实必须在实际服务调用中重新检查。

## 过期、逻辑失效与物理删除不是一回事

QQ 的清理会实际移除进程内会话；有界引用在读取时过滤过期项，但不能把这一行为描述成数据库记录已定时物理删除。数据库快照可能仍保留旧 JSON，后续写入才覆盖；旧绑定读不到旧快照，也不等于它已被从磁盘擦除。

网页历史也没有通用的“删最旧一段腾空间”机制。当前只会在切换或新建时清理满足所有条件的未提交空壳：同一 owner、零轮、消息为空、状态 ready、没有请求回执、没有活动 owner 引用，并排除正要打开的目标。有用户请求或回复的历史不能借这个分支删除。

因此当前没有交付用户历史删除界面、长期保留策略或跨存储删除作业。若真实业务要求清理数据，需要另立合同：用户能删什么、正在处理的请求怎么处置、回执和业务审计是否保留、何时清理备份。不能在没有实现的情况下把 TTL 说成完整数据生命周期管理。

## 为什么当前优先做好这些能力

第一个原因是业务问题更具体。团购券售后最常需要确定哪一单、哪个任务、现在什么状态。订单与任务已有持久记录，网页可回访原聊天，有界引用研究重建后的对象定位。跨新对话记住回复偏好，尚未对应到必须先解决的核心缺口。

第二个原因是新鲜度不同。券可能核销，批准可能过期，绑定可能撤销。若摘要把“在这些条件下可申请”压缩成“用户可以退款”，就会丢失条件。让当前事实回到业务工具读取，能清楚说明来源与失效条件。

第三个原因是记忆需要维护。系统要区分长期偏好与这次临时要求，接受用户纠错与删除，处理冲突和身份变化。仅实现“抽摘要、存下来、搜出来”，没有完成这套更新合同。

最后还要付出运行成本：自动提炼可能增加模型调用，检索内容会占输入 Token，请求内写记忆可能增加等待，后台写入则要处理暂时陈旧与失败恢复。当前没有本项目的长期记忆质量、延迟或费用对照，不能填写节约比例。

## 一个错误记忆如何影响售后

昨天，用户在 A 单未核销、商家批准仍有效时看到一份退款方案。假设系统把聊天总结成“用户同意 A 退款”。今天用户开启新对话，只问“处理了吗”。若系统直接从记忆继承同意，就丢失了方案编号、金额、展示状态和期限。

正确做法是重新授权查询原操作结果：如果已完成，解释持久结果；如果仍待确认，按原操作状态和期限处理；如果需要新的方案，重新展示并接受对应确认。历史可以帮助定位，但不能迁移成新的许可。

同样，“用户希望简短回复”可以影响文字长度，却不能让系统省略必要的订单澄清或金额说明。记忆是否有用，要看它作用在哪一个决策上，而不是召回越多越好。

## 将来需要时，从最小方案开始

假设实际使用反复出现一个问题：同一客户每次新开对话都要求简短回答。可以先让用户显式设置一个结构化偏好，而不是立即建设向量库。最小记录包含偏好值、来源、更新时间，以及修改和删除能力；按可信客户身份读取即可。

这只是将来的设计例子，当前未实现。若再研究自动提炼，就与“不使用记忆”和“用户显式设置”比较。场景必须包含临时要求、稳定偏好、纠错、删除、客户隔离和绑定变化，同时确认记忆不能扩大业务权限。

有价值的指标是用户需要重述几次、回答是否遵守当前要求、误用旧信息多少次，以及延迟和完整调用费用。先确定新场景与预算，按预定次数运行；没有净收益就暂缓，不因为架构图少一块而继续增加组件。

## 将来的最小长期偏好合同

下面是设计练习，**当前未实现**。只考虑“回复简短”这类稳定表达偏好，不保存退款资格、批准或用户确认。第一版甚至不需要向量检索：按可信客户键读取一个严格枚举的设置，比自动提取全量历史更容易控制。

| 合同项 | 一个最小选择 | 必须回答的反例 |
| --- | --- | --- |
| 写入来源 | 用户显式设置，记录来源与时间 | “这一次简单说”不能自动永久化 |
| 数据形状 | 例如 responseStyle=concise/default，附 revision | 不接受任意文本装入系统提示 |
| 读取范围 | 新对话按当前可信客户身份读取 | 换绑或撤销后不能读取旧客户偏好 |
| 冲突顺序 | 当前用户要求优先于历史默认 | 用户这轮要求详细解释时应覆盖简短默认 |
| 修改与删除 | 基于版本更新；删除后新会话不可再召回 | 延迟写入任务不能把已删除偏好重新写回 |
| 生命周期 | 明确是否长期保留、何时失效以及如何查看 | 不能只有“写入”而没有纠错或删除入口 |
| 权限边界 | 仅影响表达，不能影响订单授权或确认 | “以后都替我同意”不成为资金操作许可 |

如果未来采用后台自动提炼，删除还要有版本或删除标记，使旧任务提交时发现版本过时而拒绝；重试不能把删除前的摘要恢复。这是需要实现和验收的竞态，不是今天已有的保证。对于显式枚举偏好，先做同步更新往往更省复杂度。

验收应先用确定性场景检查隔离、版本、删除、当前要求优先以及禁止授权用途，再用新题观察重述次数是否下降。真实模型提炼只有在对照确有收益时才加入，并记录额外输入、输出、延迟、未返回用量与失败。没有实验结果时，结论只能是“已有设计和停止条件”，不能声称已提高记忆准确率或降低成本。

## 练习与面试回答

请把“用户喜欢简短回复”“A 单已退款”“用户当前选择 B 单”“该套餐预约规则”分别放入偏好、业务结果、引用和知识库。接着回答每项由谁更新、何时失效、是否能直接用于资金操作。

面试时可以这样解释选择：“我先实现持久业务结果和网页历史回访，用有限引用处理重建后的对象定位。当前关键事实都需要重新授权读取；跨新对话偏好提炼还没有明确收益，所以先不扩建。出现具体重述需求后，会用最小结构化偏好与无记忆方案比较。”

这段回答包含当前需求、替代方案、接受的体验代价和重新启动条件，比声称长期记忆永远无用或必不可少更有判断力。

继续做三道源码练习：

1. 构造两个未选金额候选，让第一个过期。预期只剩一个数据项，仍不能自动形成基准；定位 `selectionRequired` 的保留逻辑。
2. 构造一个已过期且 requestId 重复的快照。预期先拒绝非法结构，不能用过期过滤隐藏重复；查找验证发生在过滤之前的位置。
3. 查看网页的第 101 段历史创建路径。预期返回容量错误，已有记录仍可查看；清理未提交空壳不等于允许删除最旧的真实记录。

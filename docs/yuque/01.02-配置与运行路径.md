# 1.2 配置改了，为什么程序没有按预期运行？

同一个问题在两个终端里得到不同回答，先别急着归因于模型。一个终端可能运行直接工具路线，另一个开启了业务 Controller；一个使用按词检索，另一个还启用了重排。理解配置，就是把“我以为打开了什么”追到“程序实际创建了什么”。

启动时，环境变量先提供一组字符串，读取函数补上默认值并检查是否合法，最后才把它们交给对应的服务和会话。顺着这条线读，比先记几十个开关容易得多。

## 启动要经过哪几站

`npm start` 会启动 `src/cli.ts`，Node 可从本机 `.env` 读取设置；QQ 入口使用 `src/qq.ts`。终端已存在的同名环境变量优先于 `.env`，因此看到文件内容还不能确定本次运行值。

读取终端与本机设置 → 去除输入两端空白 → 仅在输入为空时使用默认值 → 拒绝非法值与非法组合 → 连接业务服务 → 创建模型运行时 → 创建对应会话。

解析负责把字符串变成程序认识的值，校验负责拒绝拼错或不支持的组合，分支负责让合法值产生实际行为。只在界面显示“已应用”而没有传入分支的开关，没有完成从配置到运行代码的传递。

## 两个小函数看懂默认与组合限制

先看两个经常一起使用的选择：atomic 让模型直接选择业务工具，controller 让业务代码组织固定步骤；memory 把引用留在进程里，mysql 选择持久引用候选。这里的“引用”是订单、协商任务和退款方案的编号等定位信息，用来承接“刚才那单”。上下文模式决定这些信息保存在哪里，当前事实仍要重新查询。

```typescript
// src/support-session.ts · 未设置时使用默认路线，拼错则直接报错
export function readSupportArchitecture(
  env: NodeJS.ProcessEnv = process.env,
): "atomic" | "controller" {
  const value = env.SUPPORT_ARCHITECTURE?.trim() || "atomic";
  if (value !== "atomic" && value !== "controller") {
    throw new Error("SUPPORT_ARCHITECTURE 仅支持 atomic 或 controller。");
  }
  return value;
}
```

```typescript
// src/support-session.ts · 校验上下文模式与架构的组合
export function readSupportContextMode(
  architecture: "atomic" | "controller",
  env: NodeJS.ProcessEnv = process.env,
): "memory" | "mysql" {
  const mode = env.SUPPORT_CONTEXT_MODE?.trim() || "memory";
  if (mode !== "memory" && mode !== "mysql") {
    throw new Error("SUPPORT_CONTEXT_MODE 仅支持 memory 或 mysql。");
  }
  // 持久引用依赖 Controller，并要求已配置售后数据库凭据。
  if (mode === "mysql"
    && (architecture !== "controller" || !env.AFTER_SALES_DB_PASSWORD)) {
    throw new Error("持久会话定位需要 Controller 和已初始化的售后数据库账号。");
  }
  return mode;
}
```

比如把架构设为 atomic、上下文设为 mysql，第二个函数就会报错。程序不会一边显示“持久引用已开启”，一边悄悄退回内存。通过配置检查后，还需实际连接数据库，才能知道服务是否可用。

这里的错误需要尽早出现。如果程序默默把拼错的值改回默认，读者会误以为正在研究持久恢复，实际却使用内存；如果等模型调用后才报错，就浪费了等待时间和费用。

## 校验必须发生在使用之前

```typescript
// src/cli.ts · main 的启动检查，先读配置再创建业务服务
const taskLimits = readModelTaskLimits(); // 一条消息的请求数与上下文预算
const architecture = readSupportArchitecture();
// CLI 咨询解析配置
const questionOptions = readCliQuestionOptions(architecture);
const contextMode = readSupportContextMode(architecture);
const parameters = resolveSupportRunParameters(
  architecture, readKnowledgeParameters(), // 检查检索配置与架构是否相容
);
const senderId = process.env.CLI_DEMO_USER || "TEST_USER1";
if (!["TEST_USER1", "TEST_USER2"].includes(senderId)) {
  throw new Error("CLI_DEMO_USER 仅支持 TEST_USER1 或 TEST_USER2 合成身份。");
}
```

这些检查通过后，程序才连接数据库、装入模型凭据并建立会话。把便宜的输入检查放前面，错误会更早、更清楚地暴露，也避免为无效配置发起模型请求。

不要把“配置合法”误解为“远端一定能用”：本地知道模型名称和密钥不为空，并不代表网络连接、远端认证或自然语言回答已经成功。不同错误发生在不同层，查启动问题时按调用顺序定位即可。

## 合法配置怎样变成真实分支

```typescript
// src/cli.ts · 同一个工厂供首次创建和失败后的会话重建使用
// store 查询订单；business 提供协商与退款服务，未配置时为空。
const createSession = () => architecture === "controller"
  ? createSupportSession(identity, store, modelRuntime, model, business, {
      knowledge,
      context: contexts?.bind(identity, "cli"), // 持久读写范围由可信身份绑定
      questionContract: questionOptions.questionContract,
      questionResolver,
    })
  : createCouponSession(identity, store, modelRuntime, model, business);
let session = await createSession();
```

现在配置真正改变了运行路径：Controller 分支接收知识服务、引用存储与咨询解析器；默认分支创建直接工具会话。查看一个开关是否生效，最后就要追到这样的使用位置。

持久存储的客户范围由会话工厂绑定，模型不能自己填客户或存储键。切换恢复方式，只改变引用保存在哪里，不改变谁有权访问订单。

## 稳定演示怎样准备

演示时建议开一个新终端，按下列清单固定参数，避免遗留实验设置改变运行路径。所需数据库和本机凭据的准备步骤见文末复现资料。

```bash
# 固定为直接工具路线与进程内上下文
export SUPPORT_ARCHITECTURE=atomic SUPPORT_CONTEXT_MODE=memory
# 使用稳定的词项检索组合
export KNOWLEDGE_MODE=lexical KNOWLEDGE_SUPPORT=binary
export KNOWLEDGE_SUPPORT_MODEL=configured KNOWLEDGE_SUPPORT_PROMPT=v5
export KNOWLEDGE_APPLICABILITY=model_only KNOWLEDGE_QUERY_MODE=combined
export KNOWLEDGE_THRESHOLD=0.71 KNOWLEDGE_TIMEOUT_MS=15000
# 清空遗留的独立解析模型设置，让默认配置接管
export CLI_QUESTION_CONTRACT=v2 CLI_QUESTION_MODEL= CLI_QUESTION_TIMEOUT_MS=
# 选择模型；空的通用密钥让程序按供应商规则查找本机专用密钥
export MODEL_PROVIDER=deepseek MODEL_ID=deepseek-flash MODEL_API_KEY=
# 使用专用合成客户；启动后发送问题会产生实际模型调用
export CLI_DEMO_USER=TEST_USER1
npm start
```

第一次阅读抓住四个选择即可：直接工具路线、词项检索、进程内上下文和指定模型。其余值用于恢复相容配置，复现时按清单原样使用。

该命令会启动实际程序，模型输入会产生远程调用。只读配置阅读无需运行它。演示商家协商与退款时，另外需要对应数据库账号及初始化；仅配置只读订单库，不会自动开放售后写入。启动前也应停止共享专用演示库的其他商家 worker，避免互相处理待办任务。

## 空字符串为什么有用

假设 `.env` 中留有某个独立解析模型的设置，本次却要使用默认解析路线。只改架构名称不够，遗留参数可能与新组合冲突。`export CLI_QUESTION_MODEL=` 明确在当前终端设置空字符串，阻止文件内旧值重新填入；读取函数再把这个空值解释为未指定。

删除一个环境变量和设置为空不是一回事。删除后，启动时可能从 `.env` 重新读取；设置为空则仍是显式环境值。这个差别也适用于通用模型密钥回退：清空通用键只是让代码按供应商规则查找专用键，并不证明专用键一定来自文件。

密钥要留在本机凭据配置中，教学截图和配置摘要只展示非敏感字段。讨论“实际生效配置”不要求把秘密也写进记录。

## 不同入口为什么需要分别确认

CLI、QQ 与网页有不同的配置入口。CLI 的咨询解析参数不会因为名称相似而自动作用于 QQ；网页提交的设置只属于网页创建的会话，也不会修改已运行的 QQ 进程。

一个完整的排查例子是：网页更换了模型，QQ 仍然使用旧模型。先确认这是两个进程或会话，再分别看各自读取参数的位置，而不是继续在网页反复点击保存。配置作用域越明确，排障越容易。

同样，数据库用户名决定连接服务使用哪组凭据，业务工具决定模型能请求哪些操作。仅仅把程序改成可写数据库账号，并不会合理地扩大模型工具集合；身份与退款确认也不应成为可关闭选项。

## 怎样观察一次设置到底改了什么

可以把一个开关拆成输入、限制、实际使用位置三个位置。例如上下文模式的输入是环境变量，限制是只接受两种模式且持久模式需要相容架构，实际使用位置是创建持久读写接口并传给会话工厂。少看任何一处，都可能把合法的字符串误当成已经接入的能力。

用这套方法读超时也一样：先找数值范围，再找计时器包住哪一段工作。模型请求超时、整轮业务超时、排队时间和取消收尾是不同范围，一个毫秒值不能自动覆盖整个用户等待过程。

记录实际配置时，只保存经过解析后的非敏感值，并说明入口与作用范围；不要把整份进程环境直接复制到文档。需要做对照时，两组配置应只改变想研究的因素，否则回答变化可能来自模型、检索、上下文或流程中的任意一处。

## 练习：先预判，再顺着代码定位

输入 `SUPPORT_ARCHITECTURE=atomic` 与 `SUPPORT_CONTEXT_MODE=mysql`，程序会在哪一步拒绝？根据完整函数，答案是持久引用组合校验，发生在创建订单数据库服务之前。

再把 `memory` 故意拼错，观察为什么应该直接报错而不是回退默认。最后口述一个成功启动：参数来源、合法组合、模型选择、可信身份、会话工厂分别是谁提供的。能从这条链路解释结果差异，就不需要背几十个开关名。

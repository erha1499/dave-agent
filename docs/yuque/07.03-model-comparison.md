# 7.3 换一个模型值不值，怎样做公平对照？

两个模型都得了 9/12，为什么一次选型仍保留原方案？因为“分数一样”可能掩盖完全不同的业务错误：一个只是把资料类别分错，但接收与拒收仍正确；另一个把缺失事实的资料接收成答案依据。

这次选型只比较“资料能不能作为回答依据”这一项工作。先看模型负责什么、错了会怎样，再看为什么相同总分会导向不同选择。

## 1. 先选角色，再选模型

主 Agent 负责理解对话并选工具；重排模型负责给候选资料排序；支持判别器负责判断每篇资料能否回答当前诉求。三个角色的输入、输出、错误代价不同，不必绑定成同一个模型。

例如用户问：“退款到底由谁批准？”两篇资料分别写“店长可以取消预约”和“客服负责登记工单，无权批准退款”。它们都谈到了相关角色，却没有说谁有批准权。判别器应该拒绝把它们当作这个问题的答案。

如果用户改问“资料有没有写清谁能批准，我还需要找人核实吗”，这些内容就能帮助解释资料的不足。同一份资料能不能用，要回到用户到底在问什么。

## 2. 四类输出把错误拆开

| 类别 | 判定含义 | 是否作为当前答案依据 |
| --- | --- | --- |
| 直接事实 | 原文提供所问事实，或准确回答规则流程 | 接收 |
| 边界回答 | 用户明确问资料覆盖或推断边界，原文回答该边界 | 接收 |
| 仅有限制 | 相关但缺少目标事实或关键条件 | 拒收 |
| 无关 | 与所问内容无关 | 拒收 |

支持判别器输出类别、原文引文与简短理由；Harness 由类别导出是否接收，而不接受模型自行声称“操作已经授权”。这些类别服务于回答依据，身份、金额和退款确认仍由业务边界处理。

“需要审批”可直接回答“办理流程是什么”，却不足以回答“这次已批准了吗”。“未列出过敏原”可以说明资料缺失，不能冒充具体配料清单。模型有时为了给出一段安全解释，把实例问题改成边界问题，这就是需要专门观测的误接收。

## 3. 一条输入怎样成为可比较结果

每道题事先固定问题、范围、候选资料，以及每篇资料应该属于哪一类、是否应该接收。这样模型返回后，只需对照既定答案，不会因为某个回复听起来合理就临时改标准。

两条实验路线使用相同问题、候选正文、提示、超时、输出上限与重试约定，仅模型和必要接口字段不同。发送顺序按题目交替，降低某一方案总是先发带来的环境偏差。仍然要保存实际请求，因为配置写了“不重试”不等于网络层一定只发了一次。

评分分成两层：逐篇检查类别和接收决定，再检查整道题接收的资料集合是否完全正确。

```typescript
// c1-model-support-comparison.ts：gold 是调用前冻结的预期标签。
export function scoreModelSupportComparison(
  item: ModelSupportComparisonCase, // 同一道题的问题、资料与预期标签
  row: ModelSupportComparisonRow, // 某个模型对这道题的实际输出
) {
  const candidates = item.expectedByCandidate.map(gold => {
    const invalid = Boolean(row.verification?.validation?.invalidDecisions.some(
      decision => decision.id === gold.id,
    ));
    const actual = row.execution === "completed" && !invalid
      ? row.verification?.value.find(decision => decision.id === gold.id)
      : undefined;

    return {
      id: gold.id,
      expectedPositive: gold.supported,
      state: invalid ? "invalid" : actual ? "valid" : "missing",
      category: actual?.category ?? null,
      supported: actual?.supported ?? null,
      // 总体正确：类别和接收决定都要与标签一致。
      passed: Boolean(actual
        && actual.category === gold.category
        && actual.supported === gold.supported),
      falseAccepted: Boolean(actual && !gold.supported && actual.supported),
      falseRejected: Boolean(actual && gold.supported && !actual.supported),
    };
  });

  // 缺失或结构无效，不能算作“正确拒收”。
  const complete = row.execution === "completed"
    && row.verification?.validation?.status === "complete"
    && row.verification.value.length === item.candidates.length
    && candidates.every(candidate => candidate.state === "valid");
  return {
    candidates,
    passed: complete && candidates.every(candidate => candidate.passed),
    // 单独看接收集合：该留的全留，该拒的全拒。
    exactAcceptanceSet: complete && candidates.every(
      candidate => candidate.supported === candidate.expectedPositive,
    ),
  };
}
```

这样就能区分类别分错与资料误收两种后果。读下表前先分清单位：每个模型回答十二道题，每题两篇资料，共二十四个候选判断。应该接收的正例与应该拒收的负例各十二篇；前三项按整道题统计，后两项按单篇资料统计。

## 4. 同分的历史对照怎样解读

| 指标 | DeepSeek Pro | 千问候选 |
| --- | --- | --- |
| 输入全部执行 | 12/12 | 12/12 |
| 分类与接收同时正确 | 9/12 | 9/12 |
| 精确接收集合正确 | 12/12 | 10/12 |
| 负例误接收 | 0/12 | 3/12 |
| 正例接收 | 12/12 | 12/12 |

“三个误收”是三篇不该接收的资料被留下，不等于三个会话失败，也不等于三次 HTTP 错误。类别分错可能只影响分类结果；误收资料却可能让客服给出没有依据的承诺，因此不能只看一个总分。

千问候选的误接收中，有资料没有说明批准角色，却被当作“边界回答”接收；也有资料未收录过敏原，却被当作能回答清单。引文都能在原文找到，错误在于它没有支持用户真正索要的内容。

DeepSeek Pro 也有类别错误，比如把“相关但不充分”判成“无关”。不过这两类都拒收，所以该题的接收决定仍正确。下一轮可以专门研究类别区分，不必抹掉错误来提高这轮成绩。

## 5. 为什么必须同时准备正例与负例

只考负例，一个永远拒收的模型就可能满分；只考正例，一个永远接收的模型也可能满分。两组要同时存在，分别回答“会不会说过头”和“会不会明明有答案却不帮助用户”。

条件覆盖也是正负例设计的重要部分。给一篇写着“工作日可用、节假日除外”的资料，用户问工作日使用流程和法定节假日可用性，两个问题可能有不同答案。不能只改变几个关键词，应该让对象、前提、例外与问法真实改变决策。

对照还要固定无答案输入和范围干扰输入，并保留所有未执行项。新增题目如果来自已知失败模式，应明确属于针对性新题；“不是旧题”并不自动等于盲测或真实用户分布。

## 6. 费用与延迟要跟着真实请求走

本次每个模型各发出十二次 HTTP，共二十四次。测到的是支持判别组件的表现，完整客服还要承担检索、主 Agent、数据库和消息发送的成本。

费用要从实际发送边界记录，再核对供应商返回的用量。历史估算中，一条路线以美元计，另一条以人民币计，应分列展示；不能直接比较数字大小，或者把失败调用从总费用删掉。若用量缺失，就保留未知并停止后续依赖完整费用的决定。

中位延迟描述当前样本的一般等待时间，高分位描述较慢尾部；十二次小样本尤其容易受缓存和网络影响。不要把某次请求较快写成稳定生产延迟承诺。质量、费用和延迟都完整后，才讨论单位成功输入成本。

## 7. 接口适配也属于比较条件

两个供应商都接受聊天消息，并不表示参数可以原封不动复制。有的输出上限字段不同，有的对系统消息角色和流式用量格式有特定要求。应让业务内容与预算含义尽量一致，把必要兼容差异明确记录；不能让一条路线多拿上下文，另一条少拿候选，再把差异归因于模型。

凭据也必须与实际供应商绑定。切换模型应选择它自己的端点与凭据，不能只改模型名，却把主模型密钥发送给另一家。请求前校验地址、模型、载荷和预算，请求后核对响应模型与用量，才能确认比较的确是预定的两个对象。

## 8. 把停止条件写在运行之前

这次对照预先要求：完整执行；负例零误收；没有新增正例误拒；精确接收集合比原方案改善。千问候选没有满足门槛，因此不进入完整会话候选，默认方案保持。

停止不等于证明某模型普遍更差。它表示在这一职责、这套输入和当前约束下，没有足够理由承担切换成本。接下来应先解释失败属于诉求理解、条件覆盖还是接口问题，再决定是否有新假设值得独立实验。

继续调整已经曝光的问题，能帮助开发，但不能再把这些题目当独立验收。换提示、换数据、换模型、改评分同时发生时，更无法判断改善来自哪里。每次只研究明确变量，留下退步样本，才有可复述的选型结论。

练习：候选模型误收由两条降到零，但正例误拒增加四条。列出你需要向业务确认的代价，并设计一个有明确分母和停止条件的小批新题。不要用“更安全所以一定更好”代替用户仍需获得帮助的事实。

## 9. 静态分工、动态路由和故障降级是三件事

本项目可以按职责分别配置主 Agent、问题解析、重排和支持判别模型。这里的“分别配置”发生在启动或实验时；系统没有为每条消息自动判断复杂度、再挑模型的通用路由器。

| 决策 | 触发时机 | 当前状态 | 最重要的验证 |
| --- | --- | --- | --- |
| 静态职责分工 | 启动或实验配置时 | 已有；保留模型、凭据和实际参数快照 | 该职责的准确性、延迟和费用 |
| 按复杂度动态路由 | 每次任务到来时 | 未实现；需要新业务收益才启动 | 路由器自身错误与额外费用、被送错模型后的损失 |
| 供应商故障降级 | 超时、限流、不可用时 | 没有跨供应商自动切换 | 原请求是否仍在执行、预算是否累积、重复副作用如何避免 |

简单场景不一定需要模型：精确确认和本人最近订单列表已有不经模型的 Harness 路径。明确订单号后的普通查询仍可能由模型选择 `get_order`，不能笼统说所有查单和状态卡都零模型。优先利用已经实现的确定性分流，比新增一个模型判断“该不该调模型”更容易解释和核验。涉及金额、批准或身份时，无论选择哪个模型，都不能绕过工具边界。

配置解析很简单：明确选了模型，就使用对应供应商；选“沿用配置”时，才读环境变量。

```typescript
// model-selection.ts：解析静态配置，不根据用户问题自动挑模型。
export function resolveModelSelection(
  selection: ModelSelection = "configured",
  env: NodeJS.ProcessEnv = process.env,
) {
  if (!modelSelections.includes(selection)) {
    throw new Error(
      "模型选择仅支持 configured、deepseek-flash、deepseek-v4-pro、"
        + "qwen3.7-plus-2026-05-26。",
    );
  }
  if (selection === "qwen3.7-plus-2026-05-26") {
    return { provider: "bailian", modelId: selection };
  }
  if (selection !== "configured") {
    return { provider: "deepseek", modelId: selection };
  }

  // configured 表示沿用环境中的供应商和模型，未填写才使用默认值。
  const provider = env.MODEL_PROVIDER?.trim() || "deepseek";
  return {
    provider,
    modelId: env.MODEL_ID?.trim()
      || (provider === "deepseek" ? "deepseek-flash" : "gpt-4.1-mini"),
  };
}
```

这段函数只读配置，没有接收用户问题或失败状态。由此也能看出，它解决的是选用哪个已支持模型，而不是自动路由或故障切换。

如果未来确需动态路由，应先定义可以测量的复杂度特征，例如是否需要跨多份规则、是否存在歧义、是否需要多轮澄清；再保留一组简单与复杂、正常与对抗的新题。对照固定主模型，记录路由成本与完整任务质量。不能仅用提示词让模型输出 easy/hard，就声称降低了总成本。

## 10. “模型失败就换一个”为什么不是完整兜底

读工具超时可以在有限次数内重试，前提是有剩余预算且操作无副作用。模型输出结构不合法可以要求一次格式修复；缺订单和指代歧义应向用户澄清。退款提交后连接断开则先查询持久结果，不能让新模型重新猜测并执行退款。

选择备份模型还要核对工具调用格式、输出限制、上下文容量和凭据归属。更小模型可能无法承接已有长对话；更大模型可能增加费用与尾延迟。备份模型与重试共享同一任务预算，不能通过换模型绕过上限。

检索降级也不能悄悄改变“有证据”的含义。向量服务异常后用关键词召回，只能得到新的候选资料，仍要检查门店、商品、版本和当前问题是否被原文支持。当前配置支持 lexical 不等于所有候选异常都已经自动安全降级。

练习：用户已精确确认退款，随后连接中断；同时主模型不可用。请画出“重新授权 → 查持久结果 → 告知已完成或当前状态”的路径，并说明为什么不需要让备份模型重新计算金额。

## 11. 面试中的两分钟选型答法

“我先按职责拆错误代价：主 Agent 要正确选工具，支持判别要避免把缺失事实当依据。对比时固定问题、资料、参数和严格标签，分开误接收与误拒收。历史十二输入对照中，候选总分相同但出现三个负例误接收，因此未推进；默认路线没有切换。我还没有实现复杂度自动路由，当前先用 Harness 精确协议处理确定性动作，再用新题检验候选是否带来完整任务收益。”

面试官继续问“什么时候才值得换”时，可以接着展示误接收样本和事前约定的门槛。一次选型的价值，是讲清为什么保留或替换方案，不是给模型排一个通用名次。

# 7.1 Agent 做得好不好，效果、延迟和成本怎么算？

一次售后评测计划十二轮，执行八轮：六轮通过、两轮失败，剩下四轮因前置失败没有执行。报告应该写多少通过率？如果只写“六除以八，75%”，读者会误以为整套业务已经跑完。

这道题先别急着做除法。先问：计划里的十二轮去了哪里？本课沿着“先定计划、再记执行、最后算结果”的顺序，把失败、跳过和缺失找回来，再讨论一次优化省了多少等待和费用。

## 1. 先定义评测对象，别急着定义分数

把“联系商家后完成退款”看作一个案例。用户提出退款、确认联系商家、收到商家结果，是其中的不同轮次；一轮里又可能包含几次模型请求和工具调用。评测最后检查的是具体结果，例如重复确认后是否仍只有一条退款记录。

一个用户轮可能先调用模型、再调用工具、最后再请求模型，所以轮次数不是模型请求数。一次通知事件也可能触发模型；而精确确认可以由 Harness 直接处理，不经过模型。按真实步骤和 HTTP 记录统计，才能知道实际用了多少服务。

运行前先列出这些案例、轮次和检查。工具选得对不对、数据库改成了什么状态，可以用代码判断；回复有没有回答问题、有没有漏掉条件，则要另看最终文字。两份成绩分开保留，才知道该修执行还是修回答。

## 2. 四种结果必须各有位置

| 结果 | 含义 | 例子 |
| --- | --- | --- |
| passed | 已执行且满足检查 | 重复确认返回同一记录 |
| failed | 已执行但不符合预期 | 越权订单被返回 |
| skipped | 明确决定不执行，并保存理由 | 协商失败后跳过退款确认 |
| missing | 计划存在，但没有有效结果 | 进程中断，结果未保存 |

跳过和缺失都不能算成功，但排查方法不同。跳过说明执行器知道依赖失败并如实记下；缺失说明记录链不完整，需要查中断或持久化问题。统一抹掉两者，最后只剩成功案例，会造成幸存者偏差。

下面把两个问题分开处理：先数全计划中的每种结果，再决定一个案例整体算什么状态。

```typescript
// eval-analysis.ts：outcomes 已按计划补齐，未拿到结果的项记为 missing。
function counts(outcomes: Outcome[]): EvalCounts {
  return {
    planned: outcomes.length, // 分母始终是完整计划
    passed: outcomes.filter(value => value === "passed").length,
    failed: outcomes.filter(value => value === "failed").length,
    skipped: outcomes.filter(value => value === "skipped").length,
    missing: outcomes.filter(value => value === "missing").length,
    passRate: outcomes.length
      ? outcomes.filter(value => value === "passed").length / outcomes.length
      : null, // 没有计划时，不编造一个通过率
  };
}

// 汇总案例时，status 是案例记录的状态，children 是各轮的结果。
// 汇总一轮时，同样用它合并该轮状态与各项业务检查。
function outcome(
  status: "passed" | "failed" | "skipped" | undefined,
  children: Outcome[],
): Outcome {
  if (status === undefined) return "missing"; // 父项本身没有结果
  if (status === "failed" || children.includes("failed")) return "failed";
  if (children.includes("missing")) return "missing";
  if (status === "skipped" || children.includes("skipped")) return "skipped";
  return "passed"; // 自身和子项都没有留下未完成或失败
}
```

如果退款前的几轮都成功，最后确认却失败，这个案例仍然失败。汇总不能让前面的成功把关键失败“平均掉”。

回到开头的例子：完整计划通过率是 6/12，即 50%；执行覆盖率是 8/12；已执行轮通过率是 6/8。可以并列报告，但必须把名字与分母说清楚。若案例目标要求全部关键轮次成功，案例通过数还要单独计算。

## 3. 断言要检查业务结果，而不是固定话术

验证退款幂等，应检查两次确认是否引用同一操作、退款记录是否只有一条、金额是否一致。只检查回复包含“成功”两个字，无法发现重复扣账，也可能把一句“操作未成功”误判为成功。

验证越权拒绝，应检查查询输入确实是他人订单、工具拒绝且未返回敏感字段；不能仅看客服语气礼貌。验证规则使用，应检查适用范围、返回的文档以及必要条件，而不是只数来源编号。

这类固定检查器也叫 oracle，即本次评测事先约定的判断标准。它应来自业务规则，而不是运行后根据模型输出临时改答案。发现标签歧义时，保留原始结果，修改题集说明并另存新版本；已看过的题目只能作为开发材料，独立验收用新题。

## 4. 如何记录执行而不干扰执行

项目复用 Pi 事件获取模型消息与工具开始、结束。采集回调只在内存记录，整轮结束后再持久化，避免在实时事件回调里插入数据库写入拖慢或打断 Agent。

工具开始时先留一条待完成记录，结束时用同一个调用编号补上结果。这样既能算耗时，也能发现只收到结束、没收到开始的采集异常。

```typescript
// eval-capture.ts：工具事件处理，放在 receive 回调中。
if (event.type === "tool_execution_start") {
  const step: EvalStep = {
    index: steps.length + 1,
    type: "tool",
    name: event.toolName,
    durationMs: null, // 结束事件到来后再计算
    input: event.args,
    isError: false,
    toolCallId: event.toolCallId,
    // 内层依赖保留外层编号，避免误当成模型独立选出的工具。
    ...(event.parentToolCallId
      ? { parentToolCallId: event.parentToolCallId }
      : {}),
  };
  steps.push(step);
  // 按调用编号保存开始时间，结束事件才能找到同一次调用。
  pendingTools.set(event.toolCallId, { step, started: performance.now() });
} else if (event.type === "tool_execution_end") {
  const pending = pendingTools.get(event.toolCallId);
  if (!pending) {
    failed = true; // 没有开始记录，说明采集链不完整
    return;
  }
  pending.step.durationMs = Math.round(performance.now() - pending.started);
  pending.step.output = event.result;
  pending.step.isError = event.isError;

  // expectedDeniedOrder 是这道题预先指定的越权订单。
  // denial 是工具的标准授权拒绝提示；普通工具故障不能算通过。
  const args = pending.step.input as { orderId?: string } | undefined;
  const result = event.result as {
    content?: Array<{ type: string; text?: string }>;
  } | undefined;
  pending.step.expectedDenial = Boolean(
    event.isError
    && event.toolName === "get_order"
    && expectedDeniedOrder
    && args?.orderId === expectedDeniedOrder
    && result?.content?.some(
      part => part.type === "text" && part.text?.includes(denial),
    ),
  );
  pendingTools.delete(event.toolCallId); // 这次工具调用已结束
}
```

有些内层查询是 Harness 为外层工具补齐的依赖。它们也产生事件，但不能算成模型主动选择了更多工具，更不能再从聊天历史重复数一次。整轮结束仍未完成的步骤会另标为异常，避免“没有收到报错”被误当成成功。

首次文本时间也要说清起点和终点。本项目记录一轮里第一次出现模型文字的时刻，它可能在工具调用之前。用户拿到最终答案、QQ 接受消息、客户端显示消息，都还在后面，不能共用这一个延迟数字。

## 5. 用量缺失为什么必须显示未知

![完整评测计划与代价](./assets/25f6fec5197fc2bc.png)

图 1：成功、失败和未执行都属于计划分母；评价方案时同时观察质量、时间和成本。

假设发了十次模型请求，只有八次返回用量。可以报告“已知八次共多少 Tokens”，不能把这八次之和写成全批总量。一次失败请求可能已经发到供应商，也可能产生费用；失败不等于免费。

汇总用量时同时保留“已经知道多少”和“是否全部知道”。下面只统计已采集的主 Agent 模型步骤；每一步都有有效用量时，才给出完整 Token 小计。

```typescript
// eval-analysis.ts：只汇总已采集的模型步骤。
function usageAnalysis(steps: EvalStep[]): EvalUsageAnalysis {
  const models = steps.filter(step => step.type === "model");
  const reported = models.flatMap(step =>
    validUsage(step.usage) ? [step.usage] : [],
  );
  const priced = reported.filter(value =>
    value.estimatedCostUsd !== null
    && Number.isFinite(value.estimatedCostUsd)
    && value.estimatedCostUsd >= 0,
  );

  // 已知小计：只加确实拿到的数字；完全没有数据时保留 null。
  const knownTokens = reported.length
    ? reported.reduce((sum, value) => sum + value.totalTokens, 0)
    : null;
  const knownCostUsd = priced.length
    ? priced.reduce((sum, value) => sum + value.estimatedCostUsd!, 0)
    : null;

  return {
    modelRequests: models.length,
    reportedRequests: reported.length,
    missingRequests: models.length - reported.length,
    coverage: models.length ? reported.length / models.length : null,
    knownTokens,
    // 每个模型步骤都报告了用量，才能给出完整 Token 小计。
    completeTokens: models.length && models.length === reported.length
      ? knownTokens : null,
    knownCostUsd,
    // 用量完整还不够，费用必须每一步都能估算。
    completeCostUsd: models.length && models.length === priced.length
      ? knownCostUsd : null,
  };
}
```

问题解析、重排和支持判别也可能调用模型，要另外记录实际请求。于是，“这些步骤的用量齐了”仍不等于“整个客服任务的费用齐了”：还要确认请求和重试有没有漏记。同一次调用也不能在步骤表与请求表里重复相加。

正式入口后来增加了按实际 HTTP 记账的摘要，第 12 节会接着讲。阅读历史报告时，先看它用哪种统计方式，不把两份计数叠加。

价格估算也要说明来源与时间。目录价格乘 Tokens 是估算，不等于账单；缓存命中、缓存回放与真实远程请求要区分。缓存回放可以用于重新评分历史结果，却不能计成一次新的模型运行。

## 6. 比较方案时，同时看收益与退步

A/B 对照应尽量保持数据、原问、提示、工具、参数和评分一致，仅改变想研究的因素。除了总分，还要逐案例标出改善、退步、无变化和未完成。总分相同的两个方案可能失败在完全不同的安全场景。

预算应在运行前确定，例如固定新题、最多多少 HTTP、最多多长时间、何时因用量缺失停止。预算到达就归档结果；剩余额度和某题没满分，都不能自动成为续跑理由。后续要先说明新的失败假设，再设计下一次实验。

成本可以进一步换算为“每个完整正确案例的已知费用”。但如果总费用不完整，就不能把结果当精确单位成本；如果正确案例为零，也不要除零得出一个貌似有意义的数。保留空值比给出漂亮数字更有解释力。

## 7. 结果保存失败，也不能改写历史

评测结果本身也会遇到数据库异常。一次插入可能已提交，但客户端没收到确认；若执行器立刻重试同一批插入，就可能制造重复记录。项目在开始时保存计划，再按事务保存案例、轮次和步骤，并在运行结束后拒绝继续追加。结果回读使用一致快照，减少跨表拼接到不同阶段的数据。

结果存不下来，就让报告显示缺失，并沿采集或持久化链路排查。用模型回复反推一条“应该发生过”的轨迹，会把原本可定位的记录故障变成一份看似完整的错误报告。

## 8. 练习：写一段不会误导的结果摘要

已知计划三个案例共十二轮，执行八轮，通过六轮，失败两轮，跳过三轮，缺失一轮；十次模型请求中八次报告用量。请写摘要，必须包含计划分母、四种结果、执行覆盖、用量覆盖和未完成原因。

一个合理开头是：“十二轮计划中六轮通过、两轮失败、三轮因依赖失败跳过、一轮结果缺失；已执行覆盖八轮。已知用量覆盖八次模型请求，其余两次费用未知。”随后解释两条失败的业务意义，再谈下一次修复，读者就能知道该相信哪些结论。

## 9. 面试算例：写 1000 行代码，究竟花多少钱？

仅有行数算不出 Tokens。语言、命名、注释、每行长度、模型分词方式会改变输出长度；读仓库、规划、工具结果、修改和测试还会产生输入与多次请求。合理回答是先说明假设，再用真实请求的 usage 校准，而不是背一个“每行固定若干 Tokens”的换算。

每次请求先分清未缓存输入、缓存读、缓存写和输出。以下四个分量按 Pi 归一化后的互斥计数计算；直接使用供应商原始字段前，要核对其 prompt\_tokens 是否已经包含缓存，避免重复相加。

```plain
# 单价的单位均为“每百万 Tokens”；四类 Token 互不重复。
请求估算费用 = (
  未缓存输入 × 输入单价
  + 缓存读 × 缓存读单价
  + 缓存写 × 缓存写单价
  + 输出 × 输出单价
) / 1,000,000

# 工具调用前后、重试等实际请求都要计入。
任务估算费用 = 所有实际请求的估算费用之和
```

为便于手算，假设每百万 Tokens 的教学单价是：输入 2 元、缓存读 0.2 元、缓存写 2 元、输出 8 元。它们只是算例单价，实际模型费用要使用该次请求对应的费率。

| 请求 | 未缓存输入 | 缓存读 | 缓存写 | 输出 | 估算费用 |
| --- | --- | --- | --- | --- | --- |
| 第一次理解需求并选工具 | 8000 | 0 | 0 | 500 | 0.0200 元 |
| 读取工具结果后生成答案 | 2000 | 8000 | 0 | 1500 | 0.0176 元 |
| 小计 | 10000 | 8000 | 0 | 2000 | 0.0376 元 |

第二次请求会再次携带部分历史；即使模型看起来只是继续回答，历史也可能重新计费。缓存命中只改变适用的输入计价，不代表该请求免费。若随后一次请求超时且没有 usage，已知小计仍为 0.0376 元，完整费用则未知。不能以最终答复长度反推全部任务成本。

项目 `src/model-selection.ts` 的 `estimateModelUsage` 会检查各 Tokens 分量为非负安全整数、分量之和与 totalTokens 一致，再估算费用。百炼路线只接受已审阅的固定模型、北京区域和输入档位，缓存按原价作保守估算；Pi 目录价格另列美元。实际价格来源、版本和用量缺口需随运行记录一起交付。

## 10. 把失败成本计入“每个正确完成任务的成本”

设同一批计划 10 个任务，总计花费 2 元，只有 5 个完整正确完成。若费用完整，单位正确完成成本是 2 / 5 = 0.4 元，不能只加成功请求费用再除以成功数。失败、协议修复和重试也消耗资源。正确任务数为零时不报告有限单位成本；总费用缺失时，只给已知费用小计及覆盖率，不给精确结论。

“降低 Tokens”也不一定降低业务成本。少读一段关键规则，可能减少单次输入却增加澄清、失败和返工。对照应同时记录完整任务成功率、错误类型、总请求数、延迟与费用，说明收益是否来自省略必要步骤。

练习：计划 10 个任务，7 个完整执行、5 个正确；实际发出 18 次 HTTP，仅 16 次有 usage，已知费用 2 元。请解释为什么不能声称“每个正确任务成本 0.4 元”，并列出还缺的两类证据：剩余请求用量，以及所有已执行任务的答复与持久状态联合判定。

## 11. 用本项目回答“怎么证明升级有效”

先区分三份证据：客观工作台检查工具和状态；答复审阅检查自然语言的事实、条件和过度承诺；联合验收把最终公开回复、工具轨迹、数据库状态和费用绑定到同一批次。Codex 辅助审阅仍需作者复核，不能用候选的一次局部通过覆盖整体未准入。

## 12. 正式入口怎样把请求上限与费用记录接起来

一条用户消息可能先解析问题、再查资料并判断支持性，随后继续主 Agent 生成。当前 CLI、QQ 和网页在受理一条消息或 Harness 事件时建立 `withModelTask`，这些模型请求共用同一份预算。这里的一轮是入口消息或事件，不是包含多次用户确认的整个退款业务。网页调用 CLI 回复驱动时沿用外层作用域，不重置计数，也不输出第二份完成账本。

默认每条入口消息最多发出 12 次模型 HTTP 请求，每次重试也占一次。达到上限后，下一次请求在联网前被挡住；任务结束或取消后，迟到请求同样不能继续发送。

```typescript
// model-request-budget.ts：HTTP 发送函数中的前置检查。
// state 是当前入口消息共用的预算；后续模型调用和重试继续累计。
// 固定本次请求参数，保证检查的内容和随后发送的内容一致。
init = { ...init };
if (state.closed || state.controller.signal.aborted) {
  throw new ModelRequestBudgetError(); // 任务结束后拒绝迟到请求
}

// 同一包装器的多次重试，只算一次逻辑调用。
logicalCall ??= ++state.summary.logicalCalls;
if (state.summary.httpRequests >= state.summary.limits.httpRequests) {
  state.summary.blockedRequests++; // 超限尝试被拒发，不计为已发送 HTTP
  stop(state, "http_limit", "http_limit");
  throw new ModelRequestBudgetError();
}
```

一次逻辑调用可能在网络层重试多次，所以逻辑调用数和 HTTP 次数分别记录。只有明确知道“尚未发送”的拒绝，才能撤回预占计数；网络出错而发送结果不明时，不能假装这次尝试没有发生。本地替代模型单独记录，也不混入真实供应商用量。

| 正式摘要字段 | 应怎样读 |
| --- | --- |
| `httpRequests`<br><br> / `blockedRequests` | 已进入底层 transport 的次数，以及被拒绝的新请求；不是工具次数、QQ 发消息次数或整个业务的费用上限 |
| `knownTokens`<br><br> / `unknownUsageAttempts` | 已知 Token 小计与未知用量的实际 HTTP 数；只要存在未知，`totalTokens`<br><br> 为 null |
| `knownCostUsd`<br><br> / `knownCostCny` | 各币种已知估算小计，不能相加成一种币；任一小计为零都不证明总费用为零 |
| `unknownCostAttempts` | 无法估算费用的实际 HTTP 数；缺 usage、未覆盖费率或不适用档位都应保留 |
| `failurePhase`<br><br> / `failureReason` | 首次故障的阶段与固定原因；清理取消不能把真正的 Harness 或展示登记故障覆盖成取消 |

请求正常结束且返回了有效用量，才进入已知小计；半途断流、取消或缺字段都保留未知。这个上限控制的是请求次数，也不能撤回已经发出的请求或费用。若还要控制金额、Token 总量或多个进程共享的账户额度，需要各自的预算机制。

可在仓库根目录执行 `node scripts/model-request-budget-check.ts` 和 `node scripts/model-task-entry-check.ts`，分别检查请求预算边界与三个入口的作用域。它们使用替代传输或本机 HTTP，能验证计数和拒发，不能证明真实模型质量或供应商账单正确。上述历史真实模型批次也核对过正式账本与实际传输的请求数，但该批次的答复联合验收未通过。修复后新题的结果另按自己的完整分母与配置记录，见[7.2 工具成功、回答却错了，怎样验收完整任务？](<./07.02-task-acceptance.md>)，不能替旧批次补分。次数上限与[4.3 上下文快满了，什么时候停止、怎样继续？](<./04.03-context-budget.md>)解决不同问题：前者限制发多少次，后者在每次发送前检查完整载荷是否容得下。

## 参考资料与实现边界

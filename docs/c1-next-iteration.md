## P0-1：把展示过的金额与用户选定的基准分开

原版本 Session 在 `state.amountReference = result.verifiedAmountReference` 覆盖旧展示，只向模型暴露一个 `itemPaidUnit`。Controller 检查身份、订单和 `requestId` 是否匹配这个最近引用；`compareRemainingAmount` 再正确核算 fresh 实付。两层都没有证明用户指的就是最近那个数。

建议复用 `TrustedAmountReference`，在 Session 内保留至多两个不同来源的实际展示候选，以及溢出标志。候选携带现有 `requestId`、订单/商品、金额和版本，不从聊天摘要还原。另记录是否已经形成唯一或明确选定的比较基准：

- 只有一个可用展示来源时，继续现有只读比较流程。
- 两个来源或已溢出、用户尚未明确选择时，宿主不提供可执行的唯一基准；即使模型给出其中一个合法旧 `requestId`，也不能代替选择。
- 当前订单是比较的目标，不能自动选择右侧的历史金额。例如明确 `COUPON-6005` 并不说明用户选择了该单此前显示的数。
- 返回固定澄清，列出宿主实际保存的订单与金额。用户明确选定后，再复用当前 fresh 授权、券选择和金额计算。

选择可复用已有卡片或确定性文本交互，但选择标识必须绑定当前 actor、群和候选版本；不接受用户直接提交金额作为宿主事实。不要仅在动作中增加一个模型自报的 `unambiguous: true`。也不要仅把两个候选都发给模型、仍允许它任取一个 ID：这只能改善提示，不能补上宿主边界。

这一方案只增加少量会话状态和歧义时的一轮交互，不增加检索、额外判别模型或通用记忆系统。保守性代价是曾展示多个金额时可能多问一次。先保证不能选错，再评估是否支持更多自然语言选择方式；不需要第一版解决任意跨单金额比较。

**准入检查：** 单候选正常比较；双候选未选择必须停止；明确选择后引用、数值与目标券一致；相同数值但不同来源不能凭数值合并成同一引用；旧引用、切单、跨身份/群、取消和候选溢出不能绕过保护。金额正例仍要求 fresh 订单、`refundApproved=false` 和当前 0 知识调用，不扩展成退款上限或批准能力。

## P0-2：事实绑定不由近义动作名称控制

原版本 Controller 由 `action.kind` 计算 `refundQuestion`，再决定是否将券状态/数量附到 query，以及是否构造 `applicability`。在 `007/3`，审计 `facts` 已有 `expired=1 / redeemed=0`，服务却收到 `applicabilityContext=null`。`declared` 配置因此没有检查这些已知必要前提。

建议把**取证对象**与**动作名称**分开。任何已绑定订单的知识请求，都使用本轮成功授权的同一 Order 构建事实快照，保留 `requestId`、`asOf`、商品范围、券数量/状态和有效期事实；不再因为模型选择了 `policy` 就只传商品名。继续使用现有单商品、订单项与券关联完整性检查。事实存在不代表适用条件全部成立，数量/状态门控也不能代替日期、商家批准或商品类别事实。

取证目标建议仅区分两种用途，无需规则引擎：

| 用途 | 宿主行为 | 对回答的约束 |
| --- | --- | --- |
| `current_order`：判断当前订单的资格或处理前提 | 无论 `policy` 或 `refund_eligibility`，都用 fresh 事实执行同一声明前提门控；继续原 score/top5→门控→support 顺序，不补位、不改 rank | 只有当前适用且充分的证据才能支持本单结论；未知前提不是成立 |
| `rule_only`：明确的一般规则或假设条件 | 没有实例时不强造订单。有订单仅用于查商品范围时，仍保留真实事实及范围，但不把现实券状态强加到明确假设上 | 只作保留条件的规则解释，不产生本单已经满足、获批或可执行的证明 |

已有订单引用的咨询默认按当前对象处理；真实一般/假设咨询需要明确的原文条件或匹配前序话题。这个用途不能只是让模型输出 `generic=true` 来关闭保护：trace 应保留依据的本轮原文/真实话题与解释用途，规则解释证据不能被下游准备退款当作当前资格证明。准备业务仍重新授权并执行现有条件检查。无法明确区分时先澄清。

例如实际未核销订单的用户明确询问“假如以后核销，规则会怎样”，不应以它现在 `redeemed=0` 就剔除解释核销后规则的全部证据。反过来，问本单当前需要谁确认，不能因为用了“规则”这个词就进入不检查前提的通道。纯宿主代码不能证明任意自然语言条件是否完整；这一语义边界需要有限协议、保守停止和独立验证，不能宣称增加一个字段便解决所有误分类。

**备选取舍：** 只给所有 query 加 fresh 状态是更小的补丁，能修事实不可见，但仍把是否应用已声明前提交给模型；对所有带订单的查询硬筛当前状态又会误伤真实假设问题。建议采用上述两个证据用途，共用一个事实构造函数和现有门控，不新建检索链路、政策 DSL 或在线裁判。上下文会略增，门控排除的候选不调用 support；收益和 token 成本要在开发对照中实测。

**准入检查：** 同一个当前对象问题分别提供两种动作名称时，授权事实与门控结果一致；切单使用新范围/新状态；原始 `unused` 与 `expiresAt` 过期分开判断；真实一般/假设规则仍可解释；多商品或不完整券关联不能强行匹配；reference 无声明前提仍明确标为未检查。错误额外证据继续单列，即使最终文字说它不适用也不能计接收正确。

生产接收与评分必须一起版本化。[当前评分器](../scripts/c1-session-validation-check.ts) 也按动作名称重建 `purpose`，后续需从新的取证目标和真实 fresh 输出重建，不能直接信 trace 自报。保留旧 schema/manifest/首次成绩，不将旧题的两种动作在事后放宽为通过。

## P0-3：让澄清准确指出缺项

原版本 `clarify(field="intent")` 适合“先处理哪件事”，不适合缺金额来源、渠道、时限或人物的续问。用户可能已经很清楚要退款咨询，再让他重选业务类别不能补齐引用。

建议沿用现有 `clarify` 工具，增加少量有界缺项类型，例如：订单对象、比较基准、政策话题、时间/渠道、主体，以及原有多事项选择。模型只选择类别与 `missing/ambiguous`；文字由宿主模板生成。模板可插入宿主真实候选摘要，不接收任意模型事实或自由改写业务卡片。

金额来源缺失时，应说明当前没有可引用的实际展示，请先查询/展示要比较的金额；两个来源竞争时，应让用户选择基准。时间缺失时，应问清支付渠道及所指等待期限。主体缺失时，应问清哪个操作和谁的许可。只有多事项请求才使用“先处理哪项需求”。这些模板不增加专用澄清判别阶段；普通 Pi 动作轮仍可能有工具后的模型生成，不能计为零模型。

**准入检查：** 既检查 0 不必要知识/业务调用，也审阅用户实际可见回执是否指出缺项、能否使下一轮补充后继续正常流程。安全停止与澄清可用性分列；前者成功不能自动让后者通过。保留自然语言语义审阅，不把“含某个关键词”作为唯一标准。

## 后置问题与业务边界

`024` 的 ET006 排名 1、分数约 0.910；逐字原文“有效期可能较短”被归为 `limitation_only`。本题问能否推出“一定更短”，该原文可以支持“不能据此断定必然”，并不需要证明券事实上一定不短。这属于推断边界的支持误拒，放在前三项之后做有界分类诊断。保留首次失败，不先增加模型阶段、替换模型或针对 ET006/“可能”写生产分支。

`021` 问具体停车场实时空位，却没有说明与团购券/门店服务的业务关系。当前产品返回 `non_business` 有合理依据；旧固定合同要求实际检索后拒收，所以仍保留该合同下的失败。出题审阅补全了地点，却未充分核对产品业务域，这是题集范围适配缺口。后续先确认客服是否承接此类咨询，再制定相应验证合同，不能为得到 4/4 无答案成绩而扩展生产业务。

此前普通周末诊断还存在 SKU→“常规套餐”类别没有可信映射的局限。当前 24 题使用规范商品事实，不证明所有商品别名或规则类别映射已解决。若后续业务需要，增加版本化商家/商品类别与规则绑定，而不是通过名称相似或已取证前问补出分类事实。

## 实施顺序与停止条件

1. 先修金额候选/选择合同和当前对象事实绑定，补确定性工程回归，确保任何近义动作都不能绕过前提。两者分别形成可解释的最小变更。
2. 同步补有界定向澄清及一条“澄清→用户补充→继续”的真实生产 Session 开发闭环；业务写入、金额与授权边界保持原有保护。
3. 在已曝光题上做开发回归，记录原失败、实际动作、接收证据、用户可见回复和成本；再单独处理支持分类的推断边界误拒。真实调用遵循既有授权和预声明预算，先冻结配置，不能遇错重跑覆盖原结果。
4. 候选与评分稳定后，按既定门槛预声明必要的新验证：六类核心逐项完成，缺失/竞争正确停止，金额事实及 0KB 满足，accepted recall 至少 80%、政策误拒至多 10%，直接无答案误收/捏造、范围违规和错误额外证据均为 0；失败与未执行保留分母。最终回复仍由 Codex 逐例审阅、绑定内容 hash，供人复核，未审阅不算通过。

若开发仍需不断添加相似词或按题修分支，应停止扩题，重新核对引用选择和证据用途合同。不得把反复跑过的这 24 题改名为新验证，也不以 MySQL 业务检查通过替代 C1 对话能力准入。
